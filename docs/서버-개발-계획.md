# 서버 개발 계획

> 지금까지 작성한 기획서([전체 개요](서버-시스템-전체-개요.md) 및 [세부 기획서](세부/))를 바탕으로 **실제 개발 순서와 기능별 소요 일정**을 정리한 문서다. 세부 명세(API 스펙·필드·수치)는 각 기획서가 정본이며, 본 문서는 "무엇을 어떤 순서로, 며칠에 걸쳐 만들 것인가"의 로드맵만 다룬다.

## 1. 전제 · 현재 상태

- **대상**: .NET 10 기반 `AccountServer` + `GameServer`, 공통 라이브러리 `TaskbarHero.Common`(netstandard2.0). 클라이언트는 Unity(별도).
- **클라이언트 병행 개발**: 서버와 Unity 클라이언트를 **동시에** 개발한다(별도 트랙). 서버-클라 공유 계약(`TaskbarHero.Common`의 `GameErrorCode`·공유 DTO)과 각 기능의 API 스펙을 **먼저 확정**해, 클라이언트는 목(mock) 응답으로 선행 개발하고 서버 구현이 완료되는 대로 **실연동으로 교체**한다. 본 계획의 소요일은 **서버 트랙 기준**이다.
- **현재**: 두 서버 모두 기본 `weatherforecast` 스캐폴드만 존재. 실제 엔드포인트 미구현.
- **저장소**: MySQL(Account DB / Game DB), Redis(인증 토큰 캐시). 마스터 데이터는 CSV/JSON 원천 → 서버 인메모리 로드.
- **소요일 단위**: 1일 = 개발자 1인 기준 작업일(man-day). 설계 검토·구현·자체 확인 포함, 대규모 부하테스트·QA는 별도(마지막 단계).
- **근무일 기준**: 주말(토·일)은 **기본 제외**(주5일 근무)로 잡는다. 다만 일정이 촉박하면 **상황에 따라 주말에도 작업**해 버퍼를 확보할 수 있다.
- **공통 기반 작업은 별도 진행**: 프로젝트 정리(스캐폴드 제거), DB/Redis 연결·설정, 공통 요청/응답 형식·`GameErrorCode`·공유 DTO, 인증 미들웨어 골격, 예외/로깅 등은 본 계획과 **별도로 진행**하며, 아래 기능 개발의 **선행 전제**로 둔다.
- **추정 성격**: 러프 추정이다. 의존 기능이 밀리면 후속도 밀린다.

## 2. 개발 순서 원칙

1. **선행이 없는 것부터 착수한다.** 의존 관계가 없는 계정/인증·마스터 데이터를 먼저(필요 시 병행) 시작하고, 저장/로드가 열리면 그 위에 콘텐츠 기능을 쌓는다. 저장/로드 전에는 어떤 게임 기능도 검증할 수 없다.
2. 각 게임 기능은 **서버 권위**로 구현한다(클라이언트 보고값 불신). 재화·성장·보상 계산은 서버가 확정.
3. 재화·아이템을 건드리는 기능(인벤토리·거래소·메일·보상)은 **원자성(트랜잭션)** 을 우선한다.
4. 메일 시스템은 거래소·출석부의 보상 지급 경로이므로 그 둘보다 **먼저** 완성한다.
5. **클라이언트 병행을 위해 계약을 먼저 굳힌다.** 각 기능은 구현에 앞서 API 요청/응답 스키마와 공유 DTO·에러 코드를 확정해 클라이언트가 목(mock)으로 병행 개발할 수 있게 하고, 기능 완료 시 실연동으로 전환한다.

## 3. 기능별 개발 계획

> 아래는 **선행 관계를 위상 정렬**해 먼저 착수 가능한 순서로 나열한 것이다. 선행이 없는 **계정/인증**·**마스터 데이터**가 착수 지점이며, 이 둘은 서로 다른 서버(Account/Game)라 **병행 가능**하다. `선행` 열의 번호는 본 표의 순번을 가리킨다. 공통 기반 작업은 별도 진행이라 모든 기능의 암묵적 전제이며 개별 표기하지 않는다.

| 순번 | 단계 / 기능 | 서버 | 개발 내용(요약) | 선행 | 예상 |
|---|---|---|---|---|---|
| 1 | **계정 / 인증** | Account | 회원가입·로그인, BCrypt 해시, 토큰 발급(HMAC), `users`/`user_auth_token`, Redis 토큰 캐시, 단일 세션 | — | 1~2일 |
| 2 | **마스터 데이터 로더/제공** | Game | CSV/JSON 원천 로드·인메모리 캐시, 각 `*_master` 조회 계층, 코드 검증 유틸(FK 대체) | — | 3일 |
| 3 | **세이브 데이터 저장·로드** | Game | 신규 계정 초기화, 전체 세이브 스냅샷 로드(`/load`), 각 테이블 영속화 골격, 저장 정책(액션별 즉시 반영) | 1 | 3일 |
| 4 | **스테이지 / 전투 결과** | Game | 진행도·난이도 관리, 클리어 보고 검증, `stage_reward` 기반 보상 확정·지급 | 2,3 | 3일 |
| 5 | **방치형(오프라인) 보상 정산** | Game | `last_active_at` 기준 경과시간 산출, 골드·경험치 지급, 상한/캡 정책 | 2,3,4 | 3일 |
| 6 | **인벤토리 / 아이템 / 큐브** | Game | 획득·배치·장착/해제(`player_item_equipped`), 강화, 용량 확장, 큐브 합성/분해, 상자 열기 | 2,3 | 3일 |
| 7 | **성장(직업·스킬·룬)** | Game | 캐릭터 생성(직업), 스킬 레벨업/장착, 룬 업그레이드, 재화 소모 검증 | 2,3 | 4일 |
| 8 | **메일(보상) 수신** | Game | 우편함 조회, 첨부 수령(재화·아이템 반영), 만료·읽음 상태, 중복 수령 방지 | 3,6 | 3일 |
| 9 | **출석부 보상** | Game | KST 자정 일자 경계, 하루 1회 수령 검증, 보상 메일 발급 | 3,8 | 2일 |
| 10 | **거래소 / 교역선** | Game | 판매 등록(에스크로), 구매·취소, 소유권 이전·대금 정산(메일 경유), 경합 검증 | 3,6,8 | 4일 |
| 11 | **통합 · 안정화** | 공통 | E2E 시나리오 점검(**클라이언트 실연동 포함**), 동시성/경합 검증, 부하 테스트, 버그 수정·문서 정합화 | 1~10 | 4일 |

**착수 순서(선행이 풀리는 흐름)**

- **즉시 착수(선행 없음)**: 1 계정/인증, 2 마스터 데이터 — 서로 다른 서버라 병행 가능.
- 1 완료 → **3 세이브** 착수 가능.
- 2·3 완료 → **4 스테이지 / 6 인벤토리 / 7 성장** 착수 가능(서로 독립).
- 4 완료 → **5 오프라인 보상**, 6 완료 → **8 메일**.
- 8 완료 → **9 출석부**, 6·8 완료 → **10 거래소**.
- 전부 완료 → **11 통합·안정화**.

> **1주차 프로토타입 전투(데모용)**: 범위를 다음 둘로 **한정**한다 — ① **시각화용 데이터 제공**: 몬스터·스테이지 스탯 등 마스터 데이터를 클라가 자동 전투를 그릴 수 있게 내려준다. ② **최소 전투 진행**: 간이 전투 루프로 진행·승패 결과만 산출한다. **보상 지급·진행도 저장·클리어 검증은 제외**한다. 이 범위는 **마스터 데이터(2)에만 의존**하므로 세이브(3)를 기다리지 않고 마스터 데이터 완료 직후 착수해 **1주차 안에 클라이언트 전투 데모**를 낼 수 있다. 진행도 저장·클리어 보상·결과 검증 등 정식 기능은 그대로 4단계(2주차)에서 완성한다.

## 4. 일정 요약

- **합계**: 약 **35~36일**(man-day, 공통 기반 작업 제외; 1주차 프로토타입 전투 2일 포함). 1인 기준 대략 **7주**.
- **마일스톤**
  - **M1 — 착수 기반 (1~3) + 프로토타입 전투**: 약 9~10일. "인증·마스터 데이터에서 시작해 접속·세이브가 오가고, 1주차에 보상 없는 전투 데모를 시연한다."
  - **M2 — 핵심 게임 루프 (4~7)**: 약 13일. "전투·오프라인 보상·인벤토리·성장이 돈다."
  - **M3 — 부가 시스템 (8~9)**: 약 5일. "메일·출석부까지 붙는다."
  - **M4 — 거래소·마무리 (10~11)**: 약 8일. "거래소 완성 후 통합 안정화."

### 일정 적합성

- **평일 기준 총량**: 주말 제외 시 평일은 **주5일 × 5주 = 25일**이다. 계획 합계 **약 35~36md**(프로토타입 전투 2일 포함)와 10~11md 차이가 나므로, 평일만으로는 창구 안에 담기지 않는다.
- **주말 버퍼**: 창구 내 주말은 4회(약 8일)다. 상황에 따라 주말을 쓰면 최대 **약 33일**까지 확보되지만, 그래도 35~36md에는 약 2~3일 부족하다.
- **8-21 준수 방법**: (a) 1주차의 **계정/인증(Account) ∥ 마스터 데이터(Game) 병행 착수**로 약 1~2일 단축, (b) **통합·안정화를 각 주 개발과 병행**(마지막에 몰지 않고 롤링 검증)해 약 2일 흡수, (c) 남는 부족분은 **주말 작업**으로 메운다. 인력이 2인이면 3주차의 **인벤토리 ∥ 성장** 병행으로 주말 없이도 여유가 생긴다.
- **프로토타입 전투는 데모 우선순위에 따른 추가 부하**다. 1주차 계정/인증(Account, 1~2일) 완료 후 남는 여력이나 주말로 흡수하되, 흡수가 어려우면 정식 전투(4단계)로 통합하거나 보상 없는 최소 시연으로 범위를 더 줄인다.
- 위 표는 (a)·(b)를 반영한 **목표 일정**이며, 주 배정량이 5일(평일)을 넘는 주는 그만큼 주말 작업이 필요함을 의미한다.
- **1주차 지연 시 이월**: 1주차 분량(9~10md)은 평일 5일을 초과하므로 병행·주말로도 다 못 끝낼 수 있다. 이 경우 **미완분(주로 세이브 마무리·프로토타입 전투)은 2주차로 이어서 진행**한다. 다만 2주차 기능(4 스테이지/전투 등)이 세이브(3)에 의존하므로, **세이브를 프로토타입 전투보다 우선 마무리**해 후속 지연을 막는다.

## 6. 리스크 · 비고

- 마스터 데이터 **수치 값**(밸런스)은 아직 미확정([전체 개요](서버-시스템-전체-개요.md) 6장). 값이 늦어지면 4·5·6·7단계의 실제 검증이 지연될 수 있어 병행 확보가 필요하다.
- **동시성 경합**(거래소 구매·인벤토리 중복 소모·메일 중복 수령)은 구현보다 검증에 시간이 든다. 11단계에 여유를 두었다.
- `enhance_master`·`box_master` 등 일부 규칙은 "값 미확정"이라 해당 하위 기능(강화·상자)은 골격 먼저, 수치 확정 후 채우는 방식으로 나눌 수 있다.
- **초반 순서 고정(마스터·세이브 → 스테이지/전투)**: 스테이지/전투를 마스터 데이터·세이브보다 앞당기는 순서 교체는 **불가**하다. 전투 계산은 `monster_master`·`stage_master`·`stage_reward`에, 진행도·보상 반영은 세이브 영속 계층에 의존하므로 두 선행이 먼저 완료돼야 한다. 따라서 현재 순서를 유지한다.
