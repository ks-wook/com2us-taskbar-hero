# 제1부 — 서버

## 1. 개발 환경

| 구분 | 내용 |
|---|---|
| 런타임 | .NET 10 · ASP.NET Core Web API |
| 구성 | `AccountServer`(계정·인증, `:5160`) · `GameServer`(게임 로직, `:5247`) · `TaskbarHero.Common`(공유 라이브러리) |
| 공유 라이브러리 | `netstandard2.0;net10.0` 멀티타겟 — 서버는 `ProjectReference`, Unity 클라이언트는 **로컬 UPM 패키지**로 같은 소스를 소비 |
| DB | MySQL 8.4 (Docker Compose) — 게임 DB / 마스터 DB 분리 |
| 캐시·부가 저장소 | Redis 8.2 (Docker Compose, `127.0.0.1:6379`) — **인증 토큰, 배치 리더 락**. 게임 데이터 조회 캐시는 실측 후 전부 제거했다(인벤토리 §6.5 · 거래소 §7.3) |
| 데이터 접근 | **SqlKata** 쿼리 빌더 + Dapper 제네릭 매핑(원시 SQL 조립·`dynamic` 금지) |
| Redis 접근 | **CloudStructures** 타입 구조체 |
| 로깅 | **ZLogger** (구조화 필드, `:@PascalCase` 규약) |
| 개발 도구 | **Claude Code**(CLI) · Swagger UI(`/swagger`, Development 전용) · `.http` 파일로 수동 호출 |
| 문서 | Markdown + Mermaid(ERD·시퀀스 다이어그램) |

## 2. 개발 방식 한눈에 보기

**AI 코딩 에이전트에게 코드를 바로 시키지 않고, 항상 문서를 먼저 만들고 그 문서를 근거로 구현을 요청했다.**

```
① 기획서 요청  →  ② 검토·확정  →  ③ 문서대로 구현 요청
                                          ↓
      ⑥ 현황판 갱신  ←  ⑤ 문서 동기화  ←  ④ 빌드 + 실서버 검증
```

핵심은 **"무엇을 만들지"와 "어떻게 만들지"를 분리한 것**이다. 기획서 단계에서 API 스키마·DB 구조·에러 코드·예외 처리를 먼저 확정하고, 구현 단계에서는 그 문서를 그대로 지시서로 썼다. 덕분에 구현 중에 설계를 즉흥적으로 바꾸는 일이 줄었고, 나중에 "왜 이렇게 했더라"를 코드가 아니라 문서에서 확인할 수 있었다.

## 3. 개발 루프 — 문서 → 구현 → 검증 → 동기화

### 3.1 ① 기획서부터 요청한다

새 기능은 코드가 아니라 **기획서 작성 요청**으로 시작했다. 이를 위해 `.claude/skills/design-doc` 커스텀 스킬을 두어, 요청만 하면 항상 같은 위치·같은 템플릿으로 문서가 나오게 했다.

- 위치: `docs/세부/<기능명>-기획서.md`
- 고정 목차: **개요 · 기능 설명 · 요구사항 · 데이터 모델 · API 명세 · 처리 흐름 · 에러 코드 · 미결 사항 · 참고**
- 작성 시 기존 `CLAUDE.md`·`ErrorCode.cs`·기존 문서를 먼저 읽어 **계약 충돌이 없는지 확인**하도록 절차에 못 박음

가장 중요하게 지킨 것은 **"확정"과 "그렇게 정한 이유"를 함께 남기는 것**이다. 예를 들어 거래소 기획서에는 "구매 직렬화는 MySQL 조건부 갱신으로만 하고 Redis 락을 두지 않는다(확정)"와 그 근거(락을 얹으면 TTL 만료·해제 실패·Redis 장애라는 실패 경계만 늘어난다)가 함께 적혀 있다. 이 기록이 있어야 몇 주 뒤에 같은 논쟁을 반복하지 않는다.

### 3.2 ② 검토·확정

작성된 기획서를 읽고 **미결 사항과 판단이 갈리는 지점만 짚어 되물었다.** 이 단계에서 스키마·정책이 여러 번 바뀌었고, 바뀔 때마다 문서를 고쳐 확정안만 남겼다(변경 이력은 문서에 남기지 않고 최종 상태만 유지).

### 3.3 ③ 문서대로 구현을 요청한다

구현 요청은 **"기획서 5.2를 구현해줘"** 같은 형태였다. 자유도를 좁히기 위해 프로젝트 공통 규칙을 `CLAUDE.md`에 미리 고정해 두었다.

- 컨트롤러에는 **HTTP 액션 메서드만** 두고, 공통 보조는 `GameApiControllerBase`에 상속으로
- 서비스 클래스의 **모든 메서드에 `/// <summary>` 주석** 필수
- DB 결과는 `dynamic` 금지 — POCO/스칼라 **제네릭 매핑**만
- 재화·아이템 변경은 **단일 트랜잭션**, 서버 권위(클라이언트 보고 불신)
- 로깅은 서비스 계층에서 ZLogger 확장 메서드로, 사용자 실수는 로깅하지 않음

### 3.4 ④ 빌드 + 실서버 검증

구현 후에는 반드시 **빌드와 실제 동작 검증**을 거쳐야 완료로 인정했다.

```
기존 서버 강제 종료 → dotnet build → 포어그라운드 기동 → 헬스 체크 → 시나리오 → 강제 종료·잔여 0 확인
```

- 서버는 **반드시 보이는 콘솔 창**으로 띄운다. 숨김·백그라운드 기동을 금지한 이유는, 남은 프로세스가 `bin/` 파일을 잠그거나(MSB3021) **다음 테스트가 옛 바이너리를 검증**하게 만들기 때문이다.
- 검증은 실제 MySQL·Redis에 붙여 API를 호출하고, 결과를 **DB에서 직접 대조**했다. 테스트로 만든 데이터는 되돌렸다.

### 3.5 ⑤ 문서 동기화 — 이 프로세스의 핵심

기능을 바꾸면 **같은 작업 안에서** 관련 문서를 전부 갱신하도록 규칙을 두었다. 세부 기획서가 정본이고, 아래 셋은 기획서를 가로질러 모은 **집약 참조본**이라 하나만 바뀌면 곧 불일치가 된다.

| 무엇이 바뀌면 | 갱신할 문서 |
|---|---|
| 엔드포인트·요청/응답 필드 | `docs/공통/api-통합.md` |
| DB 테이블·컬럼·마스터 데이터 | `docs/공통/db-erd-통합.md` (+ `db-schema.sql`) |
| 에러 코드 추가·폐기 | `docs/공통/error-code-정의.md` + `TaskbarHero.Common/ErrorCode.cs` |
| 처리 흐름 | `SequenceDiagram/README.md` (기능별 Mermaid 시퀀스) |

정합성 체크는 **양방향**으로 했다 — 기획서 → 통합 문서(빠진 항목 추가)와 통합 문서 → 기획서(폐기된 항목이 남아 있지 않은지). 경로나 이름을 바꿨으면 옛 문자열이 문서 어디에도 남지 않았는지 `grep`으로 확인했다.

### 3.6 ⑥ 현황판 갱신

기능이 끝나면 `README.md`의 개발 현황 체크리스트를 갱신했다(☐ 미착수 → ◐ 진행 중 → ☑ 완료). **서버 구현과 클라이언트 실연동을 각각 표시**해, 어느 쪽이 밀렸는지 한눈에 보이게 했다.

## 5. 규칙의 축적 — CLAUDE.md

같은 실수가 반복될 때마다 **그 교훈을 `CLAUDE.md`에 규칙으로 적어 고정**했다. 이 파일은 매 작업 시작 시 자동으로 읽히므로, 한 번 적은 규칙은 이후 모든 작업에 적용된다.

실제로 쌓인 규칙의 예:

| 규칙 | 생긴 이유 |
|---|---|
| 서버는 포어그라운드로만 기동, 테스트 후 강제 종료 | 숨겨진 서버가 남아 옛 바이너리를 검증하는 사고 |
| DB 조회 결과에 `dynamic` 금지 | 컴파일 타임 타입 검사 상실 + 튜플/변환 런타임 오류 |
| JSON 문자열 컬럼 금지, 반복 구조는 자식 테이블로 | 스키마 확장 시 마이그레이션 지옥 |
| 기능 구현 시 통합 문서 동기화 + 정합성 체크 | 문서 간 불일치가 반복적으로 발생 |
| 서비스 메서드 전체에 요약 주석 필수 | 나중에 읽을 때 의도 파악 비용 |

즉 `CLAUDE.md`는 프로젝트 규약이자, **작업 방식 자체를 코드처럼 버전 관리한 결과물**이다.

## 6. 실제 진행 사례

**(1) 문서 → 구현 (전형적인 흐름)**

```
2026-07-30  ffb483e  소모품(골드, 경험치 부스터) 기획서 작성   ← 기획서 + README 현황판만
2026-07-30  4fcd462  소모품 사용기능 추가                      ← 컨트롤러·서비스·리포지토리 구현
```

기획서 커밋에는 문서만 들어 있고, 구현 커밋에는 코드만 들어 있다. 기획서가 곧 구현 지시서 역할을 했다.

**(2) 구현과 설계 문서를 같은 작업 단위로**

가챠는 구현(`6cb7260`)과 설계 문서(`2de13e1`)를 **37초 간격으로 연속 커밋**했다. 커밋은 나뉘었지만 같은 작업에서 코드와 문서를 함께 맞춘 사례이고, 이때 `api-통합`·`db-erd-통합`·`db-schema.sql`·`error-code-정의`가 한 번에 동기화됐다.

**(3) 문서가 있어 되돌릴 수 있었던 사례 — 인벤토리 캐시**

```
2026-07-31  e05f4d4  인벤토리 아이템 조회에 대한 캐싱 기능 추가
2026-07-31  98e30fd  인벤토리 데이터 캐싱 기능 추가
2026-08-04  666411b  유저 인벤토리 캐싱기능 제거
```

가방 조회에 Redis write-through 캐시를 넣었다가, 나중에 **성능·정합성 관점에서 재검토해 제거**했다(개인 데이터라 공유 이득이 없고, 쓰기마다 가방 전량을 다시 쓰는 증폭이 컸다). 이때 기획서에 도입 근거가 남아 있었기에 **무엇을 전제로 넣었고 그 전제가 왜 깨졌는지**를 대조할 수 있었고, 제거와 함께 그 판단을 다시 문서에 기록했다. 거래소의 Redis 락도 같은 방식으로 재검토해 제거했다.

## 7. 이 방식의 효과와 한계

**효과**

- **재작업이 줄었다.** API 스키마·에러 코드를 문서에서 먼저 확정하니, 구현 후 계약이 바뀌어 클라이언트까지 고치는 일이 적었다.
- **판단 근거가 남는다.** "왜 락을 안 쓰는가", "왜 캐시를 뺐는가"가 문서에 있어 나중에 다시 논쟁하거나 잘못 되돌리는 일을 막았다.
- **AI 에이전트의 출력 품질이 안정됐다.** 자유롭게 시키면 매번 다른 구조가 나오지만, 기획서 + `CLAUDE.md` 규칙을 근거로 시키면 결과가 일정하다.
- **클라이언트 병행 개발이 가능했다.** 계약(요청/응답·에러 코드)이 먼저 확정되므로 클라이언트가 목(mock)으로 먼저 붙일 수 있었다.

**한계**

- **문서 유지 비용이 크다.** 기능 하나를 바꾸면 최대 5개 문서(세부 기획서 · api-통합 · db-erd-통합 · error-code-정의 · 시퀀스 다이어그램)를 함께 손대야 한다.
- **집약 문서는 항상 불일치 위험을 안는다.** 그래서 "같은 작업에서 갱신 + 양방향 정합성 체크"를 규칙으로 강제해야 했다.
- **작은 수정에는 과하다.** 버그 픽스·UI 조정처럼 계약이 바뀌지 않는 작업은 이 루프를 타지 않고 바로 수정했다.

# 제2부 — 클라이언트(Unity)

> 클라이언트는 **Unity 에디터라는 상태를 가진 GUI 프로그램**을 다뤄야 해서, 서버와 만드는 방법도 검증하는 방법도 다르다. 그 차이를 [9장](#9-개발-방식-한눈에-보기)에 먼저 정리하고, 각 항목을 10~13장에서 풀어 쓴다.

## 9. 개발 방식 한눈에 보기

**서버가 확정한 계약 위에서, 화면을 손으로 조립하지 않고 "화면을 만드는 코드"로 굽고, 검증은 에디터를 원격 조작해서 했다.**

```
① 서버 계약 확정(1부 산출물: api-통합 · error-code-정의 · 세부 기획서)
        ↓
② 클라 UI 기획서 작성 — 화면 구성·리소스 경로·바인딩·상호작용 흐름
        ↓
③ 에디터 빌더 스크립트로 화면을 '굽고', 런타임 컨트롤러를 배선
        ↓
④ Unity MCP로 플레이 모드 진입 → 상태 조회·스크린샷으로 검증
        ↓
⑤ 클라 문서 갱신 + README 현황판의 '클라 실연동' 칸 갱신
```

서버 루프(2장)와 뼈대는 같다 — 문서를 먼저 확정하고 그 문서를 지시서로 쓴다. 다른 것은 **③의 산출물과 ④의 검증 수단**이다. ③에서 만드는 것은 화면 자체가 아니라 **화면을 생성하는 코드**이고, ④는 서버를 띄워 API를 호출하는 대신 **에디터에 스니펫을 실행해** 플레이 모드를 조작한다.

| | 서버(1부) | 클라이언트(2부) |
|---|---|---|
| 무엇을 근거로 만드나 | 세부 기획서(정본) | 서버 계약 + 원작 캡처 → **UI 기획서(표현만, 계약 복제 금지)** |
| 무엇을 산출하나 | 컨트롤러·서비스·리포지토리 | **화면을 생성하는 에디터 빌더** + 런타임 컨트롤러 |
| 어떻게 검증하나 | 서버 기동 → API 호출 → DB 대조 | **Unity MCP로 에디터 원격 조작** → 상태 조회·스크린샷 |
| 잘못됐을 때 | 코드 고쳐 재기동 | 빌더의 숫자를 고쳐 **화면을 다시 굽는다** |
| 자산은 어디서 오나 | (해당 없음) | 외주·구매 없이 **스크립트로 절차적 생성** |

핵심은 **"만든 결과가 아니라 만드는 절차를 코드로 남긴 것"** 이다. 화면·아이콘·이펙트·마스터 데이터 번들 모두 산출물을 직접 편집하지 않고 **그것을 생성하는 스크립트**를 두었고, 그래서 어느 것이든 "다시 만들어라"가 실행 가능한 요청이 된다(자세한 이점과 그 대가는 11·13·14장).

**세션과 권한도 나눴다.** 저장소 루트의 세션은 서버 담당이고, `com2us-taskbar-hero-client/`에는 **자체 `CLAUDE.md`** 를 둬 그 폴더에서 시작한 세션만 클라이언트를 만지게 했다.

- 클라 세션은 **서버를 어떤 방법으로도 띄우지 않고**(사용자가 직접 올린다), 이미 떠 있는 서버를 임의로 죽이지도 않는다. 서버 세션 규칙(포어그라운드 기동 후 반드시 종료)과 정반대인데, 사용자가 테스트용으로 올려 둔 프로세스를 클라 세션이 내려 버리는 사고를 막기 위한 분리다.
- 같은 이유로 **네트워크 실연동 검증은 사용자가 명시적으로 요청할 때만** 하고, 그 외에는 컴파일·씬 구성·UI 흐름까지만 확인했다. 그래서 현황판의 `클라 실연동` 칸은 **배선만 된 상태는 ◐**, 서버까지 붙여 확인한 것만 ☑로 구분한다.

## 10. 계약은 서버, 표현은 클라 — 문서 분리와 원작 캡처

**클라이언트 문서는 서버 계약을 절대 복제하지 않는다.** API 스키마·에러 코드·DB 규칙은 서버 문서가 정본이고, 클라 UI 기획서는 그 문서를 **링크로 참조**한 뒤 표현(presentation)만 다룬다. 실제 인벤토리 UI 기획서 서두가 그 형태다 — "서버 권위 규칙·데이터 모델·API·에러코드는 서버 기획서가 정본이며 여기서 복제하지 않는다".

| 문서 | 위치 | 담는 것 |
|---|---|---|
| 서버 세부 기획서 | `docs/세부/` | 규칙·API·데이터 모델(정본) |
| 클라 UI 기획서 | `com2us-taskbar-hero-client/docs/ui/` | 화면 구성·리소스 경로·바인딩·조작 흐름 |
| 클라 씬 구성 | `com2us-taskbar-hero-client/docs/클라이언트-씬-UI-구성.md` | 씬·오브젝트·패널의 큰 그림 |

```
com2us-taskbar-hero-client/
├── CLAUDE.md                     # 클라 세션 전용 규칙(서버 세션과 분리)
└── docs/
    ├── README.md                 # 클라 문서 목록(새 문서는 여기 링크)
    ├── 클라이언트-씬-UI-구성.md    # 씬·오브젝트·패널 큰 그림(서버 도메인 대응)
    ├── 투명-오버레이-창.md         # 원작형 배경 투명화(DWM per-pixel alpha)
    ├── 전투-연출-개선-아이디어.md   # 타격감·전투 리듬 목록 + 적용 결과·미채택 사유
    └── ui/                       # 화면별 UI 기획서 8종
        ├── 인벤토리 · 스테이지 선택 · 뽑기 · 파티 편성
        ├── 스킬 레벨업 · 룬 · 공용 모달
        └── 텍스트-선명도.md        # 원인 분석·측정값
```

**원작 화면 캡처가 UI 명세의 출발점이다.** `docs/images/`에 원작 게임 화면 **29장**을 넣고 서버 세부 기획서가 그것을 본문에 임베드한다(예: 인벤토리 기획서의 `인벤토리_전체`·`장비아이템`·`큐브합성`·`인벤토리_확장`). 클라이언트 작업은 그 그림을 근거로 시작해, UI 기획서에서 **실제 에셋 경로와 픽셀 수치까지 확정**한다.

```
원작 캡처(docs/images/*.png)
   → 서버 세부 기획서에 임베드 = "무엇을 모작하는가"
      → 클라 UI 기획서 = "어떤 에셋으로 어떻게 그리는가"
         → 에디터 빌더 = 그 명세대로 계층을 생성
```

예를 들어 스테이지 선택 UI 기획서는 지역 창 배경(`Assets/Art/Background/stage_ui_bg/stage_ui_bg_{1~5}.png`, 2816×1536)·창 테두리(`window_frame_hollow.png`, 9-slice 경계 20px)까지 못 박아 두고, **"가운데가 불투명한 `window_frame.png`는 쓸 수 없다"** 처럼 실패한 선택지도 함께 남겼다. 텍스트로 이렇게까지 고정해 두면 에이전트가 매번 다른 에셋을 고르는 일이 없다.

## 11. UI를 손으로 만들지 않는다 — 에디터 빌더

**클라이언트 개발에서 가장 결정적인 방식 변경이다.** AI 에이전트는 Inspector에서 오브젝트를 끌어다 놓거나 화면을 눈으로 보며 배치를 다듬을 수 없다. 그래서 UI를 손으로 조립하는 대신 **"계층을 생성하는 에디터 스크립트"를 작성**해, 메뉴 한 번으로 화면을 다시 굽는 방식을 택했다.

- `Assets/Editor/`에 **35개** 에디터 스크립트, 그중 **13개가 `*UiBuilder`** 다(`InventoryUiBuilder` · `StageUiBuilder` · `GachaUiBuilder` · `MailUiBuilder` · `RuneUiBuilder` · `SkillUiBuilder` · `TradeUiBuilder` · `CubeUiBuilder` · `AttendanceUiBuilder` · `ModalUiBuilder` · `SettingsUiBuilder` · `OfflineRewardUiBuilder` · `CharacterSelectUiBuilder` 등).
- 실행은 에디터 상단 메뉴 `TaskbarHero/UI/...`. 씬 이동은 `SceneSwitcher.cs`가 `TaskbarHero/씬/<이름>` + `Alt+숫자`로 제공한다.

![에디터 메뉴 TaskbarHero/UI — 화면별 빌더가 메뉴 항목으로 노출된다](images/개발환경-images/에디터-빌더-스크립트.png)

위 화면이 이 방식의 실제 모습이다. 화면 하나하나가 **메뉴 항목 하나**로 노출되고(거래소·인벤토리·뽑기·메일·룬·스킬·스테이지·큐브·출석부·모달·오프라인 보상·캐릭터 선택 패널 등), 옆 카테고리에는 마스터 데이터 갱신·씬 이동·사운드·빌드가 함께 붙어 있다. **"UI를 다시 만들어라"가 클릭 한 번**이 되는 것이 요점이다.

이 방식의 이점은 그대로 **AI 협업의 이점**이다.

| 이점 | 설명 |
|---|---|
| 재현 가능 | 화면이 "누가 언제 드래그했는지 모르는 상태"가 아니라 **코드에서 재생성**된다. 깨지면 다시 굽는다 |
| 리뷰 가능 | UI 변경이 `.unity`/`.prefab` 바이너리 덩어리가 아니라 **C# diff**로 드러난다 |
| 대화로 수정 가능 | "패널 폭을 줄여라"를 빌더의 숫자 하나로 바꿔 재실행할 수 있다 |

**대신 이 방식 고유의 함정이 생겨 규칙으로 고정했다.**

| 규칙 | 생긴 이유 |
|---|---|
| 구워 둔 UI의 버튼 핸들러는 **런타임에 다시 연결**한다(`WireRuntime()`) | `onClick.AddListener`는 비영구 리스너라 프리팹·씬에 직렬화되지 않는다 — 빌드 시점에 붙인 리스너가 실행 시 사라져 버튼이 안 눌렸다(편성 씬 '뒤로'·'캐릭터 추가'에서 실제 발생) |
| 빌더는 **공용 아트의 임포트 설정을 바꾸지 않는다** | `Multiple`로 임포트된 텍스처를 `Single`로 바꾸면 서브 스프라이트가 삭제돼 **그것을 참조한 모든 프리팹·씬의 참조가 한꺼번에 끊긴다**(`modal_bg`·`pixel_rpg_button`에서 실제 발생). 빌더는 읽어서 배선만 한다 |
| 새 씬은 `SceneSwitcher` + Build Settings + `FullGameBuilder` 목록에 **함께** 등록한다 | 빠지면 런타임 `LoadScene`이 실패한다. `[MenuItem]`은 컴파일 타임 속성이라 동적 생성이 불가해 항목을 손으로 늘려야 한다 |
| 전투는 `BattleDevScene`이 정본, `GameScene`은 **빌더로 복제**한다 | 하네스 씬에서 전투를 개발하고 `DungeonBattleBuilder`(메뉴 `TaskbarHero/UI/던전 전투 배선`)로 GameScene에 옮긴다. GameScene을 직접 손대면 두 씬이 갈라진다 |

**개발용 하네스 씬을 따로 둔 것도 같은 계열의 선택이다.** 전투(`BattleDevScene`)와 애니메이션(`AnimDevScene`)은 게임 흐름 전체를 타지 않고도 그 부분만 켜서 볼 수 있게 격리했다. `AnimDevScene`은 `Assets/Animations/`에 클립을 넣고 씬 생성 메뉴를 다시 실행하면 목록에 자동 배선되므로, 새 모션을 확인하는 비용이 거의 없다.

![BattleDevScene — 파티 4인 스탯·스킬 쿨다운·소환 선택을 IMGUI로 띄운 전투 하네스](images/개발환경-images/BattleDevScene.png)

`BattleDevScene`은 **로그인·스테이지 진입을 거치지 않고 전투만 켠다.** 화면 왼쪽 위 IMGUI 박스에 파티 4인의 사거리·스킬별 쿨다운 잔여 시간·처치 수·파티 전진 좌표가 실시간으로 나오고, 원하는 몬스터를 즉시 소환할 수 있다. 덕분에 "광역 데미지가 몇 대에 들어갔는지", "쿨다운이 실제로 도는지"를 숫자로 확인하며 전투를 다듬을 수 있었다. 이 IMGUI는 **개발 전용**이라 `serverMode=true`인 `GameScene`에서는 `OnGUI`가 자동으로 생략된다(적 HP바처럼 게임에도 필요한 것만 남는다).

![AnimDevScene — 클립 목록·직업/성별 전환·무기 강화 단계별 이펙트를 한 화면에서 확인](images/개발환경-images/AnimDevScene.png)

`AnimDevScene`은 **캐릭터 한 명만 두고 표현을 확인하는 씬**이다. 왼쪽은 SPUM 프리팹에서 런타임에 읽어 만든 클립 목록(IDLE·MOVE·ATTACK·DAMAGED·DEBUFF·DEATH·OTHER + `Assets/Animations/`의 추가 클립 + 분노·돌진·화살비 같은 특수 모션)이고, 위쪽에서 직업·성별을 바꿔 같은 모션을 비교한다. 오른쪽 **무기 강화 단계(+0~+10) 버튼**은 강화 이펙트 검증용으로, 누르면 잔상 색·무기에 서린 빛·반짝임이 즉시 바뀐다 — 이 하네스는 잔상을 항상 방출하므로 `IDLE`에서 보이는 것이 곧 **상시 이펙트**다.

하네스의 공통점은 **검증 대상만 남기고 나머지를 잘라낸 것**이다. Unity MCP로 원격 검증할 때(12장) 진입 단계가 짧을수록 실패 지점이 줄고, 측정값도 다른 시스템에 오염되지 않는다. 같은 계열의 세 번째 하네스인 `CharacterDevScene`(몬스터 능력치·외형을 눈으로 확정하는 저작 화면)은 몬스터 파이프라인과 함께 [14장](#14-요청-한-줄로-몬스터를-만든다--master-monster-파이프라인)에서 다룬다.

## 12. Unity MCP로 에디터를 원격 조작해 검증한다

클라이언트 검증은 **Unity MCP**(`mcp__unity-mcp__*`)로 에디터에 C# 스니펫을 실행(`Unity_RunCommand`)해서 했다. 확립한 순서는 다음과 같다.

```
EditorSceneManager.OpenScene("Assets/Scenes/TitleScene.unity")   # NetworkManager가 있는 유일한 씬
  → EditorApplication.EnterPlaymode()
  → Session.SetAuth(userId, token)                               # 실토큰 주입(로그인 UI 조작 불필요)
  → 검증할 클라 코드 직접 호출(예: InventoryLoader.ReloadAll)
  → 상태 조회(result.Log) · 필요하면 ScreenCapture로 화면 확인
  → SceneManager.LoadScene("GameScene") + UIManager.ShowInventory()  # UI까지 확인
  → ExitPlaymode
```

**GUI를 원격 조작하는 일이라 함정이 많았고, 그 목록 자체가 자산이 됐다.**

| 함정 | 우회 |
|---|---|
| `Resources.FindObjectsOfTypeAll`은 씬 인스턴스가 아니라 **프리팹 에셋**을 잡는다 — 값을 쓰면 에셋이 오염된다(로그인 패널에 테스트 계정이 박힌 사고) | `Object.FindFirstObjectByType(type, FindObjectsInactive.Include)`로 씬 오브젝트만 잡는다 |
| `Unity_GetConsoleLogs`는 런타임 `Debug.Log`를 캡처하지 못한다(컴파일 메시지만) | 후속 커맨드에서 `result.Log(...)`로 상태를 직접 조회한다 |
| `Unity_Camera_Capture`는 `Camera.Render` 기반이라 **ScreenSpaceOverlay 캔버스(대부분의 패널)가 안 찍힌다** | `ScreenCapture.CaptureScreenshot(경로)` → 파일을 읽어서 본다 |
| RunCommand 샌드박스는 `TaskbarHero.Common`을 참조하지 않아 공유 DTO를 직접 만지면 컴파일 실패 | 리플렉션으로 우회(`GetProperty("Bag").GetValue(null)` 등), `using System.Reflection;` 없이 정규화 이름 사용 |
| 지연 생성되는 UI는 존재하지 않아 잡히지 않는다 | 그 씬 컨트롤러의 진입 메서드를 리플렉션으로 직접 호출해 같은 커맨드 안에서 생성시킨다 |

**Unity 고유의 "안 바뀐다" 함정 둘은 코드로 막아 뒀다.**

- 이 프로젝트는 **Enter Play Mode Options의 `DisableDomainReload`가 켜져 있어** 플레이를 껐다 켜도 `static` 필드가 살아남는다. 마스터 데이터 JSON을 최신화해도 옛 수치가 계속 쓰인 사고가 있었고(몬스터 HP 500 → 150 → 75로 낮췄는데 게임은 계속 500/150), 지금은 `MasterDataManager.ResetCacheOnPlay()`(`[RuntimeInitializeOnLoadMethod]`)와 `MasterDataChangeWatcher`(JSON 변경 시 캐시 무효화)가 자동 처리한다.
- **플레이 중 스크립트를 고치면 도메인 리로드로 전투가 조용히 깨진다** — `ObjectManager`의 추적 목록이 끊겨 광역 데미지가 `0체`가 되고 카메라 셰이크·피격 연출이 아예 발생하지 않는다(예외도 로그도 없어 "구현이 안 됐다"로 오해). 전투 수치를 측정할 때는 **플레이를 끄고 컴파일 완료를 확인한 뒤 다시 켜서** 측정한다.

## 13. 자산 파이프라인 — 아이콘·이펙트·사운드·마스터 데이터

아트 리소스를 외주·구매 없이 **코드로 생성**했다. 이미지 생성 모델을 쓰지 않고 **Python(PIL/numpy)으로 절차적으로 그리는** 방식을 커스텀 스킬로 고정했다 — 프레임 단위 제어·색상 변경·크기 조정 같은 후속 요청에 즉시 대응할 수 있기 때문이다.

| 자산 | 도구 | 산출 위치 |
|---|---|---|
| 아이템·스킬·UI 아이콘 | `com2us-taskbar-hero-client/.claude/skills/pixel-item-icons`(절차적 픽셀 아트 + 팔레트 레지스트리) | `Assets/Art/Icon/` (아이템 **96종**) |
| 전투·버프·투사체 이펙트 | `com2us-taskbar-hero-client/.claude/skills/unity-pixel-vfx`(프레임 시퀀스 PNG) | `Assets/Art/Effect/{Character,Combat,Object,UI}` |
| BGM·효과음 | `tools/poe-sfx/generate_sound.py`(오디오 생성 API 호출) | `Assets/Sound/` (**67종**, 정의서로 목록·트리거 관리) |
| 마스터 데이터 번들 | `tools/master_data_export.py`(마스터 DB → camelCase JSON) | `Assets/Resources/MasterData/*.json` (**17개**) |
| 몬스터(능력치 + 외형 + 프리팹) | `.claude/skills/master-monster` + `tools/master_monster_tool.py` → [14장](#14-요청-한-줄로-몬스터를-만든다--master-monster-파이프라인) | `Assets/Prefabs/Character/Monster/monster_{code}.prefab` (**12종**) |

아이콘 스킬에는 실수에서 나온 규칙이 들어 있다 — **렌더된 PNG를 눈으로 확인했다고 가정하지 말고 수치 검사로 검증할 것**, **파일명은 한글 아이템명 그대로**(공백을 언더바로 바꾸거나 음역하지 말 것), **유니코드 이스케이프를 기억으로 타이핑하지 말 것**(`강화석`을 `강화 석`으로 잘못 쓰는 사고).

**아이템 추가는 서버·클라를 가로지르는 파이프라인이라 스킬 하나로 묶었다.** 저장소 루트의 `.claude/skills/master-item` 스킬(구현은 `tools/master_item_tool.py`)은 요청 한 번으로 5단계를 처리한다.

```
① 입력 해석(이름·종류·등급 → 코드 자동 채번·등급 파생값)
② 마스터 데이터 추가 — master-data-값.md + master-data-schema.sql 두 정본에 동시 삽입 후 자동 재검증
③ 아이콘 생성 — pixel-item-icons로 '<이름>.png'
④ 이름 연결 — item_{code}.png 로 이동, .meta를 함께 옮겨 GUID 보존(기존 참조 유지)
⑤ 번들 갱신 — 마스터 DB 재적용 + 클라 JSON 재추출
```

이 파이프라인이 있어 "아이템 한 종 추가"가 **문서 2곳·DB·아이콘·번들 5곳을 손대는 작업에서 한 번의 요청**으로 줄었다. 실제로 자동화 검증 커밋(`e0a83c3 아이템 생성 자동화 테스트 완료`)이 남아 있다. 이번 장비 강화 작업에서도 같은 도구 계열을 그대로 썼다 — `enhance_master`를 스키마에 넣고 추출기에 테이블을 추가하자 클라 번들 `enhance_master.json`이 함께 생성됐다.

## 14. 요청 한 줄로 몬스터를 만든다 — master-monster 파이프라인

13장의 자산 파이프라인 중 **가장 많은 경계를 넘는 것이 몬스터**다. 아이콘은 파일 하나로 끝나지만, 몬스터 한 종은 **서버 정본 · 외형 레시피 · Unity 프리팹 · 전투 배선 · 클라 번들**을 모두 맞춰야 게임에 나온다. 그중 절반은 Unity 에디터 조작이라 손으로 하면 순서를 틀리기 쉬웠다. 그래서 `com2us-taskbar-hero-client/.claude/skills/master-monster` 스킬(구현은 `tools/master_monster_tool.py` + `Assets/Editor/MonsterPrefabBuilder.cs`)로 **"입력 한 줄 → 그 몬스터가 실제 전투에 나온다"** 까지를 한 번에 처리한다.

```
① 입력 해석 → ② 능력치·외형 결정 → ③ 정본 + 스폰 반영 → ④ 프리팹 생성 → ⑤ 전투 배선 → ⑥ 번들 재생성 → ⑦ 검증
                    └────────── ③ 도구(CLI) ──────────┘   └── ④⑤ Unity MCP ──┘   └ ⑥ CLI ┘
```

사용자 입력은 `"검은 갑옷의 스켈레톤 기사, 2지역 5스테이지에 4마리"` 정도다. 부족한 값은 **되묻지 않고 규칙으로 채운다** — `monster_code`는 Act 대역에서 자동 채번(보스는 `xx99`), 스테이지 미지정이면 그 Act 중간(5), 마리 수 미지정이면 그 스테이지 총량(일반 8~16마리)을 보고 정한다.

| 단계 | 무엇이 자동인가 | 수단 |
|---|---|---|
| ② 능력치 | 클라이언트 `MonsterStatCurve`와 **같은 산식**으로 Act·스테이지에서 hp·attack 산출(`recommend`) | CLI |
| ② 외형 | SPUM 태그(`--race` + `--classes`)로 파츠를 뽑아 레시피 JSON 생성. Act별 계열 고정(1 빙의된 인간 · 2 언데드 · 3 악마 · 4 타락한 성기사 · 5 공허) | CLI |
| ③ 정본 | `master-data-값.md` §9·§11 · `master-data-schema.sql` · `monster-appearance-recipe.json` · `stage_spawn` **네 곳을 한 명령으로** 갱신 | CLI |
| ④ 프리팹 | 레시피에서 `monster_{code}.prefab` 조립(루트 `SPUM_Prefabs`·`_anim` 배선·상태별 클립 검증까지) | Unity MCP |
| ⑤ 전투 배선 | `DungeonBattleBuilder`로 코드→프리팹 맵 갱신 | Unity MCP |
| ⑥ 번들 | 마스터 DB 재적용 + 클라 JSON 재추출(**전투는 클라 권위**라 이 단계까지 끝나야 게임이 읽는다) | CLI |
| ⑦ 검증 | 정본 ↔ 스키마 불일치·코드 규약·개수 문장·미배치 몬스터 검사(`verify`) | CLI |

### 14.1 자동으로 뽑은 능력치·외형을 눈으로 확정하는 하네스

②는 자동이지만 **뽑힌 외형이 쓸 만한지는 사람이 봐야 한다.** 그 확인을 위한 세 번째 하네스가 `CharacterDevScene`이다(씬 이동 `TaskbarHero/씬/CharacterDevScene`·`Alt+7`, 생성 메뉴 `TaskbarHero/UI/캐릭터 개발 씬(CharacterDevScene) 생성`, 명세는 클라 문서 [`캐릭터-개발씬-기획서.md`](../com2us-taskbar-hero-client/docs/캐릭터-개발씬-기획서.md)).

![CharacterDevScene — 왼쪽 몬스터 목록 · 가운데 외형 프리뷰 · 오른쪽 능력치·외형·산출 패널](images/개발환경-images/몬스터-외형자동결정-결과.png)

- **왼쪽 — 몬스터 목록**: 12종의 코드·이름·hp·atk와 **추천값 대비 편차**를 함께 보여 준다(`9102 스켈레톤 기사 hp 150 (+50%) / atk 16 (+60%)`처럼 손댄 값이 바로 드러난다). 뒤의 `[PR]`은 **P**refab·**R**ecipe 보유 표시로, 없으면 `·`으로 비어 12종이 모두 갖춰졌는지 한눈에 보인다.
- **가운데 — 외형 프리뷰**: 고른 몬스터의 프리팹을 그 자리에 세운다. 위 화면은 `9499 공허의 지배자`(Act5 보스)이고, 뿔 투구(`New_Helmet_04`)와 붉은 망토(`Soon_Back1`)가 태그에서 뽑힌 결과다.
- **오른쪽 위 「능력치」**: Act 1~5 · 스테이지 1~10을 누르고 **[추천값 채우기]** 를 누르면 그 조합의 hp·attack이 채워진다(9499는 `hp 10000 / atk 75`, 추천값과 ±0%). 계열에서 **이름 후보**(임프·데몬·마계 기사·서큐버스·발록)도 제안하고, 코드 채번 상태(`작업 코드 9499 / 제안 코드 9499 (이미 사용 중)`)를 함께 표시해 규약 위반을 미리 막는다.
- **오른쪽 가운데 「외형」**: 레시피 한 줄(`race devil / gender 무제한 / theme fantasy / class magical+tank / seed 94991`)과 **그 시드가 실제로 고른 파트 목록**(`Body Devil_1 · Eye Eye11 · Armor New_Armor_10 · Helmet New_Helmet_04 · Back Soon_Back1` …)이 그대로 나온다. **[외형 재생성]** 은 시드를 옮겨 다시 뽑는 것으로, CLI의 `reskin --reroll`과 같은 동작이다. 헤더의 `파츠 215개 / 패키지 3개`가 이 조합이 고르는 후보 풀이다.
- **오른쪽 아래 「산출」**: **[프리팹 저장]** · **[monster_master 반영]** · **[스니펫 복사 (서버 정본용)]** · **[전투로 검수 (BattleDevScene)]**.

여기서 지킨 경계가 하나 있다. **`[monster_master 반영]`은 클라 번들만 고친다** — 누르면 로그가 "서버 정본 반영은 별도 작업이다 — [스니펫 복사]로 넘길 것"이라고 못 박는다. 씬에서 눈으로 확정한 값을 서버 정본으로 끌어올리는 경로는 CLI의 `adopt-bundle`이고, 이 분리가 있어야 **다음 번들 재추출(⑥)에서 씬에서 한 수정이 덮여 사라지지 않는다**. 씬은 "보고 정하는 곳", 정본은 "남기는 곳"으로 역할을 갈라 둔 것이다.

### 14.2 파이프라인의 산출물

![생성된 몬스터가 실제 전투에 등장한 모습 — 왼쪽 파티와 맞서는 오른쪽 6종이 모두 파이프라인 산출물](images/개발환경-images/몬스터-자동생성-전투.png)

위 화면이 파이프라인의 최종 산출물이다. 오른쪽에 늘어선 스켈레톤 병사·데몬·스켈레톤 기사·공허의 추적자·스켈레톤 군주·타락한 성기사는 **손으로 만든 프리팹이 하나도 없고**, 전부 태그 → 레시피 → 프리팹 → 스폰 테이블을 거쳐 이 전투에 들어왔다. 이름·HP·공격력은 서버 정본에서 추출한 번들에서 읽는다.

![생성된 몬스터 프리팹 12종 — Act1 빙의된 인간부터 Act5 공허까지](images/개발환경-images/몬스터-자동생성-라인업.png)

현재 게임의 몬스터 **12종(일반 7 + Act별 보스 5)** 이 전부 이 파이프라인 산출물이다. 위 줄이 Act1·2 계열(빙의된 인간·스켈레톤), 아래 줄이 Act3~5 계열(악마·타락한 성기사·공허)이며, 계열별 색과 파츠 조합만 태그로 지정하고 나머지는 시드가 고른다.

### 14.3 요청 종류에 따라 흐름을 가른다

전부를 기계적으로 돌리지 않는 것이 이 스킬의 핵심 판단이다. **특히 외형만 바꾸는 요청은 서버 정본·DB·번들을 건드리지 않는다.**

| 사용자가 원하는 것 | 할 일 | 번들 재생성 |
|---|---|---|
| 새 몬스터를 만들어 전투에 등장 | ①~⑦ 전체 | 필요 |
| **외형만 교체**(능력치 유지) | `reskin` → 프리팹 재생성 | **불필요** |
| 마리 수만 조정 | `spawn` → 번들 | 필요 |
| 능력치만 조정 | `add --code` → 번들 | 필요 |

외형 교체가 싼 이유는 **GUID를 유지하기 때문**이다. 기존 프리팹을 `Assets/Dev/MonsterPrefabBackup/`에 백업한 뒤 **같은 경로에 덮어쓰므로** `.meta`의 GUID가 그대로여서, 전투의 코드→프리팹 맵이 계속 유효하다. 그래서 "외형이 마음에 안 든다 → 다시 뽑아 달라"(`reskin --reroll`)를 몇 번 반복해도 DB 재적용도, 씬 수정도 없다.

### 14.4 이 파이프라인에서 얻은 함정 목록

12장의 MCP 함정 목록과 같은 성격으로, 몬스터 생성에서 새로 나온 것들이다.

| 함정 | 우회 |
|---|---|
| MCP 샌드박스가 `PrefabUtility.SaveAsPrefabAsset`을 차단한다 — 커맨드에서 프리팹 생성 함수를 직접 부르면 "User interactions are not supported"로 실패 | **`EditorApplication.ExecuteMenuItem("TaskbarHero/몬스터/...")`** 로 부른다(메뉴 실행은 샌드박스 밖 경로) |
| `EditorApplication.delayCall` 우회는 통하지 않는다 | 에디터가 백그라운드면 틱이 돌지 않고, 동적 커맨드의 람다는 어셈블리가 해제되며 사라진다 — 쓰지 않는다 |
| 대상 코드를 커맨드 인자로 넘길 수 없다(메뉴 실행만 통과) | `EditorPrefs`에 코드를 써 두고 메뉴를 실행한다(키는 실행 시 한 번 쓰고 지워진다) |
| 레시피의 `colors`는 **곱셈 틴트**라 원본보다 밝게 만들 수 없다 | "더 밝게"에 밝은 색을 주면 오히려 어두워진다 — 그 파트의 색 지정을 **빼서** 원본 밝기를 되찾는다 |
| 파트가 담당하는 부위가 직관과 다르다 | `Body`는 **피부(얼굴·손·발)만**이고 몸통은 `Armor`·`Cloth`·`Pant`·`Back`이 덮는다. 뿔·볏은 `Helmet` 파츠에 들어 있다 |
| 파츠 크기는 레시피로 조절할 수 없다 | "더 크게"는 **더 큰 파츠를 고르는 것**으로만 답한다 |

**외형은 결국 눈으로 봐야 하므로 그 확인도 코드로 만들었다.** 프리뷰 씬에 프리팹을 세우고 직교 카메라 → `RenderTexture` → `EncodeToPNG`로 PNG를 남긴 뒤 그 파일을 읽으면, 열려 있는 씬을 건드리지 않고 결과를 확인할 수 있다. 후보를 고를 때는 격자 시트로 한 장에 모아 비교하고, **밝은 배경과 어두운 배경 두 장**을 내어 던전에서 묻히지 않는지 본다(어느 부위가 어느 파트인지 모를 때는 파트별로 원색을 칠해 한 장 렌더하면 즉시 판별된다). 위 라인업 이미지도 같은 방법으로 뽑은 것이다.

### 14.5 남긴 안전장치

- **정본 3파일을 손으로 편집하지 않는다.** 도구만 고치게 해서 값.md·schema.sql·레시피가 갈라지지 않도록 했고, `add`가 끝나면 **자동으로 `verify`** 가 돈다(현재 `12종 — 오류 0 · 경고 0`).
- **`monster_code`를 임의로 지정하지 않는다.** Act 대역·보스 `xx99` 규약이 깨지기 때문에 채번은 도구에 맡긴다.
- **사용자가 스테이지를 말했으면 `--spawn`을 반드시 넣는다.** 빠뜨리면 몬스터를 만들어도 어느 스테이지에도 배치되지 않아 전투에 나오지 않는다 — `verify`가 그 상태를 경고로 잡는다.
- **어시스턴트가 Unity 에디터·MySQL을 대신 띄우지 않는다.** 안 떠 있으면 거기서 멈추고 무엇이 남았는지 보고한다(예: MySQL 미기동으로 ⑥ 미완).

## 15. 클라이언트 쪽에서 얻은 것과 한계

**얻은 것**

- **UI가 코드가 되어 대화로 수정 가능해졌다.** 에디터 빌더 덕분에 "패널을 다시 만들어라"가 실제로 가능한 요청이 됐고, 화면 변경이 diff로 남았다.
- **서버 계약을 복제하지 않아 어긋나지 않았다.** DTO·`ErrorCode`를 공유 라이브러리에서 그대로 쓰므로, 서버가 필드를 늘리면 클라이언트는 컴파일 단계에서 알게 된다.
- **아트·사운드까지 자체 생산했다.** 절차적 생성이라 "조금 더 작게/다른 색으로" 같은 반복 수정이 값싸다.
- **함정 목록이 자산이 됐다.** 도메인 리로드·프리팹 오염·오버레이 캔버스 캡처 같은 문제는 한 번 겪고 규칙으로 적어 두면 다시 시간을 잃지 않는다.

**한계**

- **에디터 상태에 의존하는 부분은 문서로 못 막는다.** Game 뷰의 `Low Resolution Aspect Ratios`처럼 프로젝트 설정이 아닌 **에디터 레이아웃 상태**는 조용히 되돌아와, 결국 에디터 로드마다 교정하는 스크립트(`GameViewResolutionGuard`·`UiTextShaderRegistrar`)를 두어야 했다.
- **시각 품질은 수치로 검증하기 어렵다.** 텍스트 선명도는 렌더 해상도·래스터 픽셀 수를 실측해 두 원인(고DPI 업스케일 · AA 벡터 폰트)을 갈라냈지만([UI 텍스트 선명도](../com2us-taskbar-hero-client/docs/ui/텍스트-선명도.md)), "보기 좋은가"는 결국 사람이 봐야 한다.
- **UI를 코드로 굽는 비용이 크다.** 손으로 3분이면 끝나는 배치도 빌더를 고쳐 다시 실행해야 한다. 대신 재현성을 얻는 거래다.
- **실연동 검증이 사용자 개입에 묶인다.** 세션 권한 분리(9장) 때문에 라이브 검증은 사용자가 서버를 올려 준 시점에만 가능하고, 그때까지 기능은 "배선까지 끝난 상태"로 대기한다.
