## 1. 개발 환경

| 구분 | 내용 |
|---|---|
| 런타임 | .NET 10 · ASP.NET Core Web API |
| 구성 | `AccountServer`(계정·인증, `:5160`) · `GameServer`(게임 로직, `:5247`) · `TaskbarHero.Common`(공유 라이브러리) |
| 공유 라이브러리 | `netstandard2.0;net10.0` 멀티타겟 — 서버는 `ProjectReference`, Unity 클라이언트는 **로컬 UPM 패키지**로 같은 소스를 소비 |
| DB | MySQL 8.4 (Docker Compose) — 게임 DB / 마스터 DB 분리 |
| 캐시·부가 저장소 | Redis (저장소 내 로컬 바이너리로 실행) — **인증 토큰, 배치 리더 락**. 게임 데이터 조회 캐시는 실측 후 전부 제거했다(인벤토리 §6.5 · 거래소 §7.3) |
| 데이터 접근 | **SqlKata** 쿼리 빌더 + Dapper 제네릭 매핑(원시 SQL 조립·`dynamic` 금지) |
| Redis 접근 | **CloudStructures** 타입 구조체 |
| 로깅 | **ZLogger** (구조화 필드, `:@PascalCase` 규약) |
| 개발 도구 | **Claude Code**(CLI) · Swagger UI(`/swagger`, Development 전용) · `.http` 파일로 수동 호출 |
| 문서 | Markdown + Mermaid(ERD·시퀀스 다이어그램) |

솔루션은 `com2us-taskbar-hero.slnx`(XML 형식) 하나로 세 프로젝트를 묶는다.

## 2. 개발 방식 한눈에 보기

**AI 코딩 에이전트에게 코드를 바로 시키지 않고, 항상 문서를 먼저 만들고 그 문서를 근거로 구현을 요청했다.**

```
① 기획서 요청  →  ② 검토·확정  →  ③ 문서대로 구현 요청
                                          ↓
      ⑥ 현황판 갱신  ←  ⑤ 문서 동기화  ←  ④ 빌드 + 실서버 검증
```

핵심은 **"무엇을 만들지"와 "어떻게 만들지"를 분리한 것**이다. 기획서 단계에서 API 스키마·DB 구조·에러 코드·예외 처리를 먼저 확정하고, 구현 단계에서는 그 문서를 그대로 지시서로 썼다. 덕분에 구현 중에 설계를 즉흥적으로 바꾸는 일이 줄었고, 나중에 "왜 이렇게 했더라"를 코드가 아니라 문서에서 확인할 수 있었다.

## 3. 개발 루프 — 문서 → 구현 → 검증 → 동기화

### 3.1 ① 기획서부터 요청한다

새 기능은 코드가 아니라 **기획서 작성 요청**으로 시작했다. 이를 위해 `.claude/skills/design-doc` 커스텀 스킬을 두어, 요청만 하면 항상 같은 위치·같은 템플릿으로 문서가 나오게 했다.

- 위치: `docs/세부/<기능명>-기획서.md`
- 고정 목차: **개요 · 기능 설명 · 요구사항 · 데이터 모델 · API 명세 · 처리 흐름 · 에러 코드 · 미결 사항 · 참고**
- 작성 시 기존 `CLAUDE.md`·`ErrorCode.cs`·기존 문서를 먼저 읽어 **계약 충돌이 없는지 확인**하도록 절차에 못 박음

가장 중요하게 지킨 것은 **"확정"과 "그렇게 정한 이유"를 함께 남기는 것**이다. 예를 들어 거래소 기획서에는 "구매 직렬화는 MySQL 조건부 갱신으로만 하고 Redis 락을 두지 않는다(확정)"와 그 근거(락을 얹으면 TTL 만료·해제 실패·Redis 장애라는 실패 경계만 늘어난다)가 함께 적혀 있다. 이 기록이 있어야 몇 주 뒤에 같은 논쟁을 반복하지 않는다.

### 3.2 ② 검토·확정

작성된 기획서를 읽고 **미결 사항과 판단이 갈리는 지점만 짚어 되물었다.** 이 단계에서 스키마·정책이 여러 번 바뀌었고, 바뀔 때마다 문서를 고쳐 확정안만 남겼다(변경 이력은 문서에 남기지 않고 최종 상태만 유지).

### 3.3 ③ 문서대로 구현을 요청한다

구현 요청은 **"기획서 5.2를 구현해줘"** 같은 형태였다. 자유도를 좁히기 위해 프로젝트 공통 규칙을 `CLAUDE.md`에 미리 고정해 두었다.

- 컨트롤러에는 **HTTP 액션 메서드만** 두고, 공통 보조는 `GameApiControllerBase`에 상속으로
- 서비스 클래스의 **모든 메서드에 `/// <summary>` 주석** 필수
- DB 결과는 `dynamic` 금지 — POCO/스칼라 **제네릭 매핑**만
- 재화·아이템 변경은 **단일 트랜잭션**, 서버 권위(클라이언트 보고 불신)
- 로깅은 서비스 계층에서 ZLogger 확장 메서드로, 사용자 실수는 로깅하지 않음

### 3.4 ④ 빌드 + 실서버 검증

구현 후에는 반드시 **빌드와 실제 동작 검증**을 거쳐야 완료로 인정했다.

```
기존 서버 강제 종료 → dotnet build → 포어그라운드 기동 → 헬스 체크 → 시나리오 → 강제 종료·잔여 0 확인
```

- 서버는 **반드시 보이는 콘솔 창**으로 띄운다. 숨김·백그라운드 기동을 금지한 이유는, 남은 프로세스가 `bin/` 파일을 잠그거나(MSB3021) **다음 테스트가 옛 바이너리를 검증**하게 만들기 때문이다.
- 검증은 실제 MySQL·Redis에 붙여 API를 호출하고, 결과를 **DB에서 직접 대조**했다. 테스트로 만든 데이터는 되돌렸다.

### 3.5 ⑤ 문서 동기화 — 이 프로세스의 핵심

기능을 바꾸면 **같은 작업 안에서** 관련 문서를 전부 갱신하도록 규칙을 두었다. 세부 기획서가 정본이고, 아래 셋은 기획서를 가로질러 모은 **집약 참조본**이라 하나만 바뀌면 곧 불일치가 된다.

| 무엇이 바뀌면 | 갱신할 문서 |
|---|---|
| 엔드포인트·요청/응답 필드 | `docs/공통/api-통합.md` |
| DB 테이블·컬럼·마스터 데이터 | `docs/공통/db-erd-통합.md` (+ `db-schema.sql`) |
| 에러 코드 추가·폐기 | `docs/공통/error-code-정의.md` + `TaskbarHero.Common/ErrorCode.cs` |
| 처리 흐름 | `SequenceDiagram/README.md` (기능별 Mermaid 시퀀스) |

정합성 체크는 **양방향**으로 했다 — 기획서 → 통합 문서(빠진 항목 추가)와 통합 문서 → 기획서(폐기된 항목이 남아 있지 않은지). 경로나 이름을 바꿨으면 옛 문자열이 문서 어디에도 남지 않았는지 `grep`으로 확인했다.

### 3.6 ⑥ 현황판 갱신

기능이 끝나면 `README.md`의 개발 현황 체크리스트를 갱신했다(☐ 미착수 → ◐ 진행 중 → ☑ 완료). **서버 구현과 클라이언트 실연동을 각각 표시**해, 어느 쪽이 밀렸는지 한눈에 보이게 했다.

## 5. 규칙의 축적 — CLAUDE.md

같은 실수가 반복될 때마다 **그 교훈을 `CLAUDE.md`에 규칙으로 적어 고정**했다. 이 파일은 매 작업 시작 시 자동으로 읽히므로, 한 번 적은 규칙은 이후 모든 작업에 적용된다.

실제로 쌓인 규칙의 예:

| 규칙 | 생긴 이유 |
|---|---|
| 서버는 포어그라운드로만 기동, 테스트 후 강제 종료 | 숨겨진 서버가 남아 옛 바이너리를 검증하는 사고 |
| DB 조회 결과에 `dynamic` 금지 | 컴파일 타임 타입 검사 상실 + 튜플/변환 런타임 오류 |
| JSON 문자열 컬럼 금지, 반복 구조는 자식 테이블로 | 스키마 확장 시 마이그레이션 지옥 |
| 기능 구현 시 통합 문서 동기화 + 정합성 체크 | 문서 간 불일치가 반복적으로 발생 |
| 서비스 메서드 전체에 요약 주석 필수 | 나중에 읽을 때 의도 파악 비용 |

즉 `CLAUDE.md`는 프로젝트 규약이자, **작업 방식 자체를 코드처럼 버전 관리한 결과물**이다.

## 6. 실제 진행 사례

**(1) 문서 → 구현 (전형적인 흐름)**

```
2026-07-30  ffb483e  소모품(골드, 경험치 부스터) 기획서 작성   ← 기획서 + README 현황판만
2026-07-30  4fcd462  소모품 사용기능 추가                      ← 컨트롤러·서비스·리포지토리 구현
```

기획서 커밋에는 문서만 들어 있고, 구현 커밋에는 코드만 들어 있다. 기획서가 곧 구현 지시서 역할을 했다.

**(2) 구현과 설계 문서를 같은 작업 단위로**

가챠는 구현(`6cb7260`)과 설계 문서(`2de13e1`)를 **37초 간격으로 연속 커밋**했다. 커밋은 나뉘었지만 같은 작업에서 코드와 문서를 함께 맞춘 사례이고, 이때 `api-통합`·`db-erd-통합`·`db-schema.sql`·`error-code-정의`가 한 번에 동기화됐다.

**(3) 문서가 있어 되돌릴 수 있었던 사례 — 인벤토리 캐시**

```
2026-07-31  e05f4d4  인벤토리 아이템 조회에 대한 캐싱 기능 추가
2026-07-31  98e30fd  인벤토리 데이터 캐싱 기능 추가
2026-08-04  666411b  유저 인벤토리 캐싱기능 제거
```

가방 조회에 Redis write-through 캐시를 넣었다가, 나중에 **성능·정합성 관점에서 재검토해 제거**했다(개인 데이터라 공유 이득이 없고, 쓰기마다 가방 전량을 다시 쓰는 증폭이 컸다). 이때 기획서에 도입 근거가 남아 있었기에 **무엇을 전제로 넣었고 그 전제가 왜 깨졌는지**를 대조할 수 있었고, 제거와 함께 그 판단을 다시 문서에 기록했다. 거래소의 Redis 락도 같은 방식으로 재검토해 제거했다.

## 7. 이 방식의 효과와 한계

**효과**

- **재작업이 줄었다.** API 스키마·에러 코드를 문서에서 먼저 확정하니, 구현 후 계약이 바뀌어 클라이언트까지 고치는 일이 적었다.
- **판단 근거가 남는다.** "왜 락을 안 쓰는가", "왜 캐시를 뺐는가"가 문서에 있어 나중에 다시 논쟁하거나 잘못 되돌리는 일을 막았다.
- **AI 에이전트의 출력 품질이 안정됐다.** 자유롭게 시키면 매번 다른 구조가 나오지만, 기획서 + `CLAUDE.md` 규칙을 근거로 시키면 결과가 일정하다.
- **클라이언트 병행 개발이 가능했다.** 계약(요청/응답·에러 코드)이 먼저 확정되므로 클라이언트가 목(mock)으로 먼저 붙일 수 있었다.

**한계**

- **문서 유지 비용이 크다.** 기능 하나를 바꾸면 최대 5개 문서(세부 기획서 · api-통합 · db-erd-통합 · error-code-정의 · 시퀀스 다이어그램)를 함께 손대야 한다.
- **집약 문서는 항상 불일치 위험을 안는다.** 그래서 "같은 작업에서 갱신 + 양방향 정합성 체크"를 규칙으로 강제해야 했다.
- **작은 수정에는 과하다.** 버그 픽스·UI 조정처럼 계약이 바뀌지 않는 작업은 이 루프를 타지 않고 바로 수정했다.
