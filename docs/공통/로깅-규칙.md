# 서버 로깅 규칙

> 상위 문서: [서버 시스템 전체 개요](../서버-시스템-전체-개요.md)
>
> 두 서버(`AccountServer`·`GameServer`)에 로그를 추가하기 전에 **일관된 로깅 방식**을 정하기 위한 규약 문서다. 이 문서는 **어떻게** 쓰는지를 다루고, **어떤 사건을 어떤 필드로 남길지**는 [로그 이벤트 정의](로그-이벤트-정의.md)가 정한다(집계용 게임 이벤트 로그). 로그의 목적은 ① 운영 중 문제 추적(무엇이/언제/누구에게 실패했는가), ② 비즈니스 이벤트 감사(로그인·재화 변동 등), ③ 개발 중 디버깅이다. 아래 규칙은 이 세 목적을 만족하되 과잉 로깅(노이즈)과 민감정보 노출을 막는 것을 원칙으로 한다.

## 1. 로깅 스택

- **인터페이스는 `Microsoft.Extensions.Logging`의 `ILogger<T>`, 구현은 [ZLogger](https://github.com/Cysharp/ZLogger)를 사용한다.** 주입 타입은 표준 `ILogger<T>` 그대로이고, 기록할 때 ZLogger 확장 메서드(`ZLogInformation` 등)를 쓴다.
- 프로바이더는 두 서버 `Program.cs`에서 **기본 Console을 제거하고 ZLogger 콘솔만 등록**한다(출력 형식 단일화).

```csharp
builder.Logging.ClearProviders();
builder.Logging.AddZLoggerConsole(options =>
{
    options.UsePlainTextFormatter(formatter =>
    {
        formatter.SetPrefixFormatter(
            $"[{0:yyyy-MM-dd HH:mm:ss.fff}] [{1:short}] [{2}] ",
            (in MessageTemplate template, in LogInfo info) =>
                template.Format(info.Timestamp.Local.DateTime, info.LogLevel, info.Category));
        formatter.SetExceptionFormatter((writer, ex) => Utf8String.Format(
            writer,
            $"{Environment.NewLine}{ex.GetType().Name}: {ex.Message}{Environment.NewLine}{ex.StackTrace ?? string.Empty}"));
    });
});
```

- 출력 형식은 `[시각] [레벨] [카테고리] 메시지`이며, 예외는 다음 줄에 타입·메시지·스택을 붙인다.
- ZLogger를 쓰는 이유: 보간 문자열 핸들러 + UTF8 직접 기록으로 **문자열 할당 없이** 기록하고(레벨이 꺼지면 값 포매팅도 하지 않는다), 백그라운드 스레드로 비동기 기록해 요청 경로를 막지 않는다. 구조화 필드도 그대로 보존된다.
- 파일·롤링 파일 sink(`AddZLoggerFile`·`AddZLoggerRollingFile`)와 JSON 포매터(`UseJsonFormatter`)는 같은 패키지에 있으므로, 필요해지면 프로바이더 등록만 바꾼다(호출부는 그대로).
- 로거는 **생성자 주입**으로만 얻는다(`ILogger<MyService> logger`). `LoggerFactory`를 직접 만들거나 정적 로거를 두지 않는다.
- 카테고리는 제네릭 타입 인자(`ILogger<StageService>`)로 자동 지정되게 둔다. 문자열 카테고리를 수동 지정하지 않는다.
- 레벨 필터는 `appsettings.json`의 `Logging:LogLevel`로 제어한다. 코드에서 레벨을 하드코딩하지 않는다.
  - 운영/기본: `Default = Information`, `Microsoft.AspNetCore = Warning` (현행 유지).
  - 개발(`appsettings.Development.json`): 필요 시 자기 네임스페이스만 `Debug`로 내린다(예: `"TaskbarHero": "Debug"`, `"AccountServer": "Debug"`, `"GameServer": "Debug"`).

## 2. 로그 레벨 사용 기준

| 레벨 | 언제 쓰는가 | 예시 |
|---|---|---|
| `Trace` | 원칙적으로 사용 안 함. 극한 디버깅 시 임시로만. | — |
| `Debug` | 개발 중에만 의미 있는 흐름 추적. 운영에서 꺼진다. | "스테이지 진입 검증 통과: stageId {StageId}" |
| `Information` | 정상적인 **주요 비즈니스 이벤트**. 성공 경로의 이정표. | 로그인 성공, 캐릭터 생성, 스테이지 클리어, 마스터 데이터 적재 완료 |
| `Warning` | 처리는 됐지만 **비정상/주의가 필요한 상황**. 예상 가능한 실패 중 추적 가치가 있는 것, 경합(race) 감지, 재시도. | 이메일 중복 경합, 계정 초기화 경합, 잘못된 요청이 반복되는 패턴 |
| `Error` | **해당 요청이 실패**했고 코드/데이터에 문제가 있음. 예외 또는 "있어서는 안 될" 상태. | 마스터 데이터 누락(`stage_reward` 없음), DB 예외, 미처리 예외 |
| `Critical` | 서버 전체가 정상 동작 불가. 기동 실패, 필수 리소스 부재. | DB/Redis 연결 불가로 기동 중단, 필수 마스터 데이터 적재 실패 |

**핵심 판단 기준**
- "정상 흐름의 이정표"는 `Information`, "사용자 입력 실수"는 로깅하지 않거나 `Debug`, "서버가 예상하지 못한 상태"는 `Warning`/`Error`.
- 성공 경로 로그는 **엔드포인트당 1줄** 수준으로 억제한다(반복·루프 내부 로깅 금지).

## 3. 구조화 로깅(ZLogger 보간)

- **`ZLog*` 확장 메서드 + 보간 문자열을 쓴다.** 값마다 `:@이름`으로 구조화 필드 이름을 지정한다.
  - ✅ `logger.ZLogInformation($"로그인 성공: userId {userId:@UserId}");`
  - ❌ `logger.LogInformation("로그인 성공: userId {UserId}", userId);` — 표준 API 직접 호출 금지(형식·성능 경로가 갈린다)
  - ❌ `logger.ZLogInformation($"로그인 성공: userId " + userId);` — 문자열 `+` 연결 금지(구조가 사라진다)
- 여기서 쓰는 `$"..."`는 **일반 문자열 보간이 아니라 ZLogger의 보간 문자열 핸들러**다. 컴파일 시 값이 분리 캡처되므로 구조화 필드가 유지되고, 레벨이 꺼지면 값 포매팅조차 실행되지 않는다.
- **필드 이름은 `:@` 뒤에 PascalCase 영문**으로 쓴다(`{userId:@UserId}`, `{stageId:@StageId}`). 생략하면 표현식 텍스트(`userId`)가 키가 되므로, 검색·집계 키를 일정하게 유지하기 위해 항상 명시한다.
- 예외는 첫 인자로 넘긴다: `logger.ZLogError(ex, $"...")`.
- 핫패스에서 비싼 인자를 만들 때는 `if (logger.IsEnabled(LogLevel.Debug))`로 가드한다(ZLogger가 포매팅은 건너뛰지만, 인자를 만드는 계산 자체는 호출 전에 일어난다).

## 4. 계층별 로깅 책임

로그 중복(같은 사건을 여러 층에서 반복 기록)을 막기 위해 **층마다 역할을 고정**한다.

- **미들웨어 / 파이프라인** (`GameAuthMiddleware` 등)
  - 인증 실패(`InvalidToken`/`ExpiredToken`)를 `Warning`으로 1줄 기록(userId 알 수 있으면 포함).
  - **접근 로그(확정)**: 전역 미들웨어로 요청 1줄(메서드·경로·상태코드·소요시간)을 `Information`으로 남긴다. 프로덕션에서 과하면 레벨/범위를 조정한다.
- **컨트롤러**
  - **로깅하지 않는다.** (CLAUDE.md 규칙상 컨트롤러는 HTTP 응답 메서드만 포함하므로, 로거 주입·호출을 두지 않는다.) 요청 단위 로그는 미들웨어가, 도메인 로그는 서비스가 담당한다.
- **서비스(`*Service`)** — **로깅의 주 무대.**
  - 주요 비즈니스 이벤트 성공을 `Information`으로.
  - 예상 밖 상태/경합을 `Warning`, 실패·불변식 위반을 `Error`로.
  - `ErrorCode`를 반환하기 직전, "예상외 실패"에 한해 로그를 남긴다([5장](#5-errorcode와-로깅) 기준).
- **리포지토리(`*Repository`) / DbFactory**
  - **원칙적으로 로깅하지 않는다.** DB 예외는 삼키지 말고 상위(서비스/전역 핸들러)로 전파해 거기서 로깅한다.
  - 단, 상위에서 복구·재해석되는 예외(예: 중복키 1062 → `DuplicateEmail`)는 잡은 **서비스**에서 로깅한다(현행 `AuthService`처럼).

## 5. ErrorCode와 로깅

이 프로젝트는 예외 대신 `ErrorCode`를 담은 결과 구조체(`SaveResult`/`SignupResult`/`LoginResult`)를 반환한다. **모든 실패 ErrorCode를 로깅하지 않는다** — 사용자 실수까지 Error로 남기면 노이즈가 된다. 분류 기준:

- **사용자 입력/정상적 거부** (예: `WrongPassword`, `EmailNotFound`, 잘못된 요청 값, 재화 부족) → **로깅 안 함**(또는 개발 중 `Debug`). 정상적인 비즈니스 흐름이다.
- **경합/드묾** (예: `DuplicateEmail` 경합, 초기화 경합) → **`Warning`**.
- **서버 결함/데이터 부정합** (예: 마스터 데이터 누락, 있어서는 안 될 상태, 저장 실패) → **`Error`**.

로그를 남길 때는 **ErrorCode 값과 맥락(userId 등)을 구조화 필드로** 포함한다:
`logger.LogError("스테이지 보상 정의 누락: stageId {StageId}, errorCode {ErrorCode}", stageId, (int)ErrorCode.StageRewardMissing);`

## 6. 예외 로깅

- 예외를 로깅할 때는 **예외 객체를 첫 인자로 전달**한다: `logger.ZLogError(ex, $"마스터 데이터 적재 실패: {table:@Table}");` (`ex.ToString()`을 메시지에 문자열로 넣지 않는다 — 스택트레이스 구조가 깨진다.)
- **`catch (Exception)`로 삼키고 로깅만 하는 것을 금지.** 복구하지 못할 예외는 상위로 전파한다.
- **전역 예외 처리기 도입(확정)**: 각 서버에 미들웨어(또는 `IExceptionHandler`)를 두어 미처리 예외를 `Error`로 1회 로깅하고, 클라이언트에는 일반화된 `ErrorCode`(내부 정보 미노출) JSON을 응답한다.
- 같은 예외를 **한 번만** 로깅한다(잡은 곳에서 로깅했으면 다시 throw해서 상위에서 또 로깅하지 않는다).

## 7. 민감정보 / 금지 사항

- **절대 로깅 금지**: 비밀번호(평문·해시 모두), 인증 토큰/세션 키, BCrypt 해시, Redis 키의 토큰 값, 커넥션 문자열, 개인정보 원문.
- 이메일 등 식별자는 **필요할 때만** 남기고, 가능하면 `userId`로 대체한다(이메일은 PII). 부득이 남기면 그 사실을 인지하고 최소화한다.
- 요청 본문(request body) 전체를 통째로 로깅하지 않는다(비밀번호·토큰 포함 위험).
- 프로덕션에서 `Debug`/`Trace`를 켜 두지 않는다.

## 8. 상관관계(누구의 요청인가)

- 인증된 요청은 **`userId`를 로그에 포함**해 추적 가능하게 한다.
- 한 요청 처리 중 여러 로그에 공통 맥락을 붙이려면 `logger.BeginScope(...)`로 스코프(`userId`, 필요 시 요청 ID)를 걸어 하위 로그가 자동 상속하게 한다. 스코프는 반드시 `using`으로 해제한다.
- *(선택) 요청 ID/Trace ID를 응답 헤더 또는 로그 필드로 노출할지는 결정 ②와 함께 정한다.*

## 9. 메시지 작성 스타일

- 메시지 본문은 **한글**로 쓴다(기존 코드 관례 및 프로젝트 언어 규칙과 일치). 구조화 필드 이름(`:@` 뒤)만 영문 PascalCase.
- 형식: `"<무슨 일>: <키> {Field}, <키2> {Field2}"` — 사건을 앞에, 맥락을 뒤에.
  - 예: `"로그인 성공: userId {UserId}"`, `"인벤토리 확장 실패: userId {UserId}, errorCode {ErrorCode}"`
- 마침표·감탄사·이모지를 쓰지 않는다. 한 줄, 한 사건.
- 로그 메시지에 개행/거대한 객체 덤프를 넣지 않는다.

## 10. 체크리스트

로그를 추가할 때 매번 확인:

- [ ] 레벨이 [2장](#2-로그-레벨-사용-기준)·[5장](#5-errorcode와-로깅) 기준에 맞는가? (사용자 실수를 Error로 남기지 않았는가)
- [ ] `ZLog*` 확장 메서드를 썼고, 값마다 `:@PascalCase`로 필드 이름을 지정했는가?
- [ ] 컨트롤러에 로깅을 넣지 않았는가? (서비스/미들웨어로)
- [ ] 같은 사건을 여러 층에서 중복 로깅하지 않았는가?
- [ ] 비밀번호/토큰/PII를 남기지 않았는가?
- [ ] 예외는 `ZLogError(ex, $"...")`처럼 `ex`를 첫 인자로 전달했는가?
- [ ] 추적을 위해 `userId` 등 맥락을 포함했는가?

## 확정된 결정

검토를 거쳐 아래와 같이 확정했다.

1. **로깅 스택**: 기본 `Microsoft.Extensions.Logging`(Console) 유지. Serilog/파일 sink는 초기 단계에서 도입하지 않고 필요 시 나중에 전환.
2. **요청/응답 접근 로그**: 전역 미들웨어로 요청 1줄(메서드·경로·상태코드·소요시간)을 `Information`으로 도입.
3. **전역 예외 처리기**: 미처리 예외를 한곳에서 `Error` 1회 로깅하고 일반화된 `ErrorCode` 응답으로 반환하는 미들웨어/`IExceptionHandler` 도입.
