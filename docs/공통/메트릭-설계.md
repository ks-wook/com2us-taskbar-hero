# Prometheus 메트릭 설계 — 어디에 무엇을 계측할까

이 서버(AccountServer · GameServer)에 **어떤 지표를 어느 코드 지점에 심을지** 정리한 문서다.
컨테이너 구성과 Grafana 연동 절차는 `docs/모니터링-그라파나-연동.md`(로컬 전용 메모)에 있다.

---

## 1. 현재 상태와 전제

- 두 서버 모두 `/metrics` 엔드포인트가 **없다**. 계측 코드도 0이다.
- `docker/prometheus/prometheus.yml`에 `account-server`(5160) · `game-server`(5247) 잡은 이미 등록되어 있어,
  서버가 `/metrics`를 노출하면 추가 설정 없이 수집이 시작된다.
- 관측 수단 중 **로그는 이미 있다**(`RequestLoggingMiddleware`의 요청 1줄 로그, `docs/공통/로깅-규칙.md`).
  따라서 지표는 로그를 대체하려고 넣는 게 아니라, **로그로 답하기 비싼 질문**만 맡는다.

| 질문 | 답할 수단 |
|---|---|
| "이 요청 하나가 왜 실패했나" | **로그** (userId·경로·에러코드) |
| "지금 전체가 느린가, 특정 API만 느린가" | **지표** |
| "5분 전보다 실패가 늘었나" | **지표** |
| "어제 골드가 얼마나 발행됐나" | **DB 집계** (지표는 실시간 이상 감지용 보조) |

> **원칙**: 지표는 *집계된 추세*만 담는다. 개별 사건의 세부(userId·아이템 ID·메시지)는 로그의 몫이다.
> 이 경계를 어기는 순간 카디널리티가 폭발한다(§7).

---

## 2. 계측 방식 선택 — OpenTelemetry + `System.Diagnostics.Metrics`

두 후보가 있고, **OpenTelemetry**를 권한다.

| | OpenTelemetry (`Meter` / `IMeterFactory`) | prometheus-net (`Metrics.CreateCounter`) |
|---|---|---|
| 커스텀 계측 API | .NET 런타임 표준 `System.Diagnostics.Metrics` | prometheus-net 전용 API |
| 런타임·ASP.NET Core 내장 지표 | **그대로 수집됨**(같은 Meter 체계) | 별도 수집기 필요 |
| 백엔드 교체 | Prometheus → OTLP·기타로 설정만 변경 | Prometheus에 고정 |
| 설정량 | 조금 많다 | 두 줄이면 끝 |

.NET 8 이후 ASP.NET Core·런타임·`MySqlConnector`가 모두 `Meter`로 지표를 내보내므로, **같은 체계로 커스텀
지표를 쓰는 쪽**이 이득이 크다. 계측 코드가 특정 exporter에 묶이지 않는 것도 중요하다 — 나중에 Prometheus를
걷어내도 `Meter` 호출부는 손대지 않는다.

`IMeterFactory`를 DI로 받아 도메인별 지표 클래스를 하나 두는 형태를 기본으로 한다(§8 스케치).

## 3. 계층 0 — 코드를 안 써도 얻는 지표

가장 먼저 켜야 할 것들이다. **계측 코드 0줄**로 아래가 다 들어온다.

| Meter | 대표 지표 | 이 프로젝트에서 답해주는 것 |
|---|---|---|
| `Microsoft.AspNetCore.Hosting` | `http.server.request.duration` (히스토그램)<br>`http.server.active_requests` | 라우트별 처리량·지연 분포·상태코드. **RED 지표의 전부** |
| `Microsoft.AspNetCore.Server.Kestrel` | `kestrel.active_connections`<br>`kestrel.queued_connections`<br>`kestrel.connection.duration` | 커넥션 적체 — 방치형 클라가 폴링을 늘렸을 때 먼저 튀는 곳 |
| `Microsoft.AspNetCore.Diagnostics` | 미처리 예외 수 | `GlobalExceptionHandler`가 잡은 500의 추세 |
| `Microsoft.AspNetCore.Routing` | 라우트 매칭 실패 수 | 클라 배포 실수로 옛 경로를 때리는 상황 |
| `System.Runtime` | `dotnet.gc.*`, `dotnet.thread_pool.*`, `dotnet.process.cpu.*`, `dotnet.process.memory.working_set` | GC 압박·스레드풀 고갈. **`MasterDbProvider`가 마스터 전체를 인메모리로 들고 있어** 메모리 추세는 볼 값어치가 있다 |
| `MySqlConnector` (2.6.1) | `db.client.connections.*` (사용 중/유휴/대기 시간) | **커넥션 풀 고갈**. 리포지토리 27곳이 `BeginTransactionAsync`로 커넥션을 잡으므로 이 지표가 1차 병목 신호다 |

> 지표 이름은 .NET 버전마다 정규화가 있었다(`http_server_request_duration_seconds` 등으로 Prometheus에서는
> 단위 접미사가 붙는다). **정확한 이름은 Grafana Explore의 자동완성으로 확인**하고, 문서의 이름을 그대로 믿지 않는다.

**Redis(CloudStructures / StackExchange.Redis)는 여기에 없다.** StackExchange.Redis는 지표 Meter를 내보내지
않으므로(추적 계측만 존재), Redis 왕복은 §4의 커스텀 계측으로 직접 재야 한다. GameServer는 **모든 게임 요청이
인증 미들웨어에서 Redis를 1회 왕복**하므로 이건 선택이 아니라 필수다.

## 4. 계층 1 — 직접 심을 지표 (서버 상태 관측)

여기가 이 문서의 본론이다. 위치는 실제 파일 기준이다.

### 4.1 최우선: `ErrorCode` 단일 집계 지점

**위치**: `GameServer/Controllers/GameApiControllerBase.cs` → `ApiResult(...)`
(`AccountServer/Controllers/AccountApiControllerBase.cs`도 같은 방식)

```
game.api.result.total   Counter<long>
  labels: route(=엔드포인트 경로), error_code(=ErrorCode 이름), outcome(success|fail)
```

**왜 여기가 최고의 지점인가**: 이 프로젝트는 도메인 실패를 HTTP 상태코드가 아니라 **`ErrorCode` 59종**으로
표현하고, 그 변환이 `ApiResult` **한 곳**을 지난다. 즉 한 군데만 계측하면 전 도메인의 실패 사유 분포가 잡힌다.
게다가 `HttpStatus()` 매핑 때문에 상태코드만 보면 진실이 가려진다 — `NoOfflineReward`는 200이고,
`InsufficientCurrency`·`InventoryFull`·`StageLocked`는 전부 400으로 뭉쳐진다. 내장 HTTP 지표로는 구분이 불가능하다.

이 하나로 답이 나오는 질문:
- 클라 배포 후 `InvalidRequest`가 급증했나 (계약 불일치)
- `InventoryFull`·`InsufficientCurrency` 비율 (밸런스가 조이는 지점)
- `MasterDataNotLoaded`(503)가 나오나 (마스터 적재 실패)
- 409 계열(`MailAlreadyClaimed`·`AttendanceAlreadyClaimed`·`OfflineRewardAlreadyClaimed`·`TradeAlreadyClosed`)
  → **동시 요청 경합의 실제 발생량**. 지금은 Warning 로그를 눈으로 세야 안다

카디널리티: 이론상 59 × 38 라우트(`[Http*]` 액션 38개)지만 실제 조합은 희소하다(라우트마다 나올 수 있는 코드는 3~8종).
실측 후 200 계열을 넘어가면 `error_code`만 남기고 `route`를 빼는 쪽으로 줄인다.

### 4.2 인증 (GameServer 전 요청의 관문)

**위치**: `GameServer/Auth/GameAuthMiddleware.cs`(실패 분기 3개) · `GameServer/Auth/AuthTokenReader.cs`(`RedisAuthTokenReader` — Redis 왕복 지점)

```
game.auth.failure.total       Counter<long>   labels: reason(parse_failed|token_missing|token_mismatch)
game.auth.token_lookup.duration  Histogram<double>  (초)   labels: result(hit|miss|error)
```

- `reason`별 분리가 중요하다. `parse_failed`는 **클라 요청 형식 문제**, `token_missing`은 **정상적인 토큰 만료**,
  `token_mismatch`는 **중복 로그인 또는 위조 시도**다. 성격이 완전히 다른데 지금은 셋 다 401·Warning으로 섞여 있다.
- 토큰 조회 지연은 **Redis 왕복 지연의 대표값**이다. 모든 게임 API가 이 경로를 타므로, 여기가 느려지면 전 API가
  같이 느려진다. `http.server.request.duration`이 전반적으로 들렸을 때 "Redis인가 MySQL인가"를 이 지표로 가른다.

`AccountServer` 쪽 대응 지점은 `AuthService`(로그인·검증)와 `RedisAuthTokenCache`다.

```
account.auth.attempt.total    Counter<long>   labels: operation(signup|login|logout|validate), result(success|fail), reason
account.token.cache.duration  Histogram<double>  labels: operation(set|get|delete), result
```

로그인 실패 `reason`(존재하지 않는 이메일 / 비밀번호 불일치)은 **집계값만** 담는다. 이메일·userId는 절대 라벨에
넣지 않는다(§7). 비밀번호 검증은 BCrypt라 CPU를 쓰므로, `login` 지연 히스토그램은 CPU 포화 감지에도 쓰인다.

### 4.3 DB 트랜잭션

**위치**: 리포지토리 27개 트랜잭션 지점. 개별 계측은 현실적이지 않으니 **공통 헬퍼로 감싸는 형태**를 권한다.

```
game.db.transaction.duration  Histogram<double>  (초)  labels: operation(=논리 작업명), result(commit|rollback|error)
```

`operation`은 `"trade.buy"`, `"cube.combine"`, `"mail.claim_all"` 처럼 **고정 문자열 집합**으로 준다(SQL 문장이나
테이블명을 동적으로 넣지 않는다). 알고 싶은 것:

- **어느 도메인 트랜잭션이 오래 잡고 있나** — 거래소 구매·취소는 MySQL 행 잠금으로 직렬화하므로(기획서 7.3·7.4)
  경합이 생기면 여기서 먼저 드러난다.
- **rollback 비율** — `GachaService`의 후보 풀 부재 전체 롤백, `TradeService`의 이미 닫힌 등록 등.
- `mail/claim-all`·`inventory/list` 같은 다건 처리의 지연 꼬리(p99).

`db.client.connections.*`(계층 0)와 함께 보면 "커넥션이 부족한가, 트랜잭션이 긴가"가 갈린다.

### 4.4 주기 배치

**위치**: `GameServer/Batch/PeriodicBatchService.cs` (골격에 넣으면 파생 배치 2종이 자동으로 계측된다)

```
game.batch.cycle.total        Counter<long>      labels: batch(trade-expire|mail-gc), result(ok|error)
game.batch.cycle.duration     Histogram<double>  labels: batch
game.batch.lock.total         Counter<long>      labels: batch, state(acquired|skip|no_redis)
game.batch.processed.total     Counter<long>     labels: batch          # 1주기 처리 건수
game.batch.last_success_epoch  Gauge<long>       labels: batch          # 마지막 성공 시각(Unix초)
```

배치는 **아무도 안 보고 있어도 조용히 죽는** 종류의 코드다. 게다가 이 골격은 1주기 실패를 Error 로그만 남기고
루프를 유지하도록 설계되어 있어(의도된 동작), **실패가 계속돼도 서버는 정상으로 보인다.** 지표가 특히 필요한 곳이다.

- `last_success_epoch` → `time() - game_batch_last_success_epoch > 7200` 로 **"1시간 주기 배치가 2시간 넘게
  성공하지 못했다"** 를 경보로 잡는다. 지표 중에 유일하게 이런 형태의 gauge가 필요하다.
- `lock.state` 분포는 강제 종료 후 남은 리더 락(TTL 최대 5분) 때문에 스킵된 주기를 드러낸다 — CLAUDE.md가
  경고하는 그 상황이 실제로 몇 번 일어났는지 세어준다.
- `no_redis`는 **축소 운전 진입**(락 없이 진행) 신호다. 0이 아니면 Redis를 봐야 한다.

### 4.5 마스터 데이터

**위치**: `GameServer/Repositories/MasterDb/MasterDbProvider.cs`(조회) · `MasterDbLoader.cs`(적재)

```
game.masterdata.loaded          Gauge<int>     # 1=적재됨, 0=실패(IsLoaded)
game.masterdata.load.duration   Histogram      # 기동 시 1회
game.masterdata.entries         Gauge<long>    labels: table(stage|item|skill|gacha|...)
game.masterdata.defect.total    Counter<long>  labels: kind(stage_reward_missing|mail_template_missing|gacha_banner_invalid|class_weapon_missing|class_skill_missing|attendance_reward_missing)
```

`loaded=0`이면 관련 요청이 전부 503(`MasterDataNotLoaded`)이 된다. **기동 실패를 즉시 알아야 하는 유일한 gauge**다.

`defect.total`이 흥미로운 지점이다. 코드 곳곳에 "마스터 결함" Error 로그가 흩어져 있다
(`StageService`의 `stage_reward 누락`, `AttendanceService`·`SaveService`·`TradeService`의 메일 템플릿 미정의,
`MasterDbProvider`의 가챠 배너 검증 실패, 직업 기본 무기/스킬 미정의). 이건 **사용자 실수가 아니라 데이터 결함**이라
반드시 0이어야 하는 값이다. 카운터로 모아 "0이 아니면 경보"로 두면, 마스터 데이터를 고칠 때 회귀 감지가 된다.

### 4.6 요약 표

| 위치 | 지표 | 타입 | 왜 |
|---|---|---|---|
| `GameApiControllerBase.ApiResult` | `game.api.result.total` | Counter | ErrorCode 59종 분포 — 상태코드로는 안 보인다 |
| `GameAuthMiddleware` | `game.auth.failure.total`, `game.auth.token_lookup.duration` | Counter, Histogram | 전 요청의 관문, Redis 지연 대표값 |
| `AuthService`, `RedisAuthTokenCache` | `account.auth.attempt.total`, `account.token.cache.duration` | Counter, Histogram | 로그인 성패·BCrypt 비용 |
| 리포지토리 트랜잭션(공통 헬퍼) | `game.db.transaction.duration` | Histogram | 도메인별 트랜잭션 길이·rollback |
| `PeriodicBatchService` | `game.batch.*` | Counter/Histogram/Gauge | 조용히 죽는 코드, 락 스킵 |
| `MasterDbProvider` | `game.masterdata.*` | Gauge/Counter | 기동 실패 = 전면 503, 데이터 결함 회귀 |
| `GlobalExceptionHandler` | 계층 0으로 충분 | — | 내장 지표가 이미 센다 |
| `RequestLoggingMiddleware` | **계측하지 않음** | — | `http.server.request.duration`과 완전히 중복 |

마지막 두 줄이 중요하다. **내장 지표가 이미 세는 것을 다시 세지 않는다.**

## 5. 계층 2 — 게임 경제·밸런스 지표

이 게임의 서버는 재화·아이템 지급의 권위자이므로, 경제 흐름을 셀 수 있는 위치에 있다.

```
game.currency.flow.total   Counter<long>  labels: currency(gold|exp|...), direction(gain|spend), source
game.gacha.pull.total      Counter<long>  labels: gacha_code, pull_type(1|10), grade, is_pity(true|false)
game.stage.clear.total     Counter<long>  labels: stage_id
game.offline.claim.total   Counter<long>  labels: capped(true|false)
game.trade.event.total     Counter<long>  labels: event(register|buy|cancel|expire)
game.inventory.full.total  Counter<long>
```

- `currency.flow`의 `source`는 `stage_clear`·`offline`·`mail`·`attendance`·`gacha_cost`·`cube_craft`·
  `trade_settlement`·`inventory_expand` 등 **고정 집합**이다. 유입/유출 균형이 무너지는 순간을 실시간으로 본다.
- `gacha.pull`의 `is_pity`는 천장 발동률이다. 확률 구현이 기획대로 도는지 검증하는 데 쓰인다
  (`GachaService`의 천장 카운터·10연 보장 로직).
- `offline.claim`의 `capped` 비율은 **12시간 상한에 걸린 사용자 비중** — 상한 조정 판단 근거가 된다.
- `stage.clear`의 `stage_id`는 100종이라 라벨로 감당 가능하다. **이탈 구간**(특정 스테이지에서 클리어가 급감)이 보인다.

> **주의**: 경제 분석의 **정본은 DB 집계**다. Prometheus는 보존 기간이 짧고(현재 15일) 카운터라서 정확한 총량
> 회계에 맞지 않는다. 여기서 노리는 건 "지금 이상한 일이 벌어지는가"의 실시간 감지다.
> 재화 어뷰징 조사·누적 발행량 같은 건 DB로 한다.

> **`item_code`를 라벨로 쓰지 않는다.** 아이템은 수백 종이고 계속 늘어난다. 등급(`grade`)·종류(`item_type`)까지만
> 라벨로 올리고, 개별 아이템 단위 분석은 DB에 맡긴다.

## 6. 인프라 exporter (선택)

애플리케이션 계측이 아니라 컨테이너를 추가하는 방식. 코드 변경이 없다.

| exporter | 얻는 것 | 판단 |
|---|---|---|
| `mysqld-exporter` | QPS·slow query·InnoDB 락 대기·커넥션 수·버퍼풀 히트율 | **`db.client.connections`(계층 0) 다음으로 값어치가 크다.** 거래소·큐브의 행 잠금 경합을 DB 쪽에서 확인 가능 |
| `redis-exporter` | 키 수·메모리·히트율·명령 지연 | 토큰·배치 락만 쓰는 지금 구성에서는 우선순위 낮음 |
| `cadvisor` / `node-exporter` | 컨테이너·호스트 리소스 | 로컬 개발 환경에서는 불필요 |

`docs/공통/쿼리-분석.md`에 쿼리 분석이 이미 정리되어 있으니, `mysqld-exporter`는 그 분석을 **런타임에 이어서
확인하는 수단**으로 쓰면 맞다.

## 7. 카디널리티 — 절대 라벨에 넣지 않을 것

Prometheus는 **라벨 값 조합 하나가 시계열 하나**다. 아래는 넣으면 메모리가 터진다.

| 금지 | 이유 | 대신 |
|---|---|---|
| `userId` | 사용자 수만큼 시계열 | 로그에 남긴다(이미 그렇게 하고 있다) |
| `token`, `email` | 카디널리티 + **PII/비밀 노출**(로깅 규칙 §7과 같은 기준) | 절대 금지 |
| `item_code`, `listing_id`, `mail_id` | 수백~무한 증가 | `grade`·`item_type`으로 묶는다 |
| 예외 메시지 전문 | 문자열마다 새 시계열 | 예외 **타입 이름**만 |
| 원시 SQL·URL 쿼리스트링 | 사실상 무한 | 라우트 템플릿·논리 operation명 |
| 타임스탬프·금액 같은 연속값 | 무한 | 값은 **지표 값**으로, 라벨이 아니다 |

기준: **라벨 값의 가능한 개수를 미리 셀 수 있고, 그게 수십 이하인가**. 못 세면 라벨이 아니다.

기타 안티패턴:
- 내장 지표와 중복 계측(§4.6)
- 게이지로 셀 수 있는 것을 카운터로, 혹은 그 반대로 — **누적은 Counter, 현재값은 Gauge, 분포는 Histogram**
- 히스토그램 버킷을 기본값 그대로 두고 방치. 이 서버 API는 대부분 수~수십 ms라, 초 단위 기본 버킷은 첫 버킷에
  전부 몰려 p95가 무의미해진다. **버킷을 5ms~2s 범위로 직접 지정**해야 한다
- 라벨을 늘려두고 안 보는 것. 안 볼 라벨은 넣지 않는다

## 8. 구현 스케치

계측 코드는 도메인별 지표 클래스에 모으고, 서비스·미들웨어가 이를 주입받는다.
(로깅과 같은 배치 — 지표는 서비스/미들웨어에서 기록하고 컨트롤러에는 두지 않는다.
단 §4.1의 `ApiResult`는 컨트롤러 베이스의 공통 응답 변환 지점이라 예외로 둔다.)

```csharp
// GameServer/Metrics/GameMetrics.cs
public sealed class GameMetrics
{
    public const string MeterName = "TaskbarHero.GameServer";

    private readonly Counter<long> _apiResult;
    private readonly Histogram<double> _txDuration;

    public GameMetrics(IMeterFactory meterFactory)
    {
        var meter = meterFactory.Create(MeterName);

        _apiResult = meter.CreateCounter<long>(
            "game.api.result", unit: "{request}", description: "엔드포인트별 ErrorCode 분포");

        _txDuration = meter.CreateHistogram<double>(
            "game.db.transaction.duration", unit: "s", description: "도메인 트랜잭션 소요");
    }

    /// <summary>API 응답 1건을 라우트·ErrorCode·성패로 집계한다.</summary>
    public void RecordApiResult(string route, ErrorCode code)
        => _apiResult.Add(1,
            new KeyValuePair<string, object?>("route", route),
            new KeyValuePair<string, object?>("error_code", code.ToString()),
            new KeyValuePair<string, object?>("outcome", code == ErrorCode.Success ? "success" : "fail"));

    /// <summary>도메인 트랜잭션 소요 시간을 결과별로 집계한다.</summary>
    public void RecordTransaction(string operation, string result, double seconds)
        => _txDuration.Record(seconds,
            new KeyValuePair<string, object?>("operation", operation),
            new KeyValuePair<string, object?>("result", result));
}
```

`Program.cs`:

```csharp
builder.Services.AddSingleton<GameMetrics>();

builder.Services.AddOpenTelemetry().WithMetrics(m => m
    .AddMeter(GameMetrics.MeterName)                    // 커스텀
    .AddMeter("Microsoft.AspNetCore.Hosting")           // 계층 0
    .AddMeter("Microsoft.AspNetCore.Server.Kestrel")
    .AddMeter("System.Runtime")
    .AddMeter("MySqlConnector")
    .AddView("http.server.request.duration",            // 버킷 재지정(§7)
        new ExplicitBucketHistogramConfiguration
        {
            Boundaries = [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2],
        })
    .AddPrometheusExporter());

// ...
app.MapPrometheusScrapingEndpoint();   // /metrics
```

주의:
- `/metrics`는 **인증 미들웨어 뒤에 두지 않는다**(Prometheus가 토큰 없이 긁는다). `GameAuthMiddleware`는
  `/api/game`만 검사하므로 현재 구조에서는 그대로 통과한다.
- 운영에 올릴 때는 `/metrics`를 외부에 노출하지 않는다(내부망 또는 별도 포트).
- 히스토그램 `Record`를 요청 경로마다 여러 번 호출하는 건 저렴하지만(락 없는 누적), **Counter를 루프 안에서
  건당 호출하는 것**은 피한다 — 다건 처리(`mail/claim-all`)는 합계를 모아 한 번에 `Add(n)` 한다.

## 9. 도입 순서

| 단계 | 범위 | 얻는 것 |
|---|---|---|
| **1** | 계층 0 켜기 + `/metrics` 노출 (계측 코드 0줄) | RED 지표·GC·커넥션 풀. Prometheus 잡 2개가 UP으로 바뀐다 |
| **2** | §4.1 `game.api.result` + §4.4 배치 지표 | ErrorCode 분포와 배치 생존. **투자 대비 회수가 가장 큰 두 개** |
| **3** | §4.2 인증/Redis + §4.3 트랜잭션 | 지연의 원인 분해(Redis vs MySQL vs 앱) |
| **4** | §4.5 마스터 데이터 + §5 경제 지표 | 데이터 결함 회귀 감지, 밸런스 실시간 관측 |
| **5** | `mysqld-exporter` | DB 내부(락 대기·slow query) |

1단계만으로도 Grafana 대시보드가 의미를 갖는다. 2단계까지가 이 프로젝트에서 실질적인 손익분기점이다.

## 10. 경보 후보 (PromQL)

Prometheus 알림 룰을 붙일 때의 초안. 지금은 룰 파일을 두지 않았으므로 Grafana 패널 임계선으로 먼저 써도 된다.

| 상황 | 식 |
|---|---|
| 5xx 급증 | `sum(rate(http_server_request_duration_seconds_count{http_response_status_code=~"5.."}[5m])) > 0.1` |
| 마스터 데이터 미적재 | `game_masterdata_loaded == 0` |
| 마스터 데이터 결함 발생 | `increase(game_masterdata_defect_total[1h]) > 0` |
| 배치 정지 | `time() - game_batch_last_success_epoch > 7200` |
| 배치 축소 운전(Redis 락 불가) | `increase(game_batch_lock_total{state="no_redis"}[10m]) > 0` |
| 커넥션 풀 고갈 | `db_client_connections_usage{state="used"} / db_client_connections_max > 0.9` |
| 인증 토큰 불일치 급증(위조·중복 로그인) | `rate(game_auth_failure_total{reason="token_mismatch"}[5m]) > 1` |
| p95 지연 악화 | `histogram_quantile(0.95, sum(rate(http_server_request_duration_seconds_bucket[5m])) by (le, http_route)) > 0.5` |

지표 이름의 Prometheus 표기(점 → 밑줄, 단위 접미사)는 exporter가 변환하므로, 실제 이름은 노출 후
`http://localhost:9090/api/v1/label/__name__/values` 로 확인한다.
