# 쿼리 분석 — 인덱스 사용·정렬 점검

> GameServer가 **플레이 경로에서 실제로 실행하는 쿼리**를 리포지토리별로 모아, 인덱스를 타는지·filesort가 생기는지 측정하고 **수정이 필요한 쿼리**를 가려낸 문서다. 스키마·인덱스 정의의 정본은 [db-erd-통합.md](db-erd-통합.md)·[db-schema.sql](db-schema.sql)이고, 각 쿼리의 설계 근거는 해당 세부 기획서다. 본 문서는 그 구조가 **실제 실행 계획에서 의도대로 동작하는지**를 확인한 기록이다.

**요약 — 사용자 대기 경로에 치명적으로 느린 쿼리는 없다.** 측정한 모든 쿼리가 인덱스를 타며, 최악값도 거래소 깊은 페이지의 30.7ms다(그마저 `MaxOffset` clamp로 상한이 정의돼 있다). 아래 3건은 "고쳐야 하는 결함"이 아니라 **여유가 있을 때 손볼 개선 후보**다.

| 우선 | 대상 | 조치 | 근거(실측) |
|---|---|---|---|
| ⚠️ | 재화 조회·스택 병합(I4·S3·K1·K2) | `player_item(user_id, row_type, item_code)` 인덱스 추가 | 0.10ms → **0.014~0.02ms**, 계정당 101행 스캔 제거 |
| ⚠️ | 가챠 기록 전체 조회(G2) | 인덱스 선택이 규모에 따라 흔들림 — 실데이터로 재확인 | 40행: `idx_gachapull_gacha`+filesort / 5,040행: PK 역순 |
| ⚠️ | 거래소 깊은 페이지(T4) | 현행 유지(clamp 10,000) · keyset 전환은 UI 요구에 달림 | OFFSET 9,950에서 **30.7ms** |
| ☑ | 가방 조회의 **DB 왕복**(I1+I2+계정 확인) | 계정 확인을 **총 칸 수 0일 때만**으로 미뤄 정상 경로 3회 → **2회**(적용 완료, 5.4) | 왕복이 줄면 그대로 처리량이 는다(5.4) |
| ⚠️ | 가방 조회의 **`total`(COUNT) 왕복** | 응답에서 `total`을 빼면 정상 경로 **1회** — API 계약 변경이라 미적용(5.5) | DB 구간 처리량 1.3~1.85배지만 **성능은 근거가 아니다**(엔드투엔드 4~5%) — 값이 클라 UI 미사용 + `/load`의 `inventoryTotal`과 중복이라는 설계 근거로 판단 |

그 외 **정상 판정**: 가방 keyset 페이징·빈 칸 탐색·코어 로드 8종·메일 목록/수령·가챠 필터 조회·조건부 갱신은 모두 인덱스를 타고 filesort가 없다(6장).

**가방 조회에 Redis 캐시를 두지 않는 결정**([기획서 6.5](../세부/inventory-item-cube-기획서.md))은 실측으로 **유지가 타당함을 확인**했다 — 캐시 히트만 보면 7~13배 빠르지만 **히트율 15~20% 아래에서는 오히려 손해**이고, 무엇보다 그 차이가 체감·용량 어느 쪽에서도 의미를 만들지 못한다(8장).

> **이 문서의 수치는 DB 구간만의 비교다.** 엔드투엔드로 보면 DB는 응답 시간의 **1/4 안팎**이고, 캐시로 아끼는 시간은 **약 1.7ms**(인터넷 RTT 포함 시 전체의 4~5%)다. 처리량도 이 프로젝트 필요량의 수십~수백 배가 이미 남는다 — **현재 규모에서 위 개선들은 체감 차이를 만들지 않는다.** 배수를 인용하기 전에 8.3을 함께 읽을 것.

## 1. 분석 방법

### 1.1 쿼리를 어떻게 수집했나

이 프로젝트는 **SqlKata 쿼리 빌더**로만 질의하므로(프로젝트 규칙: 원시 SQL 조립 금지) 코드에 SQL 문자열이 없다. 그래서 세 경로를 쓸 수 있고, 본 문서는 ①을 기준으로 하고 ②·③을 검증 수단으로 둔다.

| 경로 | 방법 | 성격 |
|---|---|---|
| ① 호출 지점 전수 추출 | `GameServer/Repositories/GameDb/*.cs`의 `db.Query("table")` 문장을 파싱해 테이블·필터·정렬·LIMIT·종결 연산을 뽑는다(스크립트, 7장) | 누락 없는 **카탈로그**. 현재 **186건** |
| ② 컴파일 결과 확인 | `new MySqlCompiler().Compile(query)`의 `Sql`/`NamedBindings`/`ToString()` | 빌더가 만드는 **실제 SQL 문자열** |
| ③ 런타임 실물 수집 | `QueryFactory.Logger`(실행 직전 훅) · `performance_schema.events_statements_summary_by_digest` · general log | 서버가 **실제로 보낸** SQL과 호출 빈도 |

> 코드를 눈으로 읽어 옮기면 **트랜잭션 안의 보조 조회**(빈 칸 탐색·잔액 조회·스택 병합 대상)를 빠뜨리기 쉽다. 실제로 186건 중 절반 이상이 그런 보조 쿼리다. 그래서 ①을 기계적으로 돌린다.

### 1.2 어디에 EXPLAIN을 걸었나

**개발 DB(`taskbar_hero_game`)에서 측정하지 않는다.** 옵티마이저는 통계 기반이라 행이 수백 건이면 인덱스 대신 풀스캔을 고르는 것이 정상이고, 그 상태의 실행 계획은 운영 판단에 쓸 수 없다. 그래서 **분석 전용 DB**를 따로 만들어 대표 규모를 채운 뒤 측정했다.

- DB: `taskbar_hero_explain` — [db-schema.sql](db-schema.sql)의 Game DB 구역을 그대로 복제(인덱스 동일).
- 측정 전 `ANALYZE TABLE`로 통계를 갱신했다.
- 도구: `EXPLAIN FORMAT=JSON`(access_type·key·used_key_parts·**attached_condition**=잔여 술어·filesort 여부) + `EXPLAIN ANALYZE`(**실제 읽은 행 수**·실행 시간).

**시드 규모** (계정 5,000 기준으로, 계정당 데이터는 실제 상한에 맞춤)

| 테이블 | 행 수 | 근거 |
|---|---|---|
| `game_player` | 5,000 | 계정 수 |
| `player_item` | 505,000 | 계정당 가방 100칸(용량 상한 120) + 재화 1행 |
| `player_item_equipped` | 90,000 | 계정당 3캐릭터 × 6부위 |
| `player_character` | 20,000 | 계정당 4(파티 3 + 미편성 1) |
| `player_skill` | 120,000 | 계정당 캐릭터 4 × 스킬 6 |
| `player_rune` | 55,000 | 계정당 11 |
| `player_mail` | 200,000 | 계정당 40 — 수령/미수령·만료/무기한·발급 시각을 섞음 |
| `player_mail_reward` | 200,000 | 메일당 첨부 1 |
| `trade_listing` | 50,000 | 판매중 60% · 판매완료 20% · 취소 10% · 만료 10%, 만료 시각 분산 |
| `player_gacha_pull` | 200,000 | 계정당 40회 |
| `player_gacha_pull_item` | 200,000 | 1연 기준 |

### 1.3 범위에서 뺀 것

- **마스터 데이터 쿼리**: 기동 시 1회 인메모리 적재라 플레이 경로가 아니다(`MasterDbProvider`). 성능 대상에서 제외한다.
- **배치 쿼리**: `GameServer/Batch/`의 주기 배치(`TradeExpireBatchScheduler`·`MailGcBatchScheduler`)가 쓰는 대상 조회는 **사용자가 응답을 기다리는 경로가 아니다.** 거래 만료·메일 GC 모두 1시간에 한 번 돌고 한 주기 처리 건수도 `BatchSize`(1,000 / 500)로 상한이 잡혀 있어, 대상 조회가 수십 ms 걸려도 체감이나 처리량에 영향이 없다. 카탈로그(3장)에는 남기되 **측정·판정 대상에서 제외**한다.
- **잠금 경합**: EXPLAIN의 관심사가 아니다. 이 프로젝트의 직렬화는 조건부 갱신의 행 잠금이 담당하며(거래소 기획서 7.4), 진단은 `performance_schema.data_locks`·`sys.innodb_lock_waits`로 한다.
- **단순 PK 쓰기**(`WHERE player_item_id=?` UPDATE/DELETE 등): 계획이 자명해 개별 측정 대상에서 빼고 카탈로그에만 남긴다.

## 4. 측정 결과

> `EXPLAIN FORMAT=JSON` + `EXPLAIN ANALYZE`, 분석 DB(1.2 규모). **key**=선택된 인덱스와 실제 사용 컬럼, **스캔**=인덱스로 좁혀 읽은 행 수(추정), **정렬**=filesort 발생 여부, **판정** ✅정상 / ⚠️주의 / 🔴수정 권고.
>
> ⚠️ 실측 시간은 **버퍼풀 상태에 민감**하다(첫 실행은 디스크 I/O 포함). 판정은 시간이 아니라 **계획(선택 인덱스·잔여 술어·filesort)** 을 근거로 하고, 시간은 개선 전/후 비교에만 썼다.

## 5. 개선 여지가 있는 쿼리

**어느 것도 지금 당장 고쳐야 하는 결함이 아니다.** 사용자 대기 경로에서 가장 느린 쿼리가 30.7ms(T4, 그것도 clamp로 상한이 잡힌 최악값)이고 나머지는 모두 1ms 미만이다. 아래는 여유가 있을 때 손볼 후보와, 규모가 커졌을 때 다시 볼 지점을 기록한 것이다. 각 개선안은 **분석 DB에 실제로 인덱스를 붙여 전/후를 측정**해 확인했다(수치는 그 실험값).

### ⚠️ 5.1 `player_item(user_id, row_type, item_code)` 인덱스 추가

**문제**: `player_item`의 인덱스는 `idx_item_user(user_id)`·`uq_item_slot(user_id, slot)` 둘뿐이라, **재화 조회·스택 병합·재료 소모가 모두 `user_id`로만 좁힌 뒤 계정당 101행을 잔여 술어로 훑는다.** 특히 재화(골드) 행 조회는 강화·확장·룬·큐브·가챠·거래·스테이지·오프라인 등 **재화를 만지는 모든 트랜잭션**에 들어가 빈도가 가장 높다.

| 쿼리 | 현재 | `(user_id, row_type, item_code)` 추가 후 |
|---|---|---|
| I4 재화 행 조회 | 0.095ms | **0.014ms** |
| S3 재화 전건(코어 로드) | 0.104ms | **0.012ms** |
| K1 스택 병합 대상 | 0.101ms | **0.020ms** |
| K2 재료 소모 대상 | 0.102ms | **0.018ms** |

`enhance_level`·`player_item_id`까지 5컬럼으로 늘려도 K1이 0.020 → 0.015ms로 미미해, **3컬럼이 비용 대비 최적**이다. 쓰기가 잦은 테이블(전리품·가챠 적재)이라 인덱스를 하나 늘리는 유지 비용은 감수 판단이 필요하다.

### ⚠️ 5.2 가챠 기록 전체 조회 — 인덱스 선택이 불안정하다

`idx_gachapull_user(user_id, pull_id)`가 **바로 이 쿼리를 위해** 있는데도 선택되지 않았다.

| 계정당 기록 | 선택된 key | 정렬 |
|---|---|---|
| 40행 | `idx_gachapull_gacha (user_id)` | **filesort** |
| 약 5,040행 | `PRIMARY` (역순 스캔) | 없음 |

두 후보 인덱스가 `user_id` 접두를 공유해 비용 추정이 엇비슷하고, 규모에 따라 선택이 흔들린다. **PK 역순 스캔은 그 계정 행이 드물면 위험**하다(전체를 역순으로 훑다가 21건을 만나야 끝난다). 지금은 실측이 0.37ms라 급하지 않으므로 **실데이터가 쌓인 뒤 재확인**을 권한다. 대응 후보는 ①`idx_gachapull_gacha`를 `(user_id, gacha_code, pull_id)`로 둔 채 전체 조회에 인덱스 힌트, ②중복 인덱스 정리.

### ⚠️ 5.3 거래소 깊은 페이지 — 최악 30.7ms

`OFFSET 9,950`에서 계획이 바뀌어 10,001행을 정렬 버퍼에 넣는다(T2는 filesort가 없는데 T4는 생긴다). 현재 `MaxOffset = 10,000` clamp가 **최악 비용을 정의**하는 구조다. 해소하려면 `(price, listing_id)` keyset 커서로 바꿔야 하지만, 그러면 임의 페이지 점프를 못 한다 — UI 요구사항에 달린 문제라 지금은 **상한을 유지**하고 기록만 남긴다.

### ☑ 5.4 가방 조회의 DB 왕복 — 계정 확인을 조건부로(적용 완료)

가방 조회의 지연은 **쿼리가 아니라 왕복 수가 결정한다.** 쿼리 셋 다 인덱스를 타고 DB 엔진 시간은 0.1ms 미만이지만(I1·I2·S1), 애플리케이션에서 재면 **왕복·프로토콜·매핑 비용이 쿼리당 0.5~0.8ms**다(엔드투엔드 측정에서도 왕복 1회의 몫이 1.55ms로 나온다 — 8.3).

| 형태(동시성 32) | p50 | 처리량 |
|---|---|---|
| 왕복 3회 | 7.738ms | 3,711 RPS |
| 왕복 1회(페이지 쿼리만) | **4.154ms** | **6,438 RPS** |

**현재 구조**: `GetPageAsync`는 keyset 페이지(I1) → 총 칸 수 COUNT(I2)를 친 뒤, **총 칸 수가 0일 때만** 계정 존재 확인(S1)을 추가로 친다. 근거는 스키마에 있다 — `player_item`이 `game_player`에 FK(`fk_item_player … ON DELETE CASCADE`)로 매달려 있어 **세이브 없이 아이템 행이 존재할 수 없으므로**, 총 칸 수가 1 이상이면 세이브 존재가 이미 증명된다. 가방이 완전히 빈 계정에서만 세 번째 왕복이 발생해 `SaveNotFound(2001)`와 "세이브는 있고 가방만 빔"을 가른다.

- **응답 계약은 그대로다** — 세 경우(아이템 있음 / 가방만 빔 / 세이브 없음)의 응답이 확인을 먼저 하던 때와 동일하다. 커서가 끝을 지나 빈 페이지가 나와도 `total > 0`이라 확인 쿼리를 타지 않는다.
- **남은 여지**: `total`(I2)까지 없애면 왕복이 1회로 준다 — 측정과 판단 근거는 5.5.

### ⚠️ 5.5 `total`(COUNT) 제거 — 왕복 1회 (계약 변경 필요, 미적용)

5.4를 적용해도 **COUNT 왕복 하나가 남는다.** 이 값(`total`, 가방 점유 칸 수)을 응답에서 빼면 정상 경로가 **쿼리 1회**로 끝난다(페이지 결과가 비었을 때만 세이브 확인이 붙어 2회).

**측정** — 환경·데이터는 8.1과 같다. 세 형태 모두 같은 DTO 매핑을 수행해 매핑 비용 차이를 없앴다.

| 페이지 크기 | 동시성 | 3쿼리(옛) | 2쿼리(현행) | **1쿼리(total 제거)** | 현행 대비 |
|---|---|---|---|---|---|
| 201 | 1 | 3.092ms / 306 RPS | 2.393ms / 397 | **1.428ms / 669** | **1.68×** |
| 201 | 8 | 3.297 / 2,325 | 2.612 / 2,968 | **2.016 / 3,802** | **1.28×** |
| 201 | 32 | 8.197 / 3,533 | 6.444 / 4,459 | **4.481 / 5,850** | **1.31×** |
| 201 | 64 | 16.656 / 3,463 | 12.996 / 4,511 | **7.468 / 7,663** | **1.70×** |
| 21 | 1 | 2.570 / 379 | 2.159 / 450 | **1.343 / 720** | **1.60×** |
| 21 | 8 | 3.210 / 2,405 | 3.114 / 2,225 | **1.899 / 4,045** | **1.82×** |
| 21 | 32 | 9.718 / 2,826 | 9.480 / 2,767 | **4.994 / 5,121** | **1.85×** |
| 21 | 64 | 19.495 / 2,908 | 16.263 / 3,405 | **10.428 / 4,786** | **1.41×** |

(p50 지연 / 처리량. `limit=21`의 동시성 8·32에서 2쿼리가 3쿼리보다 느리게 나온 것은 구간별 부하 흔들림이며, 1쿼리 우위는 모든 구간에서 일관된다.)

**처리량 1.3~1.85배, 단일 요청 지연 40% 감소.** 페이지가 작을수록 이득이 커진다 — COUNT는 페이지 크기와 무관하게 계정의 점유 칸 전체를 세므로, 반환 행이 적을수록 전체 비용에서 COUNT가 차지하는 몫이 커지기 때문이다.

**`total`이 실제로 쓰이는가** — 빼도 되는지는 성능이 아니라 이 질문이 정한다. 확인 결과 세 가지가 나왔다.

| 확인 대상 | 사실 |
|---|---|
| 클라이언트 소비 | `InventoryLoader`가 `Total` 프로퍼티에 담고 **로그 문자열에만** 쓴다. 이 프로퍼티를 참조하는 UI 코드가 없다 |
| 중복 여부 | 같은 값이 코어 로드 응답의 **`inventoryTotal`** 로 이미 내려간다([api-통합](api-통합.md) `/api/game/load`) — 접속 시 1회 |
| 프로젝트 선례 | 가챠 기록 조회는 같은 keyset 페이징인데 **"전체 건수(total)는 내려주지 않는다"** 로 확정돼 있다(`GachaHistoryResultData`) |

즉 `total`은 **UI가 쓰지 않고, 코어 로드와 중복이며, 같은 형태의 다른 API는 이미 빼고 있다.** 값의 성격도 "그 페이지를 읽은 시점 기준 근사치"라 정확성을 보장하지 않는다([세이브 데이터 기획서](../세부/save-data-기획서.md) 5.2).

**캐시와의 관계** — 기준선이 빨라지면 캐시 히트와의 격차도, 히트율 손익분기도 캐시에 불리해진다(8.2). 즉 이 개선은 캐시의 대안이 아니라 **캐시보다 먼저 해야 할 일**이다.

**단, 성능이 이 변경의 근거는 아니다.** 위 수치는 DB 구간만의 비교이고, 엔드투엔드로 환산하면 왕복 하나를 줄여 아끼는 시간은 **약 1.5ms(전체 응답의 20% 남짓, 인터넷 RTT를 포함하면 4~5%)** 로 체감 불가다(8.3). `total`을 빼는 실질적 이유는 **UI가 쓰지 않고 코어 로드와 중복인 값을 응답 계약에서 걷어내는 설계 정리**이며, 왕복 감소는 부수 효과로 본다.

**미적용 상태다.** 응답 필드 제거는 `InventoryPageDto`·[api-통합](api-통합.md)·[세이브 데이터 기획서](../세부/save-data-기획서.md) 5.2·[인벤토리 기획서](../세부/inventory-item-cube-기획서.md) 6.5와 클라이언트 소비 코드가 함께 걸린 **API 계약 변경**이라, 측정과 근거만 확정해 두고 적용은 별도 작업으로 남긴다. 적용 시 남는 세이브 확인은 **페이지 결과가 비었을 때만** 치면 되므로(FK 근거는 5.4와 동일) `SaveNotFound(2001)` 계약은 그대로 유지된다 — 단, `total`이 없으면 "커서가 끝을 지난 빈 페이지"와 "가방이 빈 계정"을 구분할 수 없어 **마지막 페이지 요청에서도 확인 쿼리 1회가 붙는다.**

### 정보성 — 쓰이지 않는 인덱스 하나

`player_buff.idx_buff_expires(expires_at)`는 **현재 어떤 쿼리도 쓰지 않는다.** 활성 버프 판정은 `WHERE user_id=? AND expires_at>?`로 PK 접두를 타고(X1), 이 인덱스를 쓸 **만료 버프 정리 배치가 구현되지 않았다**(`GameServer/Batch/`에는 거래 만료·메일 GC 둘뿐). [소모품/버프 기획서](../세부/consumable-buff-기획서.md) 6.4가 예고한 정리 배치를 만들거나, 도입 전까지 인덱스를 걷는 판단이 필요하다.

| 빈 칸 탐색(I3) | 커버링 인덱스 스캔 82행 | 계정당 최대 120행이 상한이고 커버링이라 테이블 접근이 없다. "전량 읽기"라는 형태만 보고 고칠 이유가 없다 |
| 코어 로드 8종(S1~S8) | 전부 PK/유니크 접두 | 계정당 수~수십 행. 잔여 술어(`row_type`·`level>0`)도 그 규모에서 무해 |
| `mine=true` 목록(T3)의 filesort | 계정당 ≤10행 정렬 | 등록 한도가 10건이라 정렬 대상이 구조적으로 작다 |
| 메일 목록(M1)·일괄 수령(M3) | 역방향 인덱스 스캔, filesort 없음 | `OR` 조건이 잔여 술어지만 계정당 40행. **단** 아래 설계 이슈는 별개다 |
| 조건부 갱신(X3·X4·구매·취소·만료) | `PRIMARY` 단건 | 직렬화 장치이므로 성능 대상이 아니다(잠금은 EXPLAIN 밖, 1.3) |

**설계 이슈로 남기는 것**: 우편함 조회(M1)는 페이징이 없다. [메일 기획서](../세부/mail-기획서.md) 6.5는 "보관 7일 정책으로 목록 크기가 자연히 유계"라는 근거로 전건 반환을 확정했는데, **GC는 미수령 무기한 메일(`expires_at=0 AND claimed=0`)을 삭제 대상에서 제외**한다(거래 구매 아이템 보호). 즉 수령하지 않고 쌓이는 메일에는 상한이 없어, 전제가 성립하지 않는 구간이 있다. 쿼리 자체는 정상이므로 인덱스 문제가 아니라 **정책 문제**로 분류한다.

## 7. 재현 방법

측정에 쓴 스크립트는 저장소에 커밋하지 않고(일회성 분석 도구) 아래 절차로 재현한다.

1. **쿼리 카탈로그 추출** — `GameServer/Repositories/GameDb/*.cs`에서 `db.Query(` 문장을 파싱해 테이블·필터·정렬·LIMIT·종결 연산을 출력한다(1.1-①).
2. **분석 DB 생성** — [db-schema.sql](db-schema.sql)의 Game DB 구역을 복사해 DB 이름만 `taskbar_hero_explain`으로 바꿔 적용한다.
3. **대표 규모 시드** — 1.2 표의 행 수를 재귀 CTE(`WITH RECURSIVE`)로 생성하고 `ANALYZE TABLE`을 돌린다.
4. **EXPLAIN 실행** — 4장 표의 SQL을 `EXPLAIN FORMAT=JSON` / `EXPLAIN ANALYZE`로 실행해 access_type·key·used_key_parts·attached_condition·filesort·actual rows를 수집한다.
5. **개선안 검증** — 후보 인덱스를 `ALTER TABLE … ADD INDEX`로 붙이거나 쿼리를 바꿔 전/후를 다시 측정한다(5장 수치의 출처). 측정 후 실험용 인덱스는 `DROP INDEX`로 되돌린다.
6. **정리** — `DROP DATABASE taskbar_hero_explain`.

### 7.1 시드에서 실제로 걸린 함정 (재현 시 반드시 확인)

측정값을 무효로 만들 수 있는 문제를 세 번 겪었다. 같은 실수를 반복하지 않도록 남긴다.

| 함정 | 증상 | 대처 |
|---|---|---|
| **`TEMPORARY` 테이블을 한 문장에서 두 번 참조** | `ERROR 1137 Can't reopen table: 'nums'` — 숫자 테이블을 self-join 하는 캐릭터·스킬·룬 생성에서 시드가 중단됨 | 숫자 테이블을 **일반 테이블**로 만들고 시드 끝에서 `DROP` |
| **`n % 300000` 같은 나머지로 시각을 흩뿌림** | `n`이 5만·20만까지라 나머지가 무효가 되어 범위가 뭉침 → 거래 등록이 **전부 만료**, 메일이 **전부 보관 기한 이내** → 거래소 목록(T1~T5)이 **빈 결과 위에서 측정** | 곱셈으로 범위를 넓힌다(`기준 + id × 6` 등). 시드 후 **측정 대상 조건의 건수를 직접 세어 확인**한다 |
| **파생 컬럼끼리 상관됨** | `item_code = 31011 + (n%40)`, `status = f(n%10)`이라 특정 `item_code`는 항상 특정 `status`만 가짐 → 탐침 값이 조건에 아예 안 걸림 | 탐침 값을 실제 데이터에서 골라 확인한 뒤 쓴다 |

> 교훈: **시드를 넣었다는 것과 측정 대상 조건이 존재한다는 것은 다르다.** EXPLAIN을 돌리기 전에 `SELECT COUNT(*)`로 각 조건의 실제 건수를 확인하는 절차를 반드시 넣는다.

> 실물 SQL을 대조하려면 개발 환경에서 `GameDbFactory.Create(...)`가 만드는 `QueryFactory`에 `Logger`를 붙이거나(`Logger = r => log(r.ToString())`), MySQL의 `performance_schema.events_statements_summary_by_digest`를 읽는다(1.1-②·③).

## 8. 인벤토리 조회 — Redis 캐시 유무 실측 비교

가방 조회(`POST /api/game/inventory/list` → `InventoryRepository.GetPageAsync`)에 **Redis 캐시를 두지 않는다**는 확정 판단([인벤토리 기획서 6.5](../세부/inventory-item-cube-기획서.md))은 정성적 근거(캐시가 이득을 내는 네 조건) 위에 서 있었다. 그 판단이 수치로도 성립하는지 확인한 기록이다.

비교 기준은 **현재 구현 그대로**다 — DB 왕복 2회(keyset 페이지 + 총 칸 수 COUNT, 가방이 비었을 때만 세이브 확인).

**결론: 캐시 미도입 판단은 유지가 타당하다.** 이유는 "캐시가 느려서"가 아니다 — 캐시 히트는 실제로 7~13배 빠르다. 근거는 셋이다.

1. **캐시가 걷어낼 비싼 쿼리가 애초에 없다.** `player_item`은 대형 테이블이지만 가방 조회는 조인 없는 단일 테이블 접근이고, `(user_id, slot)` 인덱스가 범위 스캔과 정렬을 함께 담당해 filesort가 없으며, 읽는 행이 계정당 가방 용량(≤120)에 묶인다 — **스키마 설계가 캐시가 할 일을 미리 해 뒀다**(8.4).
2. 이득이 **히트율에 전적으로 달려 있고, 손익분기(약 15~20%) 아래에서는 캐시가 오히려 손해**다(8.2). 가방은 전리품·가챠·큐브·메일 수령·거래로 **조회보다 변경이 잦은** 데이터다.
3. 그 차이가 **체감에도 용량에도 의미를 만들지 못한다** — DB 조회는 API 응답 시간의 1/4 안팎이고, 처리량은 이미 필요량의 수백 배가 남는다(8.3).

### 8.1 측정 방법

| 항목 | 값 |
|---|---|
| CPU | Intel i7-12700F (12코어 / 20스레드) |
| MySQL | 8.4.10 (Docker, `innodb_buffer_pool_size` 128MB 기본값) |
| Redis | 8.8.0 (로컬 인스턴스) |
| 런타임 | .NET 10 / MySqlConnector 2.6.1 · SqlKata 4.0.1 · CloudStructures 3.4.2 |
| 배치 | 클라이언트·MySQL·Redis가 **같은 머신**(네트워크 홉 없음) |
| 데이터 | 분석 DB `taskbar_hero_bench` — 계정 5,000 · `player_item` 505,000행(계정당 가방 100칸 + 재화 1행), 1.2와 같은 규모 |

| 경로 | 동작 |
|---|---|
| `DB(현행)` | `GetPageAsync`의 2쿼리를 SqlKata로 그대로 재현 |
| `CacheHit` | `inv:bag:{userId}` 스냅샷 GET → JSON 역직렬화 → 커서 구간 슬라이스 |
| `CacheMiss` | GET(miss) → **DB 2쿼리** → 직렬화 → SET |
| `Invalidate` | DEL — 가방을 바꾸는 **쓰기 경로가 부담할 비용** |

캐시 값은 **계정 가방 전체 스냅샷**이다(페이지 단위로 캐싱하면 커서마다 키가 생겨 무효화가 그만큼 늘어난다). 계정당 JSON **7,503바이트**로, 5,000계정이면 Redis 메모리 **약 35MB**(활성 계정 10만이면 ~700MB).

조건마다 워밍업 후 본 측정을 했고, 히트율 혼합은 **기준선을 조건 사이에 교대로 재서** 같은 구간끼리 비교했다. 미스 경로도 같은 2쿼리로 채워 대칭을 맞췄다.

### 8.2 결과 — 캐시가 빠른 것은 맞다, 다만 히트율이 전부다

| 동시성 | DB(현행) | CacheHit | 배수 |
|---|---|---|---|
| 1 | 1.962ms / 494 RPS | **0.264ms / 3,565** | 7.2× |
| 8 | 2.447 / 3,154 | **0.331 / 22,491** | 7.1× |
| 32 | 6.610 / 4,292 | **0.580 / 48,917** | 11.4× |
| 64 | 12.704 / 4,427 | **1.066 / 57,626** | 13.0× |

(p50 지연 / 처리량. DB는 동시성 32에서 이미 4,300 RPS 부근으로 포화해 이후로는 지연만 늘어난다.)

**그런데 나머지 두 경로가 그림을 뒤집는다**(동시성 8).

| 경로 | p50 | 처리량 |
|---|---|---|
| DB(현행) | 2.447ms | 3,154 RPS |
| **CacheMiss** | **2.917ms** | 3,538 |
| Invalidate(쓰기가 추가로 무는 비용) | 0.219ms | — |

**캐시 미스는 캐시가 없을 때와 사실상 같다**(DB 2쿼리를 그대로 하고 GET·SET이 얹힌다). 여기에 가방을 바꾸는 **모든 쓰기가 DEL 0.22ms를 추가로** 문다. 그래서 순이득은 히트율이 정한다 — 확률 (1−h)로 무효화가 먼저 일어나는 혼합 부하로 측정했다(동시성 32).

| 히트율 | 캐시 혼합 | 같은 구간 DB 기준선 | 배수 |
|---|---|---|---|
| 100% | 41,578 RPS | 4,167 | **9.98×** |
| 70% | 13,683 | 5,376 | **2.55×** |
| 50% | 7,331 | 3,688 | **1.99×** |
| 30% | 5,376 | 4,640 | **1.16×** |
| 15% | 4,329 | 4,242 | **1.02×** |
| 0% | 3,765 | 5,008 | **0.75×** ❌ |

**손익분기는 히트율 15~20% 부근이다**(기준선이 구간마다 3,688~5,376으로 흔들려 폭으로 적는다). 그 아래에서는 캐시가 있는 쪽이 더 느리다.

가방이 이 선을 넘는지는 **변경 빈도**가 정한다. `player_item`을 바꾸는 경로는 전리품 획득(스테이지 클리어마다)·가챠·큐브·메일 수령·거래·강화·장착/해제/이동으로 **전투가 도는 동안 계속** 발생한다. 반면 `/inventory/list`는 **가방 UI를 열 때만** 호출되고, 액션 응답의 `inventoryDelta`로 클라이언트가 로컬 갱신하므로 재조회하지 않는다([인벤토리 기획서](../세부/inventory-item-cube-기획서.md) 5.0).

### 8.3 그 차이에 의미가 있는가 — 배수가 아니라 절대 크기로 본다

위 수치는 모두 **DB 조회 구간만** 잰 값이다. "캐시가 10배 빠르다"가 무엇을 바꾸는지는 그 구간이 전체 응답에서 얼마를 차지하는지를 알아야 한다. 실제 GameServer에 API를 호출해 엔드투엔드를 쟀다(localhost, 개발 계정 가방 25칸, 응답 1,917바이트, Development 구성).

| 엔드포인트 | DB 왕복 | p50 | min |
|---|---|---|---|
| `POST /inventory/list` | SELECT 2회 | **7.527ms** | 2.703 |
| `POST /update-last-active` | UPDATE 1회 | **5.979ms** | 1.967 |

**DB 조회는 응답 시간의 1/4 안팎이다.** 같은 머신의 DB 구간이 약 2ms인데 엔드투엔드는 7.5ms다 — 나머지는 HTTP 스택·인증 미들웨어(Redis 토큰 조회 왕복 1회)·JSON 직렬화·접근 로그가 쓴다. 두 엔드포인트의 차이(7.527 − 5.979 = 1.55ms)가 **DB 왕복 1회의 실제 몫**이다.

| 관점 | 계산 | 결과 |
|---|---|---|
| 캐시로 아끼는 절대 시간 | DB 2.0ms → 캐시 0.26ms | **약 1.7ms** |
| 엔드투엔드에서의 비중 | 1.7 / 7.5 | **23%**(상한 추정) |
| 실제 인터넷 RTT(20~50ms) 포함 | 1.7 / (7.5 + 30) | **4~5%** |
| 사용자 인지 가능성 | 체감 임계(수십~100ms)의 1/50 수준 | **인지 불가** |

> 엔드투엔드는 가방 25칸 계정으로 쟀고 DB 벤치는 100칸이라, 실제 DB 몫은 위보다 작다 — **23%는 상한**이다.

**처리량 여유도 같은 결론을 가리킨다.**

| 가정 | 필요 처리량 | 현행(4,292 RPS) 대비 |
|---|---|---|
| 동시 접속 1,000명이 분당 1회 가방을 연다 | 약 17 RPS | 여유 **약 250배** |
| 동시 접속 10,000명이 분당 1회 | 약 167 RPS | 여유 **약 26배** |

서버 1대의 현행 구현으로도 필요량의 수십~수백 배가 남는다. 캐시가 만드는 49,000 RPS는 이 프로젝트가 쓸 일이 없는 용량이다.

**측정 신뢰도** — 배수를 인용할 때의 주의점이다.

| 비교 | 차이 | 실행 간 변동 | 판단 |
|---|---|---|---|
| 캐시 vs DB(히트 100%) | 7~13배 | ±20~50% | **확실히 유의** — 노이즈보다 훨씬 크다 |
| 히트율 15~30% 구간 | 1.0~1.2배 | 기준선이 ±20% 흔들림 | **손익분기는 점이 아니라 폭**으로 읽어야 한다 |
| 엔드투엔드 | 동시성 8에서 p50이 15.2ms로 튐(같은 조건 대조군은 3.5ms) | 큼 | 비중 추정용, 정밀 비교 불가 |

엔드투엔드는 **Development 구성**(Information 레벨 콘솔 로깅·Swagger·HTTPS 리다이렉션)에서 쟀다. 이 점은 "DB가 병목이 아니다"를 약화시키지 않고 오히려 강화한다 — 줄일 것이 DB 밖에 더 많다는 뜻이다.

### 8.4 판정

| 항목 | 판정 |
|---|---|
| 가방 조회 Redis 캐시 도입 | ❌ **도입하지 않는다** — 기획서 6.5 판단 유지. 히트율이 손익분기(15~20%) 아래일 개연성이 있고, 정합성 위험(경합·잃은 갱신·무효화 누락)을 함께 사게 된다 |
| 캐시가 필요 없는 1차 이유 | ☑ **쿼리 비용을 스키마 설계에서 이미 없앴다** — 캐시로 걷어낼 "비싼 쿼리"가 애초에 존재하지 않는다(아래 상술) |
| 2차 이유 | ⓘ **차이 자체가 의미를 만들지 못한다** — 캐시로 아끼는 1.7ms는 엔드투엔드의 23%(상한), 인터넷 RTT 포함 시 4~5%다. 처리량도 필요량의 수십~수백 배가 이미 남는다(8.3) |
| 재검토 트리거 | 동접이 늘어 `/inventory/list`가 실제 병목으로 관측될 때. 단 **DB 구간이 응답의 1/4뿐이므로**, 지연을 줄여야 하면 HTTP 스택·인증·직렬화·로깅부터 본다 |

**쿼리 비용을 사전에 절감한 설계가 이 판정의 전제다.** `player_item`은 계정 수에 비례해 무한히 커지는 **대형 테이블**이고(측정 시드 505,000행), 이 프로젝트에서 페이징이 필요한 유일한 테이블이다([세이브 데이터 기획서](../세부/save-data-기획서.md) 2장). 그럼에도 가방 조회가 싼 이유는 세 가지를 설계 단계에서 미리 잡아 뒀기 때문이다.

| 설계 결정 | 효과 | 실측 확인 |
|---|---|---|
| **조인을 만들지 않았다** — 장착 여부·위치를 `player_item_equipped`로 분리하되, 가방 조회는 `player_item` **단일 테이블**만 읽는다(장착 중인 장비는 `slot IS NULL`이라 조건에서 자동으로 빠진다) | 조인 순서·조인 버퍼 같은 옵티마이저 변수가 없다 | 4.2 I1 — 단일 테이블 range 접근 |
| **쿼리에 맞춰 인덱스를 잡았다** — `(user_id, slot)` 유니크 인덱스는 원래 "한 칸에 한 행" 제약용인데, **keyset 커서(`slot > ?`)와 `ORDER BY slot`이 이 인덱스를 그대로 재사용**한다. 페이징 전용 컬럼·인덱스를 따로 만들지 않았다 | 범위 스캔과 정렬을 **인덱스 하나가 동시에** 담당 | 4.2 I1·I2 — `uq_item_slot` range |
| **filesort를 만들지 않았다** — 정렬 키가 인덱스 순서와 같다 | 정렬 버퍼·임시 테이블 없음 | 4.2 I1 **filesort 없음**(6장에서 "손댈 것이 없다"로 확정) |

결과적으로 **읽는 행이 테이블 전체 크기와 무관하게 계정당 가방 용량(≤120)에 묶인다** — 50만 행이든 5천만 행이든 한 요청이 훑는 범위는 그대로다. DB 엔진 실행 시간이 0.1ms 미만인 것도 이 때문이고(4장), 그래서 8.3에서 본 것처럼 **DB는 응답 시간의 1/4밖에 차지하지 않는다.**

이것이 기획서 6.5의 네 조건 중 **"원 쿼리가 비싸다 → ✗"** 에 해당한다. 캐시는 비싼 계산을 재사용할 때 이득을 내는데, 여기서는 **원본 쿼리가 캐시 조회와 같은 급으로 싸다.** 만약 조인이 끼거나 filesort가 생기는 구조였다면 같은 측정에서 캐시 쪽으로 결론이 기울었을 수 있다 — 즉 이 판정은 "Redis가 불필요하다"가 아니라 **"인덱스 설계가 캐시가 할 일을 미리 해 뒀다"** 로 읽는 것이 맞다.

> 이 측정은 **같은 머신**에서 이뤄져 네트워크 홉이 없다. MySQL과 Redis가 원격이면 왕복 비용이 커져 캐시의 상대 이득도 커지지만, 손익분기는 그대로 히트율 문제로 남는다.

### 8.5 재현 방법

측정 코드는 일회성이라 저장소에 커밋하지 않는다.

1. **벤치 DB 시드** — [db-schema.sql](db-schema.sql)의 `game_player`·`player_item`을 `taskbar_hero_bench`로 복제하고, 재귀 CTE로 계정 5,000 × (가방 100 + 재화 1)행을 넣은 뒤 `ANALYZE TABLE`.
2. **측정 앱** — .NET 콘솔에 MySqlConnector·SqlKata·CloudStructures를 참조해 8.1의 4경로를 구현한다. DB 경로는 `GetPageAsync`를 그대로 옮긴다.
3. **측정** — 조건마다 워밍업 후 본 측정, 지연 배열을 정렬해 p50/p95/p99와 처리량을 낸다. 히트율 혼합은 확률 (1−h)로 DEL을 먼저 호출하고, **기준선을 조건 사이에 교대로** 잰다. **형태 간 비교는 반드시 한 실행 안에서** 한다(실행이 다르면 버퍼풀·OS 캐시로 절대값이 흔들린다).
4. **엔드투엔드(8.3)** — 기동한 GameServer에 HTTP로 요청해 재고, **DB 왕복이 하나 적은 대조군**(`/update-last-active`)과의 차이를 왕복 1회 몫으로 본다. 서버 구성(Development/Production)을 함께 기록한다.
5. **정리** — `DROP DATABASE taskbar_hero_bench`, 벤치 키 삭제. 개발용 Redis를 함께 쓴다면 **DB 인덱스를 분리**해(`,defaultDatabase=5`) 기존 키와 섞이지 않게 한다.

> 재현 시 함정: **캐시 프리로드 직후 첫 수천 회는 지연이 크게 튄다**(측정 중 p99 3.5초 관측). 조건마다 워밍업을 넣고 그 수치를 결과에 섞지 않는다.
