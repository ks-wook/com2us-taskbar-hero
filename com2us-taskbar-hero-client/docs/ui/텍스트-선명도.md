# UI 텍스트 선명도

인게임 씬(TitleScene·GameScene 등)에서 텍스트가 흐릿하게 보이던 문제의 원인과 해결. 원인이 **두 가지**이고 성격이 전혀 다르다.

- **A. 렌더 해상도 업스케일** — 화면 전체(텍스트·픽셀아트 모두)가 흐려진다. → [원인 A](#원인-a--렌더-해상도가-창보다-작으면-전체가-흐려진다)
- **B. AA 벡터 폰트** — 이미지·스프라이트는 선명한데 **텍스트만** 흐려 보인다. → [원인 B](#원인-b--aa-벡터-폰트-대-하드-엣지-픽셀아트)

**텍스트가 흐리다는 보고를 받으면 A를 먼저 확인한다.** A는 글리프에 들어가는 픽셀 수 자체가 줄어드는 문제라 B의 셰이더로 보정할 수 없다.

## 원인 A — 렌더 해상도가 창보다 작으면 전체가 흐려진다

Game 뷰의 **Low Resolution Aspect Ratios**(툴바 해상도 드롭다운 안)가 켜져 있으면 Unity는 게임을 **논리 해상도(포인트)로 렌더한 뒤 창 크기(물리 픽셀)로 확대**한다. 고DPI 디스플레이에서는 이것이 그대로 배율만큼의 블러가 된다.

실측(2026-08-03, 배율 150% 디스플레이 = `EditorGUIUtility.pixelsPerPoint 1.5`, TitleScene):

| | 토글 ON (흐림) | 토글 OFF (선명) |
|---|---|---|
| Game 뷰 창(물리 픽셀) | 1708×944 | 1708×944 |
| 게임 렌더 해상도(`Screen`) | **1081×608** → 1.5배 확대 | **1622×913** (창과 1:1) |
| 씬 캔버스 배율(ref 360×640) | 1.689 | 2.535 |
| 텍스트 래스터(`fontSize × 배율`) | 17~25px | **25~38px** |

즉 글리프에 들어가는 픽셀이 1.5배 늘어난다 — 셰이더로는 얻을 수 없는 개선이다.

이 값은 프로젝트 설정이 아니라 **Game 뷰 창(에디터 레이아웃) 상태**라 레이아웃 초기화·에디터 업그레이드로 조용히 다시 켜진다(2026-08-03에 실제로 켜져 있었다). 그래서 `Assets/Editor/GameViewResolutionGuard.cs`가 에디터 로드 시마다 확인해 꺼 준다(수동: 메뉴 `TaskbarHero/UI/Game 뷰 저해상도 렌더링 끄기`). 세션 중에 직접 켜는 것은 막지 않으며(저DPI 기기 에뮬레이션 등) 다음 에디터 로드에서 다시 꺼진다.

빌드에는 이 토글이 없다(에디터 전용). 빌드에서 같은 증상이 보이면 URP `renderScale`(현재 1)과 창 크기 대비 `Screen.width/height`를 먼저 확인한다.

## 원인 B — AA 벡터 폰트 대(對) 하드 엣지 픽셀아트

측정값(TitleScene 기준):

| 항목 | 값 |
|---|---|
| 폰트 | 빌트인 동적 폰트 `LegacyRuntime.ttf` (프로젝트에 폰트 에셋이 없어 전 UI가 이것을 사용) |
| 폰트 아틀라스 필터 | Bilinear, 그레이스케일 안티에일리어싱 |
| UI 캔버스 | `ScreenSpaceOverlay` + `ScaleWithScreenSize`. 씬에 구워진 캔버스는 ref 360×640, 코드로 만드는 패널 캔버스는 ref 1080×1920(같은 화면에서 배율이 3~4배 차이 난다) |
| `Canvas.pixelPerfect` | false |

1. **주 원인 — AA 래스터화.** 동적 폰트는 글리프를 그레이스케일 AA로 래스터화하므로 획 주변에 반투명 회색이 1~2px 퍼진다. 이 프로젝트의 다른 요소(배경·UI 프레임·아이콘)는 경계가 딱 떨어지는 픽셀아트라, 같은 화면에서 텍스트만 유독 흐려 보인다.
2. **부가 원인 — 비정수 캔버스 배율.** uGUI는 동적 폰트를 `fontSize × canvas.scaleFactor`(정수 px)로 굽고 표시 크기는 실수(예: 15 × 1.689 = 25.3px)라 미세한 리샘플이 얹힌다.

검증 과정에서 배제한 가설:
- **캔버스 배율만의 문제 아님** — 같은 화면 크기를 배율 1.0(fontSize 25)과 배율 1.689(fontSize 15)로 각각 그려 비교했으나 차이가 미미했다.
- **`Canvas.pixelPerfect`는 효과 미미** — 켜고 캡처 비교했으나 눈에 띄는 개선이 없었고, 애니메이션되는 UI(버튼 punch·패널 pop)에서 1px 흔들림 위험이 있어 켜지 않았다.
- **Best Fit 아님** — 프로젝트에서 거의 쓰지 않는다.

## 원인 B의 해결 — 언샤프 마스킹 + 글리프 알파 부스트 셰이더

`Assets/Shaders/UITextSharpen.shader`(`TaskbarHero/UI Text Sharpen`)는 `UI/Default`와 동일하게 동작하되 글리프 알파를 두 단계로 손본다. 폰트·글자 크기·레이아웃을 바꾸지 않으므로 UI 배치에 영향이 없고, 페이드(정점 색 알파)도 그대로 동작한다.

| 단계 | 파라미터(`UiTextStyle`) | 기본값 | 하는 일 |
|---|---|---|---|
| ① 언샤프 마스킹(공간 대비) | `SharpenAmount` | 1.6 | 글리프 알파를 **십자 이웃 4탭 평균과 비교**해 차이를 증폭한다. 이웃보다 밝은 픽셀(획의 심)은 더 밝게, 이웃보다 어두운 픽셀(획 바깥 halo)은 더 어둡게 → halo가 걷히고 경계가 또렷해진다. |
| | `SharpenRadius` | 0.7 | 이웃 샘플 거리(화면 픽셀). 폰트 아틀라스의 글리프 간 패딩을 넘어 옆 글자를 읽지 않도록 1 이하로 둔다. 거리는 `fwidth(uv)`로 잡으므로(=화면 1픽셀) 텍스트가 확대·축소돼도 선명화 폭이 일정하다. |
| | `InkFloor` | 0.35 | 잉크 보호 하한 — 획 쪽 픽셀의 알파를 원본의 이 비율 아래로 내리지 않는다. |
| ② 알파 배율 | `AlphaBoost` | 1.35 | 남은 알파를 이 배수로 올려 획을 조금 더 진하게(셰이더에는 `_SharpenHigh = 1/AlphaBoost`로 전달). |

`SharpenAmount = 0` + `AlphaBoost = 1`로 두면 원본 렌더링과 완전히 동일해진다.

`_MainTex_TexelSize`를 쓰지 않는 이유: uGUI `Text`는 폰트 텍스처를 머티리얼이 아니라 `CanvasRenderer`의 텍스처 오버라이드로 넘기므로 텍셀 크기가 채워지지 않을 수 있다.

### 왜 언샤프인가 — 알파 값만 보면 halo와 얇은 획을 구분할 수 없다

halo(획 바깥의 반투명 회색)와 작은 글자의 얇은 획은 **알파 값 범위가 겹친다**(둘 다 0.2~0.5). 그래서 알파 값만 보고 자르거나 올리는 방식으로는 둘 중 하나를 반드시 망친다 — 실제로 아래 두 번의 실패가 그것이다.

언샤프는 **주변 문맥**을 본다. 획의 심은 이웃보다 밝은 국소 최댓값이라 항상 밝아지는 쪽이고, halo는 이웃보다 어두워 깎이는 쪽이다. 값이 같아도 역할이 다르면 다르게 처리되므로 conflict가 사라진다.

`InkFloor`도 같은 이유로 **획 쪽 픽셀에만** 적용한다(이웃 대비 밝기 `ink/n`이 높을수록 강하게 보호). 하한을 모든 픽셀에 똑같이 걸면 halo까지 보호해 선명해지지 않는다 — 실측으로 확인했다(아래 표의 "하한 일괄 적용" 행).

측정값(래스터 9/11/14px 한글, 흰 글자·검정 배경. 중간톤 = 알파 0.10~0.55 = 흐릿한 halo, 불투명 = 알파 0.85 이상):

| 설정 | 중간톤 비율 | 불투명 비율 |
|---|---|---|
| 원본(`UI/Default`) | 0.356 | 0.194 |
| 알파 배율만 (언샤프 이전 상태) | 0.312 | 0.381 |
| 언샤프 + 하한 일괄 적용(`InkFloor` 0.6, 실패) | 0.293 | 0.474 |
| **언샤프 1.6 + 획만 보호(`InkFloor` 0.35) — 현재** | **0.224** | **0.547** |

즉 halo(중간톤)가 원본의 63%로 줄고 획의 심(불투명)은 2.8배가 됐다. `SharpenAmount`를 2.2까지 올려도 9px에서 획이 깨지지 않았으나 차이가 미미해 1.6으로 뒀다.

### ⚠ 하한 컷(`_SharpenLow > 0`)은 절대 쓰지 말 것

한때 알파를 `0.35~0.62` 구간으로 재매핑(= 0.35 미만을 투명 처리)했는데, **작은 글자가 읽을 수 없게 깨졌다.**

- 원인: 작은 글자에서 한글 얇은 획은 알파 커버리지가 0.2~0.4 수준이라 하한 컷에 그대로 지워진다. 9~11px에서 "인벤토리" → "인빈도리"처럼 획이 빠졌다.
- 왜 처음 검증에서 못 잡았나: 최초 A/B를 **배율 1.689 캔버스의 fontSize 11~15(래스터 18~25px)** 로만 했다. 실제 게임 패널 다수는 `1080×1920` 기준 캔버스라 **배율 0.563**으로 동작하고(`fontSize 24` → 래스터 **14px**), 이 작은 구간이 검증에서 빠져 있었다.
- 교훈: 텍스트 렌더링 변경은 **가장 작은 래스터 크기(9~15px)와 한글**로 먼저 검증한다. 캔버스 배율은 씬·패널마다 다르므로(0.563 / 1.0 / 1.689 혼재) `fontSize`가 아니라 `fontSize × canvas.scaleFactor`를 기준으로 본다.
- 선명도가 더 필요하면 하한을 올리지 말고 `SharpenAmount`를 올린다. 셰이더에서도 하한을 `0~0.2`로 clamp해 이중으로 막는다.

### 검증 방법 — 오프스크린 A/B 렌더

에디터에서 `RenderTexture` + `ScreenSpaceCamera` 캔버스(`ConstantPixelSize`라 `scaleFactor = 1` → `fontSize`가 곧 래스터 px)에 같은 한글 문구를 여러 설정으로 그려 놓고 PNG로 떠서 확대 비교하고, 픽셀 히스토그램으로 위 표의 중간톤·불투명 비율을 센다. 파라미터를 만질 때는 이 방식으로 **9px 한글**부터 확인한다(게임 화면 캡처는 이 크기 구간이 눈으로 잘 안 보인다).

### 함께 지키는 것 — 텍스트 rect 높이에 여유를 둔다

uGUI `Text`는 `verticalOverflow = Truncate`일 때 줄 높이가 rect 높이를 넘으면 그 줄을 **부분 잘림이 아니라 통째로 렌더링하지 않는다**(글자가 사라진다). rect 높이를 글자 크기에 딱 맞춰 둔 곳(예: 로그인 패널 `InputField` — fontSize 16 / rect 높이 18 / 필요 높이 17.8)은 폰트나 글자 크기가 조금만 바뀌어도 빈칸이 된다.

`UiTextStyle`이 **한 줄조차 안 들어가는 경우에만** `Overflow`로 바꿔 살짝 넘치더라도 보이게 구제하지만(여러 줄을 의도적으로 잘라내는 텍스트는 Truncate 유지), 새 UI는 처음부터 2~3px 여유를 두고 만든다.

## 적용 방식 — 중앙 자동 스캔

`Assets/Scripts/Managers/UiTextStyle.cs`가 담당한다.

- 텍스트가 40여 곳의 컨트롤러에서 런타임 생성되므로, 생성 지점마다 배선하지 않고 **중앙에서 자동 적용**한다 — 플레이 시작(`RuntimeInitializeOnLoadMethod`) · 씬 로드 직후 · 이후 0.4초 주기 스캔(`Canvas.willRenderCanvases`).
- **호출부가 커스텀 머티리얼을 직접 지정했다면 건드리지 않는다**(외곽선·마스크 등 의도된 머티리얼 존중).
- 즉시 적용이 필요하면 `UiTextStyle.Apply(text)`를 호출한다. 런타임 생성 패널은 최대 0.4초 뒤 스캔에서 잡힌다.
- 셰이더는 코드에서만 참조하므로 **Project Settings > Graphics > Always Included Shaders에 등록**되어 있어야 빌드에 포함된다. 이 등록은 에디터 설정 저장 과정에서 유실될 수 있어 `Assets/Editor/UiTextShaderRegistrar.cs`가 에디터 로드 시마다 확인해 자동으로 다시 넣는다(수동: 메뉴 `TaskbarHero/UI/텍스트 셰이더 Always Included 등록 확인`).

## 쉬운 설명

위 내용을 용어 없이 다시 정리한 것이다. 세부 수치·근거는 앞 절들을 본다.

### 무슨 문제였나

게임 화면의 **글자가 흐릿하게** 보였다. 배경이나 아이콘 같은 그림은 또렷한데 글자만 뿌옇게 번져 보이는 상태다.

### 원인이 두 가지였고, 성격이 완전히 다르다

**원인 A — 화면 전체를 작게 그린 뒤 늘려서 보여주고 있었다.**

작은 사진을 크게 확대하면 뿌옇게 되는 것과 같다. 에디터의 Game 뷰에 "저해상도로 렌더링" 옵션이 켜져 있어서, 게임을 실제 창보다 작게 그린 다음 창 크기로 늘리고 있었다. 이러면 **글자든 그림이든 전부** 흐려진다.

이 경우 글자에 실제로 쓰이는 점(픽셀)의 개수 자체가 줄어든다. 원래 25개 점으로 그릴 글자를 17개 점으로 그린 뒤 늘리는 셈이라, **아무리 후처리를 해도 되살릴 수 없다.** 그래서 "글자가 흐리다"는 말을 들으면 **이것부터 확인**한다. 지금은 에디터를 켤 때마다 자동으로 이 옵션을 꺼 주고 있다.

**원인 B — 폰트 자체가 경계를 부드럽게 그린다.**

지금 쓰는 글꼴은 획의 가장자리를 **연필로 그은 것처럼** 부드럽게 흐려서 그린다(계단처럼 보이지 않게 하려는 일반적인 방식이다). 그런데 이 게임의 다른 그림은 전부 픽셀아트라 경계가 **도장 찍은 것처럼** 딱 떨어진다. 그래서 같은 화면에서 글자만 유독 흐려 보였다.

### 어떻게 고쳤나 (원인 B)

글자를 그릴 때 **주변과 비교해서 진하게/연하게를 강조**하는 처리를 넣었다.

- 획의 한가운데처럼 **주변보다 진한** 곳 → 더 진하게
- 획 바깥에 번진 회색처럼 **주변보다 연한** 곳 → 더 연하게

이러면 번진 부분이 걷히고 획의 윤곽이 또렷해진다. 글꼴이나 글자 크기, 배치는 전혀 건드리지 않으므로 화면 구성이 달라지지 않는다.

**왜 "주변과 비교"하는 방식이어야 했나.** 번진 회색과 작은 글자의 가는 획은 **진하기가 비슷하다.** 그래서 "연한 건 지운다"는 식으로 진하기만 보고 처리하면, 번진 부분을 지우려다 **가는 획까지 같이 지워진다.** 실제로 그렇게 만들었다가 작은 글자에서 "인벤토리"가 "인빈도리"처럼 획이 빠지는 사고가 났다. 반면 주변과 비교하면 진하기가 같아도 역할(획의 심 / 번진 자국)을 구분할 수 있다.

### 앞으로 이 부분을 만질 때 지킬 것

- **"연한 건 지운다" 방식은 절대 넣지 않는다.** 작은 글자의 획이 사라진다. 더 선명하게 하고 싶으면 강조 강도(`SharpenAmount`)를 올린다.
- **가장 작은 글자와 한글로 먼저 확인한다.** 화면마다 UI 배율이 달라서 같은 글자 크기라도 실제 그려지는 크기가 3배까지 차이 난다. 큰 글자만 보고 판단하면 작은 글자가 깨진 걸 놓친다.
- **글자 칸 높이는 딱 맞추지 말고 2~3px 여유를 둔다.** 칸이 글자보다 조금이라도 작으면 그 줄이 **일부만 잘리는 게 아니라 통째로 안 보인다.**
- 새 글자를 만들 때 **따로 할 일은 없다.** 선명화는 전체 화면을 주기적으로 훑어 자동 적용된다.
