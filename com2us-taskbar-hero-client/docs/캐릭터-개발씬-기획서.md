# CharacterDevScene(몬스터 유닛 자동생성) 기획서

## 1. 개요

**목적** — 몬스터 **외형 프리팹(`monster_{code}.prefab`)과 능력치(`monster_master` 행)를 한 화면에서 함께 만드는 것**이다. 지금은 외형을 SPUM 편집 씬에서 손으로 조합하고, 능력치는 서버 마스터 데이터 문서를 열어 따로 정하는 두 갈래 작업이다. 외형은 SPUM의 태그 자동 조합으로 생성하고, 능력치는 **역할별 통일 기준값을 버튼으로 채우고, "몇 지역 몇 스테이지에 낼 몬스터인가"를 고르면 그 자리의 등장 레벨이 추천되도록** 해서 한 몬스터를 한 번에 완성한다. 현재 12종은 `Assets/Thirdparty/SPUM2/Scene/SPUM_Scene.unity`에서 파츠를 일일이 골라 만든 결과물이라, 몬스터가 늘어날 때마다 같은 수작업이 반복되고 계열(스켈레톤·데몬 등)의 외형 일관성도 사람 손에 달려 있다. SPUM이 갖고 있는 **태그 기반 자동 조합**과 **프리팹 저장**에서 자동생성에 필요한 부분만 뽑아 프로젝트 코드로 재구현하고(§2.2 — SPUM 편집 씬은 쓰지 않는다), `monster_master`의 몬스터 코드 목록으로부터 프리팹을 일괄 생성·검수하는 전용 개발 씬을 만든다.

**대상** — Unity 클라이언트 전용(에디터 도구·개발 하네스 씬). 서버(AccountServer·GameServer)·`TaskbarHero.Common` 코드 변경 **없음**. 신규 API·DB 테이블·에러 코드 **없음**(그래서 이 기획서에는 API·데이터베이스·에러 코드 절이 없다). 단 능력치는 **서버 마스터 데이터(`monster_master`)의 값**이므로, 이 씬은 값을 **만들어 제안·로컬 반영**까지만 하고 정본 반영은 서버측이 맡는다(§7.4).

**적용 범위** — **이번 범위는 몬스터 유닛만**이다. 아군 캐릭터(직업×성별 8종) 생성은 **다음 단계로 예정**되어 있으므로, 파이프라인을 "유닛 종류"에 대해 일반화해 두고 몬스터 구현만 채운다 — 이번에는 저장 후 **후처리 훅의 시그니처만** 확정하고 아군용 구현·레시피는 다음 단계로 미룬다(§3 N2).

**관련 문서** — [클라이언트 씬 / 오브젝트 / UI 구성](클라이언트-씬-UI-구성.md) · [투명 오버레이 창](투명-오버레이-창.md)(전투 화면 규격) · 상위 저장소 `CLAUDE.md`의 「AnimDevScene」·「던전 전투 배선」·「새 씬을 추가하면 …」 규칙.

## 2. 현재 자산 파악 (이 기획의 전제)

### 2.1 SPUM 편집 씬이 이미 제공하는 기능

`SPUM_Scene.unity`의 루트 오브젝트는 `SPUM_Manager` · `SPUM_UIManager` · `SPUM_AnimationManager` · `SPUM_PaginationManager` · `SPUM_PromptTagManager`(타입은 `SPUM_ImprovedTagManager`) · `SPUM_ShareCodeImporter`다. 자동생성에 쓸 수 있는 것은 다음 셋이다.

| 기능 | 담당 | 핵심 API |
|---|---|---|
| **태그 기반 파츠 자동 조합** | `SPUM_ImprovedTagManager` | `GenerateRandomCharacter()`(public) → `ConvertToPreviewMatchingElements()`(**private**) → `SPUM_Manager.SetSprite(elements)`. 씬 버튼 `generateCharacterButton`이 `ApplyGeneratedCharacterToManager()`(private)에 연결돼 있다 |
| **프리뷰에 파츠 적용** | `SPUM_Manager` | `SetSprite(List<PreviewMatchingElement>)` · `ItemResetAll()` · `SetType(unitType)` · `ItemRandomAll()`(태그 무시 완전 랜덤) |
| **프리팹 저장** | `SPUM_Manager.SavePrefabs()` → `IPrefabFileHandler.Save()` | 프리뷰 복제 → 비활성 파츠 제거 → `UnitType`별 Animator 배선 → `PopulateAnimationLists()` → `unitPath + UIManager._unitCode.text + ".prefab"` 저장 |

**그런데 이 API들은 SPUM 편집 UI 계층이 살아 있어야만 동작한다** — 실측 근거는 셋이다.

- `SetSprite()`는 씬의 `SPUM_SpriteButtonST`(UIManager가 만드는 파츠 버튼)를 찾아 `ignoreColorPart`를 읽고, 마지막에 `UIManager.DrawItemOff()`를 부른다(`SPUM_Manager.cs:381~391`).
- `SavePrefabs()`는 파일명을 `UIManager._unitCode.text`에서 읽고 `ToastOn`·`ResetUniqueID`·`ShowNowUnitNumber`를 부른다(`SPUM_Manager.cs:772~791`).
- 태그 필터의 선택 상태는 데이터가 아니라 **UI Toggle**이다 — `GenerateRandomCharacter()`가 `GetSelectedToggleValues(...)`로 토글의 `isOn`을 읽는다(`SPUM_ImprovedTagManager.cs:1027`).

→ 즉 이 경로를 쓰려면 **SPUM_Scene을 통째로 얹어야** 하고, 그러면 하네스가 편집 UI·페이지네이션·프리셋 계층에 종속된다.

### 2.2 채택: SPUM_Scene을 쓰지 않고 필요한 기능만 추출한다

**이 씬은 `SPUM_Scene`을 재활용하지 않는다.** 자동생성에 필요한 네 가지만 뽑아 `SpumUnitComposer`(`Assets/Scripts/Spum/SpumUnitComposer.cs`)로 재구현했고, 화면에는 **캐릭터(프리뷰 유닛) 하나만** 뜬다. SPUM 서드파티 코드는 여전히 고치지 않으며(N4), 데이터 타입과 프리팹 에셋을 **읽기만** 한다.

| 뽑아 쓴 것 | 출처 | 재구현한 절차 |
|---|---|---|
| 태그 DB(파츠) | `SPUM_PromptTagManager.prefab`의 `allCharacterData` — 프리팹 에셋의 직렬화 값을 **인스턴스화 없이** 읽는다(그 컴포넌트의 `Awake`/`Start`가 돌지 않는다) | 태그 AND 필터 + 파트별 시드 랜덤 선택(무기 방패 50%·듀얼 70% 규칙 포함) · 파트별 목록 제공(F14) |
| 패키지(텍스처·클립 인덱스) | `Resources`의 `*Index*` JSON | `SPUM_Manager.LoadPackages()`와 같은 파싱 + 생성일 정렬 |
| 애니메이터 컨트롤러 | `SPUM_Manager.prefab`의 유닛 타입별 컨트롤러(+ `_version`) | 저장 시 `_anim`에 배선 |
| 프리뷰 유닛 | `SpritePrefab.prefab`(루트 `SPUM_Prefabs` + `UnitRoot`/`HorseRoot`) | `SetSprite` 대체(파츠별 `SPUM_MatchingList` 순회) · `IPrefabFileHandler.Save` 대체(복제 → 비활성 자식 제거 → Animator·패키지 동기화 → `PopulateAnimationLists`) |

**태그 DB는 설치된 패키지에 맞춰 걸러 쓴다** — 태그 DB에는 SPUM이 파는 애드온 전체(652개)가 들어 있지만 이 프로젝트에 설치된 패키지는 3개(Legacy·Ver121·Ver300, 텍스처 429개)뿐이라, 설치되지 않은 파츠를 고르면 스프라이트가 없어 몸통이 통째로 비어 버린다(실측: Body `Zombie_3` → 요소 0개). 그래서 **패키지에 텍스처가 실재하는 항목만 남긴다(652 → 215개)**. SPUM 원본은 이 경우 경고만 남기고 빈 파츠를 만든다.

**재현성(F6)은 그대로 성립한다** — 조합은 `UnityEngine.Random`만 쓰므로 조합 **직전에** `Random.InitState(seed)`를 호출하면 같은 시드가 같은 결과를 낸다(실측 확인). 그래서 그 사이에 다른 난수 소비를 끼워 넣지 않는다.

**쓸 수 있는 태그 축**(실측) — `allCharacterData` 652개가 들고 있는 값은 다음과 같다.

| 축 | 값 |
|---|---|
| `Part`(10) | Armor, Back, Body, Cloth, Eye, FaceHair, Hair, Helmet, Pant, Weapons |
| `Race`(6) | human, **undead**, **devil**, orc, elf, highelf |
| `Gender`(2) | male, female |
| `Theme`(2) | fantasy, modern |
| `Class`(8) | melee, ranged, magical, tank, damage, support, healing, physical |

이 축이 이 프로젝트의 몬스터 구성과 잘 맞는다는 점이 태그 방식을 채택하는 근거다 — 스켈레톤 계열(9101·9102·9199)은 `undead`, 데몬 계열(9201·9299)은 `devil`, 나머지는 `human` + `Class` 조합으로 표현된다. 다만 **설치된 패키지에 몸통이 있는 종족은 human·orc·undead·elf·devil 다섯**뿐이라 `highelf`는 쓸 수 없다(9399는 `elf`로 잡았다).

보조 수단으로 **`SPUM_ShareCodeImporter`** 가 있다(공유 코드/JSON → `equipment`·`colors`·`directions`·`masks` → `PreviewMatchingElement` 목록). 태그로 표현하기 어려운 개체(보스 등)를 손으로 만들고 그 결과를 코드로 고정하는 데 쓸 수 있다 — 레시피에 `shareCode` 자리만 예약해 두고 구현은 필요해질 때 한다(§4.1).

### 2.3 이 프로젝트의 몬스터 프리팹 규격 (자동생성이 만족해야 하는 것)

실측 결과 **몬스터 프리팹은 순수 SPUM 유닛**이다. `monster_9001`·`monster_9099`의 루트는 `RectTransform` + `SPUM_Prefabs` 둘뿐이고, layer는 `UI`, 자식은 `UnitRoot` 하나다(`_code`는 `SPUM_20240911…`, `_version` 170, `spumPackages` 3, 클립 IDLE 1·MOVE 1·ATTACK 6·DAMAGED 1·DEATH 1·OTHER 3).

전투에 필요한 나머지는 **전부 런타임에 붙는다**(`BattleDevController.SpawnMonsterByCode`).

- `EnsureSpumAnimator(go)` — `SpumCharacterAnimator`를 타입명으로 부착
- `SetUnitSortingOrder(go, EnemySortingOrder)` — 자식 `SortingGroup`의 순서를 덮어씀(프리팹의 구운 값을 고칠 필요 없음)
- `SetFacingRight(go, false)` · `AddComponent<MonsterUnit>()` + `mu.Init(name, hp, atk, …)` · 보스면 3배 크기·왕관·경고 연출
- 스탯·이름은 프리팹이 아니라 `monster_master`에서 온다

→ **자동생성의 산출물 요구사항은 "정상적으로 동작하는 SPUM 유닛 프리팹 + `monster_{code}` 파일명" 하나로 좁혀진다.** 구체적으로 다음 셋을 만족해야 한다.

1. 루트에 `SPUM_Prefabs`가 있고 `_anim`(자식 Animator)이 배선되어 있다 — `SpumCharacterAnimator.Init`이 `_spum._anim == null`이면 아무것도 하지 않는다.
2. 상태별 클립 리스트가 비어 있지 않다 — 비면 `PopulateAnimationLists()`가 `spumPackages`와 Resources 클립 경로로 다시 채우므로, `spumPackages`가 실제 사용 파츠를 담고 있어야 한다(`SavePrefabs()`가 `SyncPackagesWithImageElement`로 정리한다).
3. 자식에 `SortingGroup`이 있다(SPUM 저장물의 기본 구성).

### 2.4 프리팹이 전투에 연결되는 경로

`monster_master.json`(12종: 9001·9002·9099·9101·9102·9199·9201·9299·9301·9399·9401·9499, 필드 `monsterCode`·`name`·`hp`·`attack`)의 각 코드와 `Assets/Prefabs/Character/Monster/monster_{code}.prefab`이 1:1이다. 에디터 메뉴 **`TaskbarHero/UI/던전 전투 배선`**(`DungeonBattleBuilder`)이 그 폴더를 `monster_*.prefab` 패턴으로 스캔해 `DungeonBattleFlow`의 코드→프리팹 맵을 채운다. 따라서 **프리팹을 새로 만들거나 추가하면 이 빌더를 다시 실행해야 전투에 반영된다.**

### 2.5 스테이지 구성과 몬스터 능력치 (등장 레벨 추천의 근거)

**스테이지 구조** — `stage_master.json` **100행** = **5 Act(지역) × 2 난이도 × 10 스테이지**. 필드는 `stageId`·`act`·`difficulty`·`stage`·`spawns[{monsterCode,count}]`·`bossMonsterCode`·`backgroundType`이고, `stageId = act×1000000 + difficulty×10000 + stage`(예: `1010001` = Act1·난이도1·스테이지1)다. **스테이지 1~9는 일반, 스테이지 10은 보스**(`bossMonsterCode ≠ 0`)다. 진행 순서는 난이도-바깥이라 `sequence = (difficulty-1)×50 + (act-1)×10 + stage`(1~100)로 표현된다([서버 스테이지·전투 기획서](../../docs/세부/stage-battle-기획서.md)).

**몬스터 코드 규약** — Act1 `90xx` · Act2 `91xx` · Act3 `92xx` · Act4 `93xx` · Act5 `94xx`, 각 Act의 보스는 그 대역의 `xx99`(`9099`·`9199`·`9299`·`9399`·`9499`). 즉 **"지역 + 일반/보스"가 코드에 이미 담겨 있다** — 지역·스테이지 선택 UI가 코드 채번과 자연스럽게 연결된다.

**현행 능력치(12종)** — `monster_master`의 `hp`·`attack`은 **레벨 1 기준값**이고, 서버 리밸런싱 이후 **종류가 아니라 역할로만 갈린다**. 12종 전부 `hp` **50**이며 `attack`은 일반 **5** · 보스 **1**뿐이다(정본: [`master-data-값.md`](../../docs/세부/master-data/master-data-값.md) §9).

| 역할 | 대상 | hp | attack |
|---|---|---|---|
| 일반 | 9001·9002·9101·9102·9201·9301·9401 (7종) | 50 | 5 |
| 보스 | 9099·9199·9299·9399·9499 (5종) | 50 | 1 |

**세기는 몬스터가 아니라 등장 자리의 레벨이 만든다.** 난이도를 정하는 것은 `stage_spawn.monster_level`이고(같은 문서 §11-B), 실제 전투 스탯은 기준값에 **레벨 배율**(§9.4 — hp `×1.25^(L-1)` · attack `×1.18^(L-1)`)을 곱해 **클라이언트가** 산출한다(`Assets/Scripts/MasterData/MonsterStats.cs`). 그래서 같은 레벨이면 어느 몬스터든 체력이 같고, **새 몬스터를 추가할 때 고를 값은 `hp`·`attack`이 아니라 "그 자리에 몇 레벨로 낼 것인가"** 다.

**레벨 곡선(정본 §11-B)** — 지역 안에서 3스테이지마다 +1, 지역이 바뀌면 +3~4다.

| act | s1~3 | s4~6 | s7~10 | 보스 |
|---|---|---|---|---|
| 1 | 약 1 / 강 2 | 약 2 / 강 3 | 약 3 / 강 4 | 14 |
| 2 | 약 8 / 강 9 | 약 9 / 강 10 | 약 10 / 강 11 | 24 |
| 3 | 15 | 16 | 17 | 28 |
| 4 | 19 | 20 | 21 | 31 |
| 5 | 24 | 25 | 26 | 34 |

**여기서 읽히는 규칙** — ① **Act1·2는 일반 몬스터가 2종**이라 강몹이 약몹보다 **+1 레벨**이다(체력 ×1.25 · 공격 ×1.18). Act3~5에는 그 구분이 없다 ② **보스는 그 지역 잡몹보다 8~13 위**이며, 보스가 오래 버티는 것은 `attack`이 아니라 레벨(=체력)이 만든다 — 그래서 보스의 기준 `attack`은 같은 레벨 일반의 1/5인 1이다 ③ **난이도(1·2)는 몬스터도 레벨도 바꾸지 않는다** — 난이도 2는 스폰 구성이 난이도 1과 같고 보상만 상향된다. 즉 **난이도는 능력치 축이 아니다**(§8 M8).

### 2.6 참고할 하네스 씬 선례

- **AnimDevScene** — 카메라·EventSystem·캐릭터 프리팹 1개·`AnimDevController`만 있는 최소 구성. 씬은 `Assets/Editor/AnimDevSceneBuilder.cs`가 메뉴로 생성하고, 컨트롤러는 **`Assets/Scripts/Spum/`(Assembly-CSharp)** 에 둔다 — `SPUM_Prefabs`가 Assembly-CSharp에 있어 asmdef 어셈블리에서는 직접 열거할 수 없기 때문이다. **CharacterDevScene도 같은 제약을 받는다.**
- 캐릭터 프리팹 루트는 `RectTransform`이라, 월드에 놓을 때 `position`이 아니라 **앵커·`anchoredPosition`을 중립화해서** 배치해야 한다(`AnimDevSceneBuilder.PlaceCharacter`의 경위 주석 참조).

| F4 | 목록 전체를 순회하는 **일괄 생성**을 실행할 수 있다(대상 필터: 전체 / 프리팹 없는 코드만) |
| F5 | 생성 결과를 그 자리에서 **애니메이션으로 검수**할 수 있다(IDLE·MOVE·ATTACK·DAMAGED·DEATH 재생) |
| F6 | 같은 입력(레시피 + 시드)이면 **항상 같은 결과**가 나온다(재현성) |
| F7 | 기존 프리팹을 덮어쓸 때는 **백업 후 교체**한다 |
| F8 | 생성 후 `던전 전투 배선` 빌더를 다시 실행해야 함을 **씬에서 안내**한다(또는 버튼으로 실행) |

| F10 | **지역(Act 1~5) · 스테이지(1~10) · 약몹/강몹**을 고르면 그 자리의 **등장 레벨이 추천되고**, 그 레벨에서의 실제 전투 스탯이 함께 표시된다. `hp`·`attack` 입력란은 버튼 한 번으로 **역할별 통일 기준값**(일반 50/5 · 보스 50/1)이 채워진다 |
| F11 | 스테이지 10을 고르면 **보스 기준**(기준값 50/1 + 그 Act의 보스 레벨)이 적용되고, 코드 채번도 그 Act의 `xx99`를 제안한다(§2.5 코드 규약) |

| F14 | **파트별로 외형을 직접 고를 수 있다** — 파트(Body·Eye·Hair·FaceHair·Cloth·Pant·Armor·Helmet·Weapons·Back)를 고르면 그 파트에서 쓸 수 있는 파츠 목록이 나오고, 누르면 **그 파트만** 즉시 바뀐다. 파트 비우기도 된다(투구·망토처럼 없어도 되는 파트) |

## 4. 데이터 모델

몬스터 한 종은 **외형(프리팹)** 과 **능력치(`monster_master` 행)** 두 축으로 이뤄진다. 4.1~4.2가 외형, 4.3~4.5가 능력치다.

### 4.1 외형 결정: 태그 레시피를 정본으로, 시드 랜덤을 폴백으로

외형 결정 방식은 세 가지가 가능했다.

| 방식 | 채택 | 이유 |
|---|---|---|
| **태그 레시피 테이블** | ✅ 정본 | `undead`/`devil` 같은 축이 몬스터 계열과 맞아 의도를 담을 수 있고, 같은 입력이면 결과가 같아 재현된다(F6) |
| **코드 시드 랜덤** | ✅ 폴백 | 레시피가 없는 신규 코드도 즉시 채울 수 있다. 단 의도는 담기지 않아 "일단 채우고 나중에 레시피로 확정"용 |
| SPUM 공유 코드 임포트 | ⏸ 자리만 예약 | 재현성은 좋지만 외형을 결국 손으로 만들어야 해 자동화 목적과 어긋난다. 레시피 스키마에 `shareCode` 필드 자리만 두고(있으면 태그 조합을 건너뛰고 이 코드로 복원), **구현은 "태그로 외형이 안 나오는 개체"가 실제로 나왔을 때** 한다 |

### 4.2 외형 레시피 스키마

레시피는 **에디터·개발 씬만 읽는 데이터**이므로 `Resources`에 두지 않고(빌드에 항상 포함되므로) TextAsset을 컨트롤러의 `[SerializeField]`에 배선한다 — 프로젝트의 "프리팹·데이터는 Resources 대신 직접 배선" 규칙과 같은 이유다.

**위치**: `Assets/Dev/monster-appearance-recipe.json` (개발 전용 폴더, 빌드 미포함)

```jsonc
{
  "version": 1,
  "recipes": [
    {
      "monsterCode": 9101,          // monster_master의 코드. 이 값이 프리팹 파일명(monster_9101)을 결정한다
      "note": "스켈레톤 병사",       // 사람이 읽는 메모(생성에 영향 없음)
      "race": "undead",             // Race 태그 1개
      "gender": "male",             // Gender 태그(생략 시 무제한)
      "theme": "fantasy",           // Theme 태그(생략 시 무제한)
      "classes": ["melee", "physical"], // Class 태그(복수 = AND 필터)
      "seed": 9101,                 // 파츠 선택 난수 시드(생략 시 monsterCode)
      "fixedParts": {               // 태그 조합을 덮어쓰는 고정 파츠(선택). 키 = Part, 값 = SPUM 파일명
        "Weapons": "Sword_1"        // 무기 2개는 SPUM 규약대로 콤마 구분: "Sword_1,Shield_2"
      },
      "colors": {                   // 계열 팔레트(선택). Body·Hair·Cloth 3키만 쓴다. 미지정은 SPUM 기본
        "Body": "#8FB7A8"
      },
      "effectColor": "#4DE07A",     // 무기 스윙 이펙트(궤적·불티) 기준색(선택). 생략 시 보스는 지역 색, 일반은 기본 불티색(§4.6)
      "shareCode": null             // 예약 필드. 값이 있으면 태그 조합을 건너뛰고 이 코드로 복원(§4.1)
    }
  ]
}
```

- `monsterCode`만 필수. 나머지가 비면 그 축은 "무제한"으로 두고 시드 랜덤이 고른다.
- **`fixedParts`의 값은 SPUM 파일명**이다(`ImprovedCharacterDataItem.FileName` = `SpumTextureData.Name`). SPUM 내부도 파일명 + `PartType` + `UnitType`으로 텍스처를 찾으므로(`SPUM_ImprovedTagManager.cs:2462`) 같은 키로 맞물리고, 전체 경로(`ItemPath`)와 달리 SPUM 폴더 구조가 바뀌어도 깨지지 않는다. 태그 DB(`allCharacterData`)에 없는 파일명은 **생성 전 검증에서 실패로 보고**한다(§6.4).
- 레시피에 없는 코드는 `seed = monsterCode`인 **전 축 무제한 랜덤**으로 생성한다(F4의 "프리팹 없는 코드만" 대상과 조합해 신규 몬스터를 즉시 채울 수 있다).
- **`Style` 축은 쓰지 않는다** — 태그 DB 실측에서 확인된 축은 `Part`·`Race`·`Gender`·`Theme`·`Class`뿐이고 `Style`은 `SPUM_Custom_Styles.json`·`SPUM_Style_Elements.json`에 의존한다. 같은 이유로 **`enableStyleFilterFallback`은 꺼 둔다**(기본값 `false`) — 이 옵션은 "필터 결과가 0개면 조건을 몰래 빼고 재검색"하는 동작이라, 왜 그 파츠가 나왔는지 추적할 수 없어 레시피가 의도를 담는다는 전제(F6)와 어긋난다. 결과가 0개면 **실패로 보고**한다(§6.4). 필요해지면 스키마 `version`을 올려 `style` 배열을 추가한다.
- **색은 계열 일관성이 필요한 3키(`Body`·`Hair`·`Cloth`)에만 준다** — 색은 태그로 통제되지 않는 유일한 계열 레버(스켈레톤=탈색 톤 등)지만, 전 파트를 지정하면 레시피 유지비가 급격히 는다. 나머지는 SPUM 기본에 맡긴다.
- 12종에 대한 초기 레시피(계열이 명확한 것만 채우고 나머지는 랜덤). **이 12종은 프리팹을 재생성하지 않는다**(N3) — 레시피는 채워 두되, "레시피로 만든 미리보기 vs 기존 프리팹"의 육안 비교를 **도구 품질 지표**로 쓴다:

| 코드 | 이름 | race | classes |
|---|---|---|---|
| 9001 | 빙의된 병사 | human | melee, physical |
| 9002 | 빙의된 암살자 | human | melee, damage |
| 9099 | 암흑 마법사 (Act1 보스) | human | magical, damage |
| 9101 | 스켈레톤 병사 | undead | melee, physical |
| 9102 | 스켈레톤 기사 | undead | melee, tank |
| 9199 | 스켈레톤 군주 (Act2 보스) | undead | tank, magical |
| 9201 | 데몬 | devil | melee, damage |
| 9299 | 마왕 (Act3 보스) | devil | magical, damage |
| 9301 | 타락한 성기사 | human | tank, melee |
| 9399 | 몰락한 대천사 (Act4 보스) | highelf | magical, support |
| 9401 | 공허의 추적자 | devil | ranged, damage |
| 9499 | (Act5 보스) | devil | magical, tank |

> 보스(코드 x099·x199·x299·x399·x499)는 전투에서 **3배 크기·왕관**이 런타임에 적용되므로, 레시피에서 크기를 다루지 않는다.

> **무기 파츠가 없으면 스윙 이펙트도 없다.** 몬스터가 무기를 휘두를 때 나오는 궤적·불티(`MonsterWeaponSwingFx`)는
> `R_Weapon` 스프라이트를 기준으로 그리므로, 태그 조합 결과에 `Weapons`가 없으면 연출이 통째로 빠진다.
> `devil` + `ranged`(9401)·`devil` + `magical`(9499) 조합이 실제로 그랬고, `fixedParts.Weapons`로
> 각각 `Spear_1`·`AxeLong1`을 고정해 해결했다. 새 몬스터를 만들 때 무기 칸이 비면 같은 방식으로 지정한다.

### 4.3 능력치 결정: 통일 기준값 + 지역·스테이지 등장 레벨 추천

**`monster_master`에 넣는 `hp`·`attack`은 고를 값이 아니다.** 역할별 통일 기준값(일반 50/5 · 보스 50/1)이 정해져 있고(§2.5), 몬스터의 세기는 `stage_spawn.monster_level`이 만든다. 그래서 씬이 추천하는 것은 능력치가 아니라 **그 자리의 등장 레벨**이다.

| 경로 | 동작 |
|---|---|
| **직접 입력** (F9) | `name`·`hp`·`attack`을 그대로 입력한다. 기준값을 벗어난 값도 넣을 수는 있으나(원작 수치 이식 등) **권장하지 않는다** — 아래 경고를 보라 |
| **통일 기준값 채우기** (F10) | `[통일 기준값 채우기]` 버튼이 그 자리의 역할(일반/보스)에 맞는 기준값을 입력란에 넣는다 |
| **등장 레벨 추천** (F10·F11) | **Act(1~5) + 스테이지(1~10) + 약몹/강몹**을 고르면 §4.4의 곡선으로 **등장 레벨**이 추천되고, 그 레벨에서의 실제 전투 스탯(`hp`/`attack`)이 함께 표시된다 |

**기준값을 벗어나면 경고한다** — 입력한 `hp`·`attack`이 통일 기준값과 다르면 진단 줄이 노란색으로 바뀌고, `monster_master` 반영 시에도 로그로 알린다. 값 자체를 막지는 않지만(사람이 판단할 여지를 남긴다), 기준값을 깨면 **`monster_level`이 아무 일도 하지 않게 되고 같은 레벨의 몬스터끼리 능력치가 수천 배 차이 나는** 상태로 되돌아간다(값 문서 §9의 경위).

**약몹/강몹 축은 Act1·2에서만 의미가 있다** — 그 두 지역만 일반 몬스터가 2종이고 강몹이 +1 레벨이기 때문이다(§2.5). Act3~5와 보스 자리에서는 선택이 레벨을 바꾸지 않으므로 씬도 그 표시를 흐리게 둔다. 마스터 데이터에 약/강 컬럼은 없으므로, 몬스터를 고를 때의 초기값만 코드 관례(그 대역의 2번째 일반 코드부터 강몹)로 잡고 나머지는 사람이 토글한다.

**난이도(1·2)는 축이 아니다** — 난이도 2는 스폰 구성이 난이도 1과 같고 보상만 상향되므로 몬스터도 레벨도 달라지지 않는다(§2.5). 옛 `difficultyMultiplier` 파라미터 자리는 **제거했다**(§8 M8).

**이름은 직접 입력이 원칙이다**(F9). 자동 생성은 하지 않는다 — 이름은 세계관 텍스트라 규칙 조합이 어색해진다. 대신 레시피의 `race`에 맞춘 **후보 목록을 드롭다운으로 제시**하고(예: `undead` → 스켈레톤·구울·리치·본나이트), 고르면 입력란을 채우기만 한다. 후보는 손으로 관리하는 목록이며 생성 결과에 영향을 주지 않는다.

### 4.4 추천 등장 레벨 산출식

**산식의 정본은 서버 도구 [`tools/master_monster_tool.py`](../../tools/master_monster_tool.py)** 의 `BASE_HP`·`BASE_ATTACK`·`SPAWN_LEVEL`·`STRONG_LEVEL_GAP`·`BOSS_LEVEL`·`spawn_level()`·`stats_at()`·`recommend()`이며, 씬(`MonsterStatCurve`)은 그것을 **그대로 옮긴 것**이다. 한쪽만 고치면 씬 추천이 정본과 갈라지므로 함께 고친다.

**① 기준값 — 고르지 않는다**

```
hp     = 50            # 일반·보스 공통
attack = 5 (일반) / 1 (보스)
```

**② 등장 레벨 — 이것이 고르는 값이다**

```
band(s)  = 0 (s1~3) · 1 (s4~6) · 2 (s7~10)
레벨      = 보스면 BOSS_LEVEL[act]
           아니면 SPAWN_LEVEL[act][band(s)] + (강몹이고 act ≤ 2 이면 +1)
```

| act | s1~3 | s4~6 | s7~10 | 보스 |
|---|---|---|---|---|
| 1 | 1 | 2 | 3 | **14** |
| 2 | 8 | 9 | 10 | **24** |
| 3 | 15 | 16 | 17 | **28** |
| 4 | 19 | 20 | 21 | **31** |
| 5 | 24 | 25 | 26 | **34** |

(Act1·2의 강몹은 위 값 +1. 보스는 스테이지와 무관하게 그 Act의 보스 레벨이다.)

**③ 그 레벨의 실제 전투 스탯 — 읽기 전용 결과**

```
hp     = max(1, round(50 × 1.25^(레벨-1)))
attack = max(1, round(기준 attack × 1.18^(레벨-1)))
```

**배율을 씬에서 다시 정의하지 않는다** — 전투가 실제로 쓰는 [`MonsterStats.Scale`](../Assets/Scripts/MasterData/MonsterStats.cs)를 그대로 호출한다. 그래야 씬이 보여 주는 숫자가 게임 안 값과 어긋나지 않는다(정본: 값 문서 §9.4, 시뮬레이터 `tools/balance_sim.py`도 같은 상수를 쓴다).

| Act·자리 | 추천 레벨 | 실제 hp | 실제 attack |
|---|---|---|---|
| Act1 s1 약몹 | 1 | 50 | 5 |
| Act1 s7 강몹 | 4 | 98 | 8 |
| Act1 s10 보스 | **14** | **909** | **9** |
| Act2 s5 약몹 | 9 | 298 | 19 |
| Act3 s7 | **17** | **1776** | **71** |
| Act5 s10 보스 | 34 | 78886 | 236 |

**신규 코드 채번** — 지역·스테이지 선택에서 코드까지 제안한다(§2.5 규약). 일반은 `9{act-1}01`부터 비어 있는 번호를 순차로(Act2에 일반 추가 → `9103`), 보스는 그 대역의 `xx99`를 쓴다. 이미 쓰는 코드면 채번을 건너뛰고 경고한다.

> **씬은 스테이지 배치를 하지 않는다.** 추천 레벨은 `monster_master`가 아니라 **`stage_spawn`에 들어가는 값**이므로, 씬은 그 값을 보여 주고 스니펫에 배치 명령을 적어 줄 뿐이다(§4.5·§7.4). 배치와 마리 수 조정은 `master_monster_tool.py spawn`이 하고, 총 체력이 목표 클리어 시간에 맞는지는 밸런스 시뮬레이터가 판정한다(값 문서 §9.1).

### 4.5 능력치 산출물

씬은 능력치를 두 형태로 내보낸다(F12).

1. **클라이언트 번들 로컬 반영** — `Assets/Resources/MasterData/monster_master.json`에 행을 추가/갱신한다. `MasterDataChangeWatcher`가 이 폴더의 변경을 감지해 `MasterDataManager` 캐시를 무효화하므로 **에디터 재시작 없이** 다음 전투에 반영된다(진행 중 전투에는 반영되지 않으니 스테이지를 다시 입장할 것).
2. **서버 정본 반영용 스니펫** — 세 줄을 출력해 복사할 수 있게 한다: ① 번들 JSON 한 줄 ② `master-data-값.md` §9 표 한 줄 ③ **배치 명령**. ③이 붙는 이유는 `hp`·`attack`이 통일 기준값이라 그것만으로는 그 몬스터가 **얼마나 센지도, 전투에 나오는지도** 정해지지 않기 때문이다 — 세기를 정하는 등장 레벨은 `stage_spawn`이 갖는다(§4.4). 정본 반영 자체는 **`tools/master_monster_tool.py`가 수행**하므로(§7.4) 이 스니펫은 눈으로 확인·수동 대조용이다.

```jsonc
// 출력 예 (Act2 일반 3번째를 5스테이지에 낼 때)
{ "monsterCode": 9103, "name": "스켈레톤 궁수", "hp": 50, "attack": 5 }
| 9103 | 스켈레톤 궁수 | 50 | 5 |
# 배치(등장 레벨은 도구가 레벨 곡선에서 넣는다 — Act2 s5 → Lv9):
python tools/master_monster_tool.py spawn --code 9103 --stages "5:6"
```

### 4.6 무기 스윙 이펙트 색

몬스터가 무기를 휘두르는 순간에만 나오는 **궤적 + 불티**(`MonsterWeaponSwingFx`)의 기준색이다. 상시 이펙트는
두지 않는다 — 가만히 선 몬스터가 빛나면 아군의 무기 강화 이펙트로 오독된다. 색 하나만 정하면 궤적의
밝은 쪽·어두운 쪽과 불티 두 색이 그 색에서 파생된다.

- **정본은 프리팹**이다 — 프리팹 루트의 `MonsterSwingFxPalette`가 색을 담고 런타임은 그 값을 읽는다.
  컴포넌트가 없으면 기본 불티색이다. 런타임이 몬스터 코드로 색을 유추하지 않으므로 코드 대역 규약이
  바뀌어도 전투 연출이 흔들리지 않는다.
- **레시피의 `effectColor`가 초기값**이고, 생략하면 **보스는 그 지역(Act) 컬러링**, 일반 몬스터는 기본색이다.
- 프리팹에 심는 시점은 두 곳 — 자동 빌더(`MonsterUnitFactory.BuildPrefab`)의 저장 직후와 CharacterDevScene의
  `프리팹 저장`. 색 규칙만 바꿨을 때는 재생성 없이 메뉴
  **`TaskbarHero/몬스터/무기 스윙 이펙트 색 반영`** 으로 기존 프리팹 전체에 다시 심는다.

| 지역 | 색 | 값 | 근거 |
|---|---|---|---|
| 1지역 | 녹색 | `#4DE07A` | 지정 |
| 2지역 | 흰색 | `#F0F5FF` | 지정(스켈레톤 계열의 뼈 색과도 맞물린다) |
| 3지역 | 화염 주황 | `#FF6B2E` | 불타는 황무지(`dungeon_bg_3`) |
| 4지역 | 사막 금빛 | `#FFD157` | 사막(`dungeon_bg_4`) |
| 5지역 | 공허 보라 | `#AD61FF` | 보랏빛 묘지(`dungeon_bg_5`) |

씬 우측 패널의 **▍무기 스윙 이펙트 색** 절에서 프리셋(기본 + 지역 5색)으로 고르고, 견본 막대와 hex로
확인한 뒤 `프리팹 저장`을 눌러야 반영된다. 몬스터를 고르면 **저장된 프리팹 → 레시피** 순으로 현재 색을 읽는다.

## 6. 처리 흐름

### 6.1 실행 조건: 에디터 플레이 모드

조합 엔진(`SpumUnitComposer`)은 SPUM 매니저에 의존하지 않아 **에디터 모드에서도 그대로 동작한다**(에디터 스크립트에서 직접 불러 일괄 생성하는 경로를 나중에 붙일 수 있다). 다만 하네스 화면 자체는 런타임 UI를 만드는 `MonoBehaviour`이므로 **플레이 모드에서 쓴다**. 저장은 `AssetDatabase`를 쓰므로 에디터에서만 유효하다(빌드에 포함되지 않는 씬이라 문제 없다 — N1).

**플레이 중 `AssetDatabase.Refresh()`를 부르지 않는다** — "스크립트를 다시 불러올까?" 대화상자가 떠 하네스가 멈춘다. 폴더가 없으면 `AssetDatabase.CreateFolder`로 만든다(실제로 겪은 문제다). 같은 이유로 저장 전에는 프리뷰의 프리팹 인스턴스 연결을 끊는다(`UnpackPrefabInstance`) — 연결된 채로 `SaveAsPrefabAsset`을 부르면 "원본/변형 중 무엇으로 저장할지" 대화상자가 떠 일괄 생성이 멈춘다.

### 6.2 단일 생성 흐름

```
[씬 목록에서 몬스터 선택]  또는  [신규: 지역(Act)·스테이지 선택]
        │
        ├─ 능력치 ─ 지역·스테이지·약몹/강몹 선택 → 등장 레벨 추천 + 통일 기준값 채우기(§4.4) → 코드 제안(§4.4)
        │
        ├─ 외형 ─ 레시피 조회(monsterCode) ─ 없으면 seed = monsterCode 랜덤 레시피 생성
        │
        ▼
1) 레시피 검증    : race·gender·theme·classes·fixedParts 값이 태그 DB에 있는지 확인 (§6.4)
2) 조합           : Random.InitState(seed) → Compose(레시피)                    (F6)
                    파트별 필터 + 랜덤 선택(무기는 방패 50%·듀얼 70% 규칙)
3) 요소 변환      : BuildElements(조합 결과) — 파일명·파트로 패키지 텍스처 조회
4) 색·고정 파츠   : 레시피의 colors/fixedParts를 요소 목록에 덮어쓴 뒤
5) 프리뷰 적용    : ApplyToUnit(프리뷰 캐릭터, 요소)  ← 화면에 즉시 반영(F2)
        ▼
[검수: 애니메이션 재생 — IDLE/MOVE/ATTACK/DAMAGED/DEATH]  (F5)
        ▼
6) 기존 백업      : 같은 이름 프리팹이 있으면 백업 폴더로 복사             (F7)
7) 저장           : SaveAsPrefab(프리뷰, "…/monster_{code}.prefab")
                    → 복제·프리팹 연결 해제 → 비활성 자식 제거 → Animator 배선
                    → 사용 패키지만 남기기 → PopulateAnimationLists → 에셋 저장
8) 저장 검증      : SPUM_Prefabs · _anim · 클립 리스트 3항목 (§7.1)
                    실패하면 백업으로 되돌린다
9) 후처리 훅      : (몬스터는 없음 / 아군 확장 시 컴포넌트 부착·DB 등록)   (N2)
        ▼
10) 능력치 반영   : monster_master.json에 행 추가/갱신 + 정본용 스니펫 출력 (F12 · §4.5)
        ▼
[안내: 던전 전투 배선 빌더 재실행 필요]                                    (F8)
```

**외형과 능력치는 서로를 막지 않는다** — 능력치만 고쳐 반영하거나(프리팹 재생성 없이), 외형만 다시 생성하거나(능력치 그대로) 각각 실행할 수 있어야 한다. 한쪽 실패가 다른 쪽 산출물을 되돌리지 않는다.

**외형의 출발점은 셋이다** — ① 레시피 조합(1~5) ② 저장된 프리팹 불러오기(F15 — 요소 목록을 프리팹에서 읽어 5로 바로 간다) ③ 파트 직접 교체(F14 — 해당 파트 요소만 갈아 끼우고 5를 다시 돌린다). 어느 쪽이든 이후 단계(검수·저장·능력치 반영)는 같다.

**주의점(실측 기반)**

- 저장 경로는 `Assets/Prefabs/Character/Monster/`다. SPUM 기본값(`Assets/SPUM/Resources/Units/`)과 달리 `Resources` 밖에 둔다(빌드 항상 포함·부분 언로드 불가).
- **저장해도 프리뷰는 초기화되지 않는다** — 저장은 프리뷰의 사본으로 하므로 같은 외형을 그대로 두고 이어서 작업할 수 있다(SPUM의 `SavePrefabs()`는 저장 후 프리뷰를 리셋한다).
- 저장물의 `SPUM_Prefabs._code`에는 파일명(`monster_9101`)이 들어간다. 기존 12종은 `SPUM_2024…` 형식이라 **값 형식이 달라지지만**, 전투는 `_code`를 쓰지 않으므로(코드→프리팹 맵은 파일명 기준) 동작에 영향이 없다.
- 실측 검증: 신규 저장물과 기존 `monster_9101`의 구성이 일치한다 — 자식 `UnitRoot` 1개 · layer `UI` · `SortingGroup` 있음 · 패키지 3개 · 클립 IDLE 1·MOVE 1·ATTACK 6·DAMAGED 1·DEBUFF 1·DEATH 1·OTHER 3.
- **요소를 자리에 붙이는 비교는 SPUM 데이터의 지저분함을 견뎌야 한다.** 실제로 두 번 걸렸다.
  - `PartSubType`은 **양쪽 다 값이 있을 때만** 비교한다 — 무기 자리(`L_Weapon`·`R_Weapon`)는 `PartSubType`이 비어 있는데 무기 텍스처는 `Axe`·`Sword` 같은 값을 갖고 있어, 무조건 비교하면 **무기가 한 번도 매칭되지 않아 손이 빈 채로 나온다**.
  - 문자열은 **앞뒤 공백을 무시하고** 비교한다 — 투구 앞면 자리의 `Structure`가 `"Helmet "`(뒤에 공백)으로 구워져 있어, 그대로 비교하면 **투구가 영영 안 씌워진다**.
  - 자리를 정하는 값은 `PartType`·`Dir`(방패 Left / 그 외 Right, 투구 Front)·`Structure`다.

### 6.3 일괄 생성 흐름

일괄 생성은 **외형만** 다룬다 — 능력치는 이미 `monster_master`에 있는 값을 쓰고 덮어쓰지 않는다(대량 밸런스 변경을 도구가 임의로 하지 않는다는 뜻이다). **능력치 일괄 재계산 기능은 만들지 않는다** — 되돌리기와 전투 재검증 비용이 커서 도구가 자동으로 할 일이 아니다. 대신 좌측 목록의 **"기준값 일치 여부" 표시(읽기 전용)** 로 어느 몬스터가 통일 기준값을 벗어났는지 진단만 제공하고, 실제 수정은 한 종씩 사람이 판단한다. 세기 조정은 애초에 이 씬의 일이 아니다 — 그것은 `stage_spawn`의 레벨·마리 수이고, 밸런스 시뮬레이터로 측정해서 바꾼다(`.claude/skills/rebalance`).

1. 대상 결정 — `monster_master` 전체를 순회하며 필터 적용(기본: `monster_{code}.prefab`이 **없는** 코드만. N3)
2. 각 코드에 대해 §6.2의 1~9를 순차 실행(프레임을 나눠 코루틴으로 — 진행 상황이 화면에 보이고, 대량 작업이 에디터를 얼리지 않게)
3. 결과 리포트 — 코드별 성공/실패, 실패 사유(태그 조합 결과 0개 등), 백업된 파일 목록
4. 완료 후 `던전 전투 배선` 재실행 안내(또는 버튼)

## 7. 검수·안전장치

### 7.1 백업·자동 검증

- **백업 경로**: `Assets/Dev/MonsterPrefabBackup/monster_{code}_{yyyyMMdd_HHmmss}.prefab` (SPUM의 `unitBackUpPath`와 분리해 프로젝트 자산으로 관리). 능력치는 `monster_master.json`을 고치기 전 같은 폴더에 원본 사본을 남긴다
- **저장 직후 자동 검증** 3항목 — ① 루트 `SPUM_Prefabs` 존재 ② `_anim` 배선 ③ 상태별 클립 리스트 비어 있지 않음(§2.3). 하나라도 실패면 저장물을 백업으로 되돌리고 실패로 보고
### 7.2 육안 검수

- 생성 직후 미리보기에서 애니메이션 재생(F5). AnimDevScene의 목록 UI 구성을 따르되, 이 씬은 상태별 대표 클립 1개씩만 재생하는 축약 버전으로 둔다
- **전투 확인**(§7.3) — 최종 확인은 `던전 전투 배선` 재실행 후 BattleDevScene/GameScene에서 실제 스폰으로 한다(프리팹 자체에는 전투용 컴포넌트가 없으므로 씬 검수만으로는 부족). 능력치도 이때 함께 본다 — 체감(처치까지 걸리는 시간·아군 피해량)은 표의 숫자로 판단할 수 없다

### 7.3 능력치 검수는 전투에서 한다

몬스터의 세기(= 등장 레벨에서 환산된 `hp`·`attack`)는 전투 길이와 난이도를 직접 정하는 값이라 씬에서 숫자만 봐서는 판단이 어렵다. 이 씬은 검수 편의를 위해 **대상 몬스터 코드를 BattleDevScene 하네스에 넘겨** 그 몬스터만 스폰해 보게 한다. 전투에서 확인할 것 — ① 일반 몬스터가 아군 파티에게 **한두 방에 죽지 않는지**(연출이 보일 시간이 필요) ② 보스가 지나치게 오래 버티지 않는지 ③ 아군이 실제로 죽을 수 있는지(`attack`).

**전달은 `EditorPrefs`로 한다** — 이 씬이 `TaskbarHero.Dev.SpawnMonsterCode` 키에 코드를 쓰고, `BattleDevController`가 `#if UNITY_EDITOR` 블록에서 시작 시 읽어 **그 몬스터만 스폰**한 뒤 **키를 지운다**(한 번만 적용되고 다음 실행에 새지 않게 한다). static 필드와 달리 플레이 재시작·재컴파일(도메인 리로드)을 넘겨도 남고, 인스펙터 필드와 달리 씬 파일을 고치지 않아 커밋에 섞이지 않는다. 하네스 인스펙터의 수동 오버라이드 필드는 그대로 두어, 키가 없을 때 손으로 지정하는 경로를 남긴다.

### 7.4 정본 반영 책임 분리

`monster_master`는 **서버 마스터 데이터**다. 정본은 서버 저장소의 [`docs/세부/master-data/master-data-값.md`](../../docs/세부/master-data/master-data-값.md)와 `master-data-schema.sql`(+ DB 시드)이며, 씬이 직접 고치는 것은 클라이언트 번들과 프리팹까지다. **정본 반영은 `tools/master_monster_tool.py`가 담당**한다.

**씬이 정할 수 없는 값이 하나 더 있다 — 등장 레벨이다.** `monster_master`의 `hp`·`attack`은 통일 기준값이라 씬이 넣을 값이 사실상 정해져 있고, 그 몬스터가 **얼마나 센지**는 `stage_spawn.monster_level`이 정한다(§4.4). 그 행은 서버 정본에만 있으므로 씬은 **추천 레벨을 보여 주고 스니펫에 배치 명령을 적는 데서 멈춘다.** 즉 씬에서 F12까지 마쳐도 배치를 하지 않으면 그 몬스터는 전투에 나오지 않는다.

| 대상 | 갱신 주체 |
|---|---|
| `master-data-값.md` §9 표 · `master-data-schema.sql` `monster_master` | **`master_monster_tool.py add`** (표 + 「규모/현황」 + INSERT + 머리 주석을 한 번에) |
| `master-data-값.md` §11 · `schema.sql` `stage_spawn` (스테이지 배치) | **`master_monster_tool.py add --spawn` / `spawn`** |
| `Assets/Dev/monster-appearance-recipe.json` (외형 레시피) | **`master_monster_tool.py add`** |
| `Assets/Prefabs/Character/Monster/monster_{code}.prefab` | **`MonsterPrefabBuilder`**(에디터 메뉴, 플레이 모드 불필요) — 이 씬은 사람이 눈으로 만들 때 쓴다 |
| `DungeonBattleFlow`의 코드→프리팹 맵 | `던전 전투 배선` 빌더(F8) — 위 메뉴가 이어서 실행한다 |
| `Assets/Resources/MasterData/monster_master.json`·`stage_master.json` (클라 번들) | **`tools/master_data_export.py`** (정본 → DB → 번들). 씬의 F12는 **export 전 임시 확인용** |

**순서가 중요하다** — `master_data_export.py`는 `schema.sql` → DB → 번들 **단방향**으로 번들을 다시 만든다. 정본을 먼저 맞추지 않고 export를 돌리면 **씬이 F12로 고친 값이 덮어써져 사라진다**. 그래서 정본·배치 반영(도구) → 프리팹 생성 → 전투 배선 → 번들 재생성(export) 순으로 간다. 씬에서 F12로 먼저 고쳐 버린 뒤라면 `master_monster_tool.py adopt-bundle`이 그 값을 정본으로 끌어올린다.

**전체 파이프라인은 클라이언트 스킬 [`.claude/skills/master-monster/SKILL.md`](../.claude/skills/master-monster/SKILL.md)가 끝까지 자동화한다** — 외형 컨셉·지역·스테이지만 주면 능력치 산출부터 실제 전투 등장까지 사람 조작 없이 진행된다(프리팹 생성·전투 배선은 Unity MCP `ExecuteMenuItem`으로 호출). 손이 필요한 곳은 값.md §11 (B) 요약 표뿐이고, 필요할 때 `verify`가 경고로 알려 준다.

> **조합 로직의 정본은 [`MonsterUnitFactory`](../Assets/Scripts/Spum/MonsterUnitFactory.cs)** 다. 이 씬과 자동 빌더가 **같은 코드**로 외형을 만들므로 "손으로 만든 것"과 "자동 생성한 것"이 갈라지지 않는다. 자동 빌더는 조립을 **프리뷰 씬**에서 하므로 열려 있는 씬을 건드리지 않으며, 임시 유닛에 `HideFlags`를 붙이지 않는다(`DontSave`는 프리팹 저장을 거부시키고 `HideInHierarchy`는 저장물에 박혀 전투에서 몬스터가 보이지 않게 된다).
