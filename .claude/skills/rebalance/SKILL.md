# 스테이지 리밸런싱 (측정 → 조정 → 정본 → 번들)

밸런스는 **손계산으로 정하지 않는다.** `tools/balance_sim.py`(밸런스 시뮬레이터)가 마스터 수치와 클라이언트 전투 규칙으로 한 스테이지를 고정 스텝 실행해 **클리어 여부·소요 시간·최저 체력**을 낸다. 이 스킬은 그 측정을 축으로 리밸런싱 한 바퀴를 끝까지 돈다.

```
① 목표 확인 → ② 현재 측정 → ③ 수치 조정 → ④ 수렴 확인 → ⑤ 정본 반영
                    ↑______________|
                                          → ⑥ 도구 상수 동기화 → ⑦ 클라 번들 최신화 → ⑧ 문서 동기화
```

## 절대 규칙

1. **측정 없이 수치를 고치지 않는다.** 바꾸기 전과 후를 시뮬레이터로 각각 돌려 숫자로 비교한다.
2. **정본 두 곳(`master-data-값.md` · `master-data-schema.sql`)은 항상 같이 고친다.** `master_monster_tool.py verify`가 오류 0이어야 끝난 것이다.
3. **⑦ 클라이언트 번들 최신화까지가 이 스킬의 책임이다.** 전투는 **클라이언트 권위**라 번들을 다시 만들지 않으면 정본을 아무리 고쳐도 **게임 안 수치는 그대로**다. 여기서 멈추면 작업이 끝나지 않은 것이다.

## ① 목표 확인

정본은 [`master-data-값.md` §9.1](../../../docs/세부/master-data/master-data-값.md)이다. 사용자가 새 목표를 주면 **먼저 §9.1을 그 목표로 갱신**하고 그것을 기준으로 튜닝한다.

| 축 | 현재 확정값 | 어디에 |
|---|---|---|
| 목표 클리어 시간 | 지역 안에서 1스테이지 30초 → 9스테이지 50초, 보스 60초 (±20%) | 값 §9.1-(1) · `balance_sim.py`의 `TARGET_SEC` |
| 기준 파티(투자) | 1지역 1명(신규 계정) → 2지역 2명 → 3지역부터 3명. 2지역부터 **장비 등급·강화·스킬 레벨이 기준에 포함** | 값 §9.1-(2) · `ACT_STANDARD` |
| 하한 파티(무투자) | 한 등급 낮은 장비·강화0·스킬 Lv1. **1지역은 끝까지 클리어, 2지역 중반부터 무너진다** | 값 §9.1-(3) · `ACT_FLOOR` |
| 긴장도(최저 체력) | 지역 안에서 스테이지가 오를수록 좁아진다(레벨이 3스테이지마다 오르므로). 지역별 가장 좁은 지점(9스) 46/68/46/61/36% · 보스 52/43/47/57/53% | 값 §9.3 · `TENSION_S9`/`TENSION_BOSS` |

기준 레벨은 **적지 않는다** — `standard_level()`이 `stage_reward` 경험치와 `level_master`에서 계산하므로 보상을 고치면 자동으로 따라간다.

## ② 현재 상태 측정

```bash
python tools/balance_sim.py baseline                      # 기준 파티 + 하한 파티 한 장 요약(가장 먼저)
python tools/balance_sim.py all --brief --difficulty 1,2  # 100 스테이지 중 목표를 벗어난 것만
python tools/balance_sim.py act 2                         # 한 지역 10스테이지 상세
python tools/balance_sim.py act 2 --floor                 # 투자 안 한 계정이 어디서 막히는지
python tools/balance_sim.py stage 1-1-9 --verbose         # 한 판을 전투 로그로 뜯어보기
```

`baseline`이 **시간 달성률**(목표 대비 %)과 **최저 체력**, 그리고 **하한 파티가 무너지는 지점**을 함께 보여 준다. 여기서 어긋난 축이 무엇인지 먼저 특정하고 ③으로 간다.

## ③ 수치 조정 — 무엇을 만지면 무엇이 바뀌나

| 바꾸고 싶은 것 | 만질 값 | 왜 |
|---|---|---|
| **클리어 시간** | `stage_spawn.spawn_count` (레벨 곡선을 고정한 뒤) | 시간을 정하는 것은 **스테이지 총 hp = Σ(마리 수 × 레벨 배율 hp)** 이고, 여기에 **스폰 하한**(1.5초에 한 마리 · 동시 5마리 → `마리 수 × 1.5초`)이 겹친다. 그래서 마리 수는 총량과 시간에 **동시에** 걸린다 |
| **세기 전반(체력·공격력 동시)** | `stage_spawn.monster_level` | 기준값은 역할별 통일값(일반 50/5 · 보스 50/1)이라 `monster_master`를 만질 일이 없다. 레벨 +1 = 체력 ×1.25 · 공격력 ×1.18 — **한 레벨이 체력 25%라 지수로 튄다.** 레벨을 바꾸면 같은 작업에서 마리 수를 다시 맞춘다 |
| **긴장도(체력이 닳는 정도)** | 그 구간의 `monster_level`, 그리고 **마리 수** | 공격력은 레벨에 묶여 있어 따로 못 만진다. 게다가 **개체가 약하고 많으면 오히려 헐거워진다** — 동시 5마리 상한 때문에 잡몹이 광역기에 빠르게 녹으면 전선이 비고, 맞는 총량이 줄기 때문이다. 반대로 개체가 강하고 적으면 5자리가 계속 차 있어 조여진다 |
| **보스 스테이지** | 보스 `hp`·`attack`을 **일반 몬스터와 따로** | 보스 스테이지는 강몹 8마리가 60초 내내 붙는다. 보스 attack까지 일반 비례로 올리면 **전 직업 즉사**한다(같은 Act 최강 일반의 0.6~1.6배로 지역마다 다르다) |
| **투자 요구 지점** | `ACT_STANDARD`/`ACT_FLOOR`의 장비 등급·강화·스킬 레벨 | "언제부터 장비작·스킬작이 필요한가"는 **몬스터가 아니라 두 프로파일의 간격**이 정한다 |
| **성장 속도(기준 레벨)** | `stage_reward.reward_exp` · `level_master` | 경험치 총합이 100레벨 누적 요구치(`50×L×(L−1)`)와 맞아야 마지막 지역에서 성장이 멈추지 않는다. **골드 곡선과 묶지 말 것** |
| **직업 간 편차** | `class_master`의 `hp`/`atk`/`def` | 마지막 수단이다. 아래 「직업 편차의 진짜 원인」 참조 |

**순서를 지킨다 — 레벨 곡선 → 마리 수(시간) → 프로파일(투자 요구).** 레벨을 먼저 놓아야 개체 스탯이 정해지고, 그 다음 마리 수로 목표 시간을 맞춘다. 순서를 뒤집으면 아군이 죽어 전투가 조기 종료되고, 그 상태의 소요 시간은 측정값으로 쓸 수 없다.

**레벨 곡선의 정본은 값 §11-B다** — 지역 안에서 3스테이지마다 +1(s1~3 / s4~6 / s7~10), 지역이 바뀌면 +3~4, Act1·2의 강몹은 약몹보다 +1. 1지역 Lv1 → 5지역 Lv26까지 **단조 증가**해야 하고(스테이지가 오르면 레벨이 오른다), 보스는 그 지역 잡몹보다 8~13 위다. 곡선을 바꿀 때는 **각 지역의 마지막 구간(s7~10)이 그 지역 긴장도를 정한다**는 점을 먼저 본다 — 그 구간을 한 레벨 올리면 공격력이 18% 오르고 최저 체력이 20~40%p 떨어진다(측정으로 확인된 민감도다).

**튜닝은 이분 탐색으로 한다.** "현재값 × (목표/실측)" 식의 비례 보정은 죽기 직전 구간에서 발산한다(전멸하면 피해량이 더 이상 늘지 않아 되먹임이 끊긴다). 목표 최저 체력을 향해 공격력 배율을 이분 탐색하고, **전사(`dead_allies`)가 하나라도 나오면 실패로 친다.**

**직업 편차의 진짜 원인은 체력이 아니라 광역 처리력이다.** 1지역은 4직업 중 무엇으로도 시작할 수 있는데, 광역 평타(기사)·광역 스킬(마법사·슬레이어)이 있는 직업은 몰려온 무리를 걷어내고 **단일 대상뿐인 레인저는 5마리가 쌓인 채 오래 맞는다**. 공격력만 올리면 레인저·슬레이어부터 전멸하므로, 그때는 `class_master`의 체력 격차를 **좁히는** 쪽으로 답한다(탱커 우위는 `def`와 방패 독점으로 남긴다).

## ④ 수렴 확인

세 가지를 모두 통과해야 ⑤로 간다.

```bash
python tools/balance_sim.py all --brief --difficulty 1,2   # 목표를 벗어난 스테이지 0 · 클리어 실패 0
python tools/balance_sim.py act 1 --party 3 --repeat 5     # 1지역은 4직업(1~4) 각각 · 난수 5회
python tools/balance_sim.py act 2 --floor                  # 하한 파티가 의도한 지점에서 무너지는지
```

- **전수**: 100 스테이지가 목표 ±20% 안, 기준 파티 클리어 실패 0.
- **직업 편차**: 1지역은 **4직업 모두 솔로로** 돌린다. 치명타 난수 때문에 시드에 따라 결과가 흔들리므로 `--repeat 5`(또는 `--seed`를 바꿔가며)로 **최악값에서도 전멸이 없는지** 본다. 최악 최저 체력은 10% 이상을 권장한다.
- **하한 파티**: 무너지는 지점이 §9.1-(3)의 의도와 같은지.

## ⑤ 정본 반영

**두 파일을 반드시 함께 고친다.** 값이 갈라지면 `verify`가 잡아낸다.

| 바꾼 것 | `master-data-schema.sql` | `master-data-값.md` |
|---|---|---|
| 몬스터 hp·attack | `INSERT INTO monster_master` | §9 데이터 표 |
| 스폰 마리 수 | `INSERT INTO stage_spawn` | §11 (B-1)(B-2) 표 + 총 행수 문장 |
| 직업 스탯 | `INSERT INTO class_master` | §2 (A) 표 + 산정 근거 |
| 레벨 곡선 | `INSERT INTO level_master` | §3 공식 + 대표 행 표 |
| 보상 | `INSERT INTO stage_reward` | §10 base 표 + 전개 예 |
| 목표·기준 파티 자체 | 머리 주석의 밸런싱 기준 | **§9.1·§9.2·§9.3 전면** |

- **표의 숫자에 천 단위 쉼표를 넣지 않는다** — `master_monster_tool.py`가 §9 표를 파싱해 SQL과 대조하는데 `1,000`은 읽지 못한다.
- 문서는 **확정된 최종 상태만** 남긴다(변경 이력·이전 값을 적지 않는다). 다만 **왜 그 값인가**는 반드시 남긴다 — 다음 리밸런싱이 같은 논쟁을 반복하지 않게 하는 것이 이 문서의 값어치다.

```bash
python tools/master_monster_tool.py verify    # 오류 0 (경고 "클라 번들이 정본과 다름"은 ⑦에서 해소된다)
```

## ⑥ 도구 상수 동기화

**시뮬레이터는 목표·기준의 사본을 들고 있다.** 목표나 기준 파티를 바꿨으면 여기도 고쳐야 다음 측정이 옳다.

| 파일 | 상수 | 언제 |
|---|---|---|
| `tools/balance_sim.py` | `TARGET_SEC` · `TARGET_TOLERANCE` | 목표 시간을 바꿨을 때 |
| 〃 | `ACT_STANDARD` · `ACT_FLOOR` | 기준/하한 파티(인원·장비·강화·스킬)를 바꿨을 때 |
| 〃 | `TENSION_S9` · `TENSION_BOSS` | 긴장도 목표를 바꿨을 때 |
| 〃 | `CODE_CONSTANTS` | **클라이언트 전투 코드가 바뀌었을 때**(항목마다 `파일:줄` 출처가 달려 있다) |
| `tools/master_monster_tool.py` | `BASE_HP` · `BASE_ATTACK` · `SPAWN_LEVEL` · `BOSS_LEVEL` | 기준값이나 레벨 곡선을 바꿨을 때(`recommend`가 이 곡선으로 등장 레벨을 추천한다) |

> ⚠️ 레벨 배율 상수(1.25·1.18)는 **클라이언트 `MonsterStats`(`Assets/Scripts/MasterData/MonsterStats.cs`)와 같은 값**이어야 한다. 배율을 바꾸면 클라이언트 세션에서 같은 값을 반영해야 한다는 사실을 사용자에게 알린다. 클라이언트의 몬스터 생성 추천 곡선(`MonsterStatCurve` in `CharacterDevRecipe.cs`)은 **몬스터별 hp·attack을 추천하던 옛 구조**를 따르므로, 기준값을 통일한 지금은 `CharacterDevScene`의 추천 표시가 정본과 갈린다 — 클라이언트 세션에서 "기준값 통일 + 등장 레벨 추천"으로 바꿀 필요가 있다.

## ⑦ 클라이언트 데이터 최신화 — **반드시 실행한다**

**전투 계산은 클라이언트 권위**다. `monster_master`·`class_master`·`level_master`를 고쳐도 클라이언트가 읽는 것은 `Assets/Resources/MasterData/*.json` 번들이라, 번들을 다시 만들기 전까지 게임 안 수치는 **바뀌지 않는다**.

```bash
python tools/master_data_export.py     # schema.sql 재적용(MySQL) → 마스터 DB 조회 → 클라 JSON 번들 재생성
python tools/master_monster_tool.py verify   # "클라 번들이 정본과 다름" 경고가 사라졌는지 확인
```

- 이 명령은 **MySQL(도커 `taskbar-hero-master`, `127.0.0.1:3306`)과 `pymysql`** 이 필요하다. 안 떠 있으면 `docker compose up -d`로 **컨테이너만 올려서** 실행한다.
- **MySQL을 끝내 올릴 수 없으면 거기서 멈추고 그 사실을 보고한다.** 정본(⑤)은 이미 반영된 상태이며, 사용자에게 남은 한 단계가 **Unity 메뉴 `TaskbarHero > 마스터 데이터 > 최신화 (DB→JSON)`** 임을 알린다. 임의로 "완료"로 보고하지 않는다.
- 어시스턴트가 **Unity 에디터를 대신 띄우지는 않는다.** 번들 갱신은 위 CLI로 충분하고, 아이콘 DB 재빌드가 필요한 작업(아이템 추가)이 아니면 에디터 조작은 필요 없다.

## 보고 형식

1. **무엇을 왜 바꿨는지** — 레버별로 한 줄씩(예: "보스 공격력을 강몹의 1.6배 → 0.6~1.6배로 지역마다 분리. 강몹 8마리가 60초 내내 붙어 있어 비례 상향은 전 직업 즉사").
2. **측정 결과 표** — `baseline` 출력을 그대로 옮기지 말고, 목표 대비 달성률과 최저 체력 곡선을 요약한다.
3. **하한 파티가 무너지는 지점** — 투자 요구가 의도대로 걸렸는지.
4. **번들 최신화 여부** — 했으면 했다고, 못 했으면 무엇이 막았고 사용자가 무엇을 하면 되는지.

## 하지 말 것

- 시뮬레이터를 돌리지 않고 수치만 고치기 — "이 정도면 되겠지"는 이 스킬의 반대말이다
- 정본 한쪽만 고치기(`verify` 오류 상태로 완료 보고)
- **⑦을 건너뛰고 완료 보고** — 정본만 고친 상태는 게임에 아무 변화가 없다
- 전멸이 나는 상태의 소요 시간을 목표 달성으로 읽기(전투가 조기 종료된 값이다)
- 1지역을 한 직업만 확인하고 넘어가기(신규 계정은 4직업 중 무엇이든 고를 수 있다)
- `class_master`를 먼저 만지기 — 몬스터 쪽으로 풀 수 있는 문제인지 먼저 확인한다
